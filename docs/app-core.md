# App core (schedule-manager.html)

The manager app's skeleton: the page layout, global state, tabs and rendering, the Schedule tab, login and session, data loading and saving, the data-call dispatcher, uploads, telemetry, PWA. Module-specific code is in the other docs.

`schedule-manager.html` is the markup and the page's CSS (inline `<style>`), and one module script, `src/manager/page/entry.ts` (a Vite entry since React migration stage 8c-2): it loads `src/manager/globals.ts` (the data layer and the logic, under their old global names), then the page's own script — the former inline script, the same code, split by section into 18 typed modules of `src/manager/page/` (`base`, `language`, `nav`, `header`, `render`, `worker-window`, `clients`, `workers`, `suppliers`, `windows`, `wiring`, `gate`, `admin`, `bridge`, `toast`, `scan`, `form101`, `init`, imported in that order; each imports only from the earlier ones, so the code runs in its old order; `dom.ts` holds `byId` / `qs` / `qsa`, `globals.d.ts` the names still reached as globals), then the React pieces (`src/manager/main.tsx`), in one bundle. Only the page's names that the markup's handlers, the other modules' forward references (`globals.d.ts`) and the browser tests reach are globals (window accessors); 142 that nothing reached were made module-scoped in React migration 8f. Since the React migration (stages 6–7) every tab and window is React, and since stage 8e-1 the frame too (the title bar, the side menu / bottom bar and More, the bell button, the account menu — `src/manager/Frame.tsx`, below); the page keeps the scan window (the sign-in, the Firms screen, the map picker and the bell's list are React since stages 8e-2 to 8e-4), the data layer and the actions the React pieces call through `bridge()` (`src/manager/bridge.ts`; `window.ManagerBridge` is kept for the browser tests). It loads more files:
- `payroll.js` — before the module, the global `Payroll` (docs/accounting.md → Payroll module);
- `firestore-backend.js` — at startup (the data layer starts loading it), the browser data layer, [backend.md](backend.md);
- pdf.js — when a PDF is read, [scan.md](scan.md).

Modals don't add their own backdrop `onclick`. ## Global state

`workers`, `clients`, `suppliers` (the data; the in-code defaults are demo data, replaced on load), `weekStart` (Sunday of the shown week), `selectedClientId` (Schedule filter), `currentTab`, `editingWorkerId` / `editingClientId` / `editingSupplierId`.

Shared helpers:
- `uid()`, `genToken()`;
- `esc(s)` — HTML-escapes `& < > " '`. **Every value put into HTML must go through it.**
- `fmtDate`, `fmtRange`, `fmtDMY`, `localYMD(d)` — use this, not `toISOString()`, which in Israel gives the previous day;
- `toMins`, `calcHours(s,e)` (crosses midnight), `nowHHMM`, `getSundayOfWeek`;
- `showToast(msg, dur)` (`src/manager/toast.ts`, imported by the page's modules; `window.showToast` is the same function, for the browser tests) — a small note at the bottom right (above the tab bar on a phone): an icon and a coloured left edge by kind, `toastKind(text)` guessing from the text — error (failed, error, not saved…, red), ongoing (ends with …, blue), warning (check, empty, missing…, amber), else done (green); a new one replaces the shown one. A toast whose text reads as an error (failed, could not, offline, denied, ⚠…) is also sent to the error log (`reportError(msg, 'toast')`, Admin → Errors). The punch page has a copy (`src/punch/core.ts`); the other React pages use the Sonner toasts.

## Tabs and rendering

- **Data then draw:** an action changes the page's data (the data layer in `src/manager/data/`, which emits events), then calls `render()`; the React pieces read it through `ManagerBridge` ([build.md](build.md) → The manager's React pieces).
- **`render()`** redraws whichever tab is open (`currentTab`; the React tabs through `window.ManagerIsland`). So an edit made on the Workers tab shows at once.
- **`switchTab(tab)`** toggles the tab/section and renders that tab. Opening Admin also runs `setupAdminPaneBar()`, only there, so a save doesn't reset the Admin pane ([admin.md](admin.md)).
- **Permissions (client-side visibility only; the server enforces):**
  - `hasPermission(section)` — only a `staff` or `hr` role is limited, by its flat rights (`session.rights`, the login reply's `rights` = claim `rt`; an HR's `accounting` is its `commission` right, `exports` / `payEdit` map to `export` / `editPay`); every other role passes;
  - `canChange(k)` — `editSchedule` / `editWorkers` / `editPunches` for a `staff` or `hr` login: one of its flat rights; every other role passes;
  - `NAV_TABS` is the tabs in menu order (Today, Schedule, Workers, Clients, Suppliers, Admin, Accounting, Commission, Hours); `NAV_TAB_PERMISSION` maps tabs to sections: schedule, workers, clients, suppliers, accounting, and `admin` → `workers`. Today is never gated, except for HR (and a staff login on the flat rights: Today and Punch log are their own ticks);
  - `tabAllowed(tab)` adds the HR rule: an `hr` login never gets Today, Admin or Accounting (`HR_HIDDEN_TABS`), and among the firm's logins only an HR gets **Commission** (`hrPayOnly()`, the Accounting section) and **Hours** (`hrHourReview()`, an hours tick); a supplier's Commission and Hours tabs are its own, drawn by the portal view (`portalTabs`, [portals.md](portals.md)) — [accounting.md](accounting.md); `homeTab()` is Today for everyone else and the first allowed tab (Workers by default) for HR;
  - `applyNavPermissions()` hides tabs (Today included) and moves off a hidden tab to `homeTab()`; without the `exports` section it also hides the header Export menu and the salary export (`.perm-exports`).

## Schedule tab (`#sectionSchedule`)

A weekly roster, with changes for single dates. **Drawn in React** (stage 6b): `src/manager/Schedule.tsx` into `#scheduleRoot`, through `window.ManagerIsland.renderSchedule()` ([build.md](build.md) → The manager's React pieces). The page keeps the state and the data — the shown week (`weekStart`), the site filter (`selectedClientId`, the tab's site select), `workers` — and draws the tab with `renderSchedulePage()` (from `render()` while the tab is open, and from `switchTab('schedule')`); the tab reads `ManagerBridge.schedule()` and writes only through the bridge's actions (`setWeek`, `setClient`, `setShift`, `applyDated`, `decideRequest`, `moveWorker`, `editWorker`, `exportAs`, `toast`), which change the page's data, `render()` and `autoSave()`. Schedule only: nothing here touches punches or pay.
- **Shifts:** the weekly roster per weekday in `w.schedule[0..6]` (Sunday first), plus changes for one date only in `w.dateShifts` (`{'YYYY-MM-DD': {type, start, end}}`), which win over the roster on that date. `shiftOn(w, date)` gives a date's shift (marked `dated` when it comes from `dateShifts`), `weekShifts(w)` the seven of the shown week; the page's copies feed `workerTotalHours`, the exports and the Today tab, the tab's own copies are in `src/manager/schedule.ts` (`shiftOn`, `weekShifts`, `weekHours`, `visibleWorkers`, `copyPlan`; CLAUDE.md → Duplicated on purpose). Date changes older than 62 days are dropped on save (`pruneDateShifts`).
- **Week navigation:** the week always opens on the current week; `applyData()` does not restore the saved `weekStart`. ‹ / › (glass icon buttons) move a week, a tap on the week's dates opens a calendar (Popover + Calendar) and the picked day's week is shown (`setWeek`, local dates).
- **Who is shown:** `visibleWorkers` (the page's `getVisible()`, still used by the exports) — with a site, the active workers of that site; otherwise only active workers with a working day in the roster or in the shown week.
- **Layout (variant 6 → V7):** the sub line, then the week navigator: ‹, the week's dates over "This week · Nh · N shifts" (the visible workers), ›, and the export icon (a Dropdown Menu, only with the `exports` section: Excel, PDF, JSON of the shown week — the page's `exportExcel`, `exportPDF`, `exportJSON`). Under it **one site select** (`data-testid="site-select"`; owner, 2026-10-26 — a row of tabs broke with many clients): **All sites** first, then the sites by name; a pick runs `setClient` → `filterByClient`, the same filter the tabs had. The breadcrumb reads the picked one from the select's wrapper (`data-crumb`): "Schedule › All sites", "Schedule › Site A", the workers' requests, then the **Workers** section (its count; with the `schedule` section its tools: Copy last week, Repeat for N weeks, Select).
- **A plate per visible worker** (`PagedList` with `columns`, 10 at a time): the name, "site · N shifts" and seven **day marks** for the shown week (green work, blue a night crossing midnight, amber off while on vacation, grey off; today ringed), the week's hours in green and an arrow; the bar green with shifts, amber on vacation. A tap opens or closes its 7 days under it (kept open while the app is open): a line per day — the day, date and site (today in accent), a dot when the day was changed for that date only, "Can't work" when the worker marked that day, the times in the figure green (blue across midnight) or "Day off" in amber. A double click / long press (or ⋮ → Edit) opens the worker window (`openEditWorker`). On a computer, with the `schedule` section, a plate can be dragged onto another to put it before it in the roster order (`moveWorker`, saved).
- **The shift window** (a day line, with the `schedule` section; `Window`): Working / Day off, **Applies to** — "Every <weekday>" (writes `w.schedule[di]` and removes a change of that date) or "Only <date>" (writes `w.dateShifts[date]`) —, start and end with the hours badge ("crosses midnight"), Save; a dated day also offers "Back to the weekly schedule" (drops the date's change).
- **Copy last week / Repeat for N weeks** (owner, 2026-10-17; `copyPlan`): Copy last week puts each working day of the previous week on the same weekday of the shown week; Repeat puts each working day of the shown week on the next 1, 2, 3, 4, 6 or 8 weeks (picked in the window, 4 by default). Each copied day is a change for that date only. **No overwrite:** a day that already has a shift keeps it — a working roster day, any change for that date (a day off set for that date too), or a day the worker marked they can't work. The Workers tools act on the visible workers; in **Select** mode the bar's Copy last week / Repeat act on the ticked ones. The window lists every shift that would be added (worker, day, times) before anything changes; "Add N shifts" applies them (`applyDated`, then `autoSave()`) and the Undo snack ("N shifts added · Undo", `undoDelete`) takes them back for 5 s.
- **Requests from workers** (stage 5b; a panel above the workers): `loadShiftRequests()` (the backend's `loadShiftRequests`, at most once a minute while the tab is drawn) reads the workers' `shiftRequests` from today on and hands them to the tab (`schedule().requests`). A plate per pending shift offer ("Avi → Dana", the date and times, an amber note when the colleague already works that day) and per day a worker can't work (with the shift planned that day, if any), offers first, paged by 10, filtered by the site tab. With the `schedule` section an offer has **Confirm** (one tap) and ✕ Decline: the page's `decideShiftRequest(id, ok)` — on Confirm the worker's date becomes a day off and the colleague's date gets the shift (both changes for that date only, `w.dateShifts`), sent with the schedule to the backend's `decideShiftRequest`, which writes the request's `confirmed` and both workers in one batch — all or nothing; on a failure both dates are put back. Decline only marks the request `declined` (the rules let a decision change only its status). Both workers must be in the login's list (an own-workers HR's holds only its own; a colleague of another HR is the manager's to hand over).
- **Loading and empty:** Skeleton plates until the page has its data; with no one to show, an `Empty` frame ("No one on the schedule") with Add a worker (with the `workers` section).

## Login and session

- **Session:** `localStorage.schedMgr_session` (`SESSION_KEY`). It only remembers who is signed in; the real authentication is the Firebase sign-in (the rules and the functions check the Firebase ID token). `getSession()` returns `null` and clears the session when it has no `uid` (a session from before the move off Apps Script has none, so that user logs in once more).
- **Session fields:** `uid` (the Firebase user), `role` (`superadmin` / `tenant_admin` / `staff` / `hr`), `tenantId`, `username`, `tenantProfile`, `rights` (staff / HR / supplier / client: the flat rights; refreshed from the ID token at start), `supplierId`, `clientId`, `ownOnly`, `commissionRate` / `commissionDayRate` and `fullName` (HR), `viewingTenantId` (and `viewingTenantName` / `viewingTenantProfile` for a super-admin).
- **Language:** one Language button per screen (React `LanguageButton`, English by default): in the frame's title bar before the account, in the sign-in screen's corner, in the Firms screen's header; it calls the page's `setLanguage()` through `ManagerBridge`, and every React root follows the page's language (`LanguageScope`, the frame state's `lang` — `syncLangButtons()`); the choice is kept on this device (`localStorage.uiLang`) and, when signed in, on the user's account (`updateMyLanguage`); `signIn` takes the account's `language` from the login reply. Before `gateApp`, `loadI18n(storedLanguage())` loads that dictionary and `applyI18n()` translates the static texts ([translations.md](translations.md)).
- **`gateApp(runInitApp)`** decides the screen:
  1. No session → `#loginScreen` (frame state `screen: 'login'`), and a warm-up `{ping:true}` to the `login` function (`pingLogin`, from the sign-in screen); its time is kept in `window.__pingMs`.
  2. A super-admin with no firm picked → `#firmsScreen` (`renderFirmsScreen()`: the React `FirmsScreen`, which loads the firms, `loadFirms()`).
  3. Otherwise → `renderAccountControl(s)` and the init sequence: `loadData()`, `render()`, `applyNavPermissions()`, `switchTab(homeTab())`, `warmCloudFunctions([USERS_ADMIN_FN_URL])` (sends a warm-up `{ping:true}` to `users_admin` so its first real call skips a cold start).
- **`submitLogin()`:** `firestore-backend.js` `login()` — the `login` function checks the password and returns a custom token, then the device signs in to Firebase with it. The session is saved, the login timing kept in `sessionStorage.pendingLoginTiming`, and the page reloads. A staff / HR / supplier / client session without `rights` (signed in before the flat rights; its token has no `rt` claim, so the rules refuse it) is cleared at start and the sign-in shown (`gateApp`). A **supplier** or **client** login stays here (permissions plan, stage 3): `gateApp` runs `startPortal` instead of the app's start — the same frame with its own tabs (`portalTabs`, `src/manager/portal.ts`), every tab drawn into `#sectionPortal` by `src/manager/Portal.tsx` with the portal's screens over the `supplier` / `hours` functions (`switchTab` and `render()` draw only that while `portalInfo()` is set, `nav.ts`); no firm data is loaded, nothing reads Firestore. It also writes the portal's own session key (`supplierPortal_session` / `clientPortal_session`), which those screens read, and takes over such a key left by the old portal pages (`adoptPortalSession`); Sign out clears them too (`clearPortalSessions`).
- **Firms:** `switchToTenant(tenantId)` (super-admin) sets `viewingTenantId` / Name / Profile and reloads. `backToFirmsList()` has no UI caller.
- **`logout()`** first saves a change that is still waiting (`flushSave()`, `src/manager/data/store.ts`: the 800 ms debounce runs at once, a save under way is awaited — for at most 5 s, and not at all while the device is offline, since a Firestore commit without a network never settles; it lands once the device is back online); when a change still has not reached the server (offline, a failed save, an edit queued before the load), or another firm opened on this device still has changes kept after a failed save (`unsavedFirms()`, `src/manager/data/session.ts`: a `schedMgr_v1_<firm>_unsaved` flag younger than 3 days with that firm's cache still here — the purge removes every firm's data, not only the open one's), it asks "Changes on this device have not reached the server yet and will be lost. Sign out anyway?" and stays signed in on Cancel. Then it clears the Firms and admin caches and the session, removes the firm data kept on this device (`purgeDeviceData()`, `src/manager/data/session.ts`: every `schedMgr_v1*` key — the cache per firm, its `_bak` / `_unsaved` / `_base` copies, and the unscoped `schedMgr_v1` older builds wrote — and the punch caches `punchLog:<firm>`; the firm-wide `punchLog` older builds wrote is removed once, on the first purge (flag `schedMgr_sharedPunchLogCleared`)). It keeps the punch page's own keys — its history `punchLog` and its worker cache `punchWorkers_v1` (the same origin: a foreman's phone may hold both) — and the Form 101 rebuild flags `form101Regen:<firm>` (no firm data; the rebuild they promise still runs when that firm is opened). Then it signs out of Firebase, and reloads. A sign-in (`signIn` → `adoptLogin(uid)`) does the same purge when the login differs from the device's last one (`schedMgr_lastUid`), so a login never sees, or saves back, another login's cached workers or punches (an own-workers HR after the owner on a shared tablet).
- **Requests:** `gsAuth()` → `{asTenantId}` for a super-admin viewing a firm, otherwise `{}`; `gsAuthQuery()` is the same as a query string.
- **Firm profile** (Form 101 employer block):
  - `FIRM_PROFILE_FIELDS` — company name, deductions file, phone, street, city;
  - `activeTenantProfile()`, `firmProfileMissing()` (the amber warning lists the missing fields; a tap on it opens the firm form, `openMyFirmForm`);
  - `cacheTenantProfile(tenantId, profile)` keeps the session copy current after an edit;
  - an incomplete profile colors the Admin tab icon amber (`renderAccountControl`).

## Data calls

The code of this section and the two after it (Loading and saving data, Telemetry) — and of `getSession` / `saveSession` / `clearSession` / `gsAuth` / `fsTenantId` / `STORAGE_KEY` (Login and session), the punch cache (`getPunchLog` / `savePunchLog` / `ensurePunchesSince` / `mergeRemotePunches`), `uid()` / `genToken()` and the data itself (`workers`, `clients`, `suppliers`, `__dataReady`) — is TypeScript in `src/manager/data/`, bundled into the page's module (`src/manager/page/entry.ts`, through `src/manager/globals.ts`). It is layered, each file using only those above it:

| File | What |
|---|---|
| `events.ts` | the events the layer emits and the page answers (`data`, `punches`, `hours`, `save`, `notice`, `loaded`), the `Message` type (a text and its values, untranslated), and the page's answers to its questions (`setHost`: may this login write workers, is a worker window open, the week on screen) |
| `ids.ts` | `uid()`, `genToken()` |
| `session.ts` | the session, the firm worked in, the cache key, `gsAuth` |
| `state.ts` | the data: `workers`, `clients`, `suppliers`, `ready`; `applyData`, `getDataObj` |
| `telemetry.ts` | errors and timings (Telemetry below) |
| `api.ts` | `firestore-backend.js` loaded once, the dispatcher, the direct calls, uploads |
| `punches.ts` | the punch cache and its sync |
| `store.ts` | load, save, the offline cache, the HR and hours watchers |

The page's logic that decides or computes without drawing is in `src/manager/logic/` (React migration stage 8c-1), in the same bundle (through `src/manager/globals.ts`) and under the same old names: `access.ts` (Permissions below: `hasPermission`, `tabAllowed`, `homeTab`, `hrPayOnly`, `hrHourReview`), `i18n.ts` (`tr`, `uiLocale`, `storedLanguage`, `loadI18n` — the markup's `applyI18n` and the Language button stay on the page), `util.ts` (`esc`, `loadXlsx`, `calcHours`, `fmtDMY`…), `pay.ts` (the pay wrappers over `payroll.js`), `workers.ts` (`isActiveWorker`, `workerExpiryStatus`, `workerDocStatus`, `workerDocId` / `workerAddress` — the last two from `src/manager/worker.ts`), `uploads.ts` (Uploads: `fileToUploadPages`, `filesToUploadPages`, `fileForStorage`, `downscaleForUpload`), `functions.ts` (the Cloud Functions' URLs, `warmCloudFunctions`), `schedule.ts` (the Schedule's week and site filter — `weekStart` / `selectedClientId` are accessors to it — `shiftOn`, `weekShifts`, `workerTotalHours`, `getVisible`, `filterByClient`, `pruneDateShifts`, the workers' requests `loadShiftRequests` / `decideShiftRequest`, which emit `requests` / `data`), `exports.ts` (`exportExcel`, `exportPDF`, `exportJSON`, `getWorkerMonthShifts`, `exportShiftsDetail`), `admin.ts` (`firmProfileMissing`, `activeTenantProfile`, the Admin caches `saveAdminCache` / `loadAdminCache`, `adminPanes`, `USER_ROLE_LABELS`, `hrColor`, `assignWorkersToHr` / `assignWorkersToSupplier`, `firmsPayableRows(firms)`, `logPeriodRange`, `copyTextToClipboard`). A logic toast is `notify(text)` with a text already translated by `tr()`.

**It never draws:** it never calls a page function, shows a toast or looks at the DOM. The page answers its events in one block (`schedule-manager.html` → "The data layer's events", next to the Save / Load section): `data` → `render()`; `punches` → the open tab's redraw (Today, Accounting, Admin); `hours` → the Accounting badge (`updateHoursBadge`, from `pendingHoursCount()`), the bell, the open windows, Accounting; `save` → the save indicator (`setSaveStatus`); `notice` → `showToast(tr(text, vars))`; `loaded` (fresh server data) → `maybeRegenAfterFirmEdit()`. Its entry `global.ts` gives the page every function under its old name on `window`, the data as read / write accessors (`workers = …` on the page replaces the layer's list), and the state the page reads as read-only accessors (`__uploadsInFlight`, `__punchLoadedFrom`, `__punchSynced`, `__hoursBatches`), so the page's other code and the browser tests call them as before.

- **Direct calls:** `gsLoad` / `gsSave` / the punch listener (`syncPunchesFromGS`) / `gsSavePunch` / `gsUpdatePunch` / `gsDeletePunch` / `gsDeleteWorkerDoc` call `firestore-backend.js` for `fsTenantId()` (the firm being worked in). The names are old; there is no other backend.
- **The dispatcher (`API_URL`):** every other data call is written as `fetch(API_URL, {method:'POST', body: JSON.stringify({action, ...})})` or `fetch(API_URL + '?action=…')`. `API_URL` (`'api://app'`) is not a server: a `window.fetch` wrapper sends the call to `firestore-backend.js` `handleAction(action, params, ctx)` and returns its answer as a JSON `Response`. It covers the firms and users actions, Errors / Timings, telemetry, `deletePunchesByMonths`, the hours queue, another firm's `loadSchedule` / `loadPunchLog`, `loadWorkerAssets` / `deleteWorkerDoc`, and the six AI actions ([backend.md](backend.md) has the list). Any other `fetch` passes through untouched.
  - An action nothing answers → `{error:'Unknown action: …'}`; an exception → `{error:'Firestore: …'}`.
  - A call slower than 2500 ms (`SLOW_API_CALL_MS`) goes to Timings as `gs:<action>`. An AI reply's `_meta` (from `ai_read`) is taken off the reply and kept in that measurement's details, with the request's `part`.
  - A reply whose `error` is exactly `SESSION_EXPIRED_ERROR` (the functions refused the Firebase ID token — signed out, or revoked after a rights change) clears the session and reloads to the login screen. Telemetry and login never trigger this.
- **Uploads:** `uploadWorkerFile(body, onProgress)` — `saveWorkerDoc` / `saveWorkerPage` / `saveWorkerSignature` / `saveWorkerFile` go to Storage through `firestore-backend.js`, with real byte progress, and reply `{ok, id, url}`. The replaced file (`previousFileId`) is deleted afterwards (`gsDeleteWorkerDoc`). `DOC_STORE` = `'Firebase Storage'` names the store in the UI. `__uploadsInFlight` counts running uploads; a new-version reload waits for it to reach 0.

## Loading and saving data

- **Cache:** `localStorage`, under a key per firm: `STORAGE_KEY()` = `schedMgr_v1_<tenantId>` (plus `_bak`), and next to it the **save base** `BASE_KEY()` = `…_base`: the data as the app held it when it was last in step with the server (per kind, record id → a hash of the record; `scheduleBaseOf(data)` of `firestore-backend.js`, written after every server load and successful save — for a save, of the data that save sent — only when the cache it belongs to was written; when the cache write fails, or the base itself does not fit, the base is removed, so the base is never newer than the cache). Nothing is written under the unscoped `schedMgr_v1` any more (the punch page keeps its own cache, `punchWorkers_v1`). Every cache write is best-effort (a full `localStorage` is logged and skipped): it never stops a save or a load.
- **`loadData()`:**
  1. Draw the cache at once (`applyData`, `render`, `markFirstContent`).
  2. `gsLoad()`. On success → `applyServerLoad()`, `markFreshContent('app')`, `syncPunchesFromGS()`. On failure → a toast with the reason and `retryLoadDataWhenBack()` (on `online`, on the tab becoming visible, or after 15 s).
- **`gsLoad()`:** `backend.loadSchedule(fsTenantId())`. With no Firebase user the session is cleared and the page reloads. A failure is kept (`loadError()` in `api.ts`) and sent to Errors.
- **`applyData(d)`** fills `workers` (defaults: `id`, `clientIds`, `token`, `status`), `clients` and `suppliers`.
- **`applyServerLoad(gd)`:** if this device has unsaved changes (`hasUnsavedLocal()`, the `UNSAVED_KEY()` flag younger than 3 days, an edit queued before the load came back, or an edit whose 800 ms save has not run or finished yet — a retried load landing in between), it keeps them and calls `autoSave()` instead of applying the server copy — that save is a **merged save** (below). Otherwise it applies the server data and writes the cache and the save base.
- **`autoSave(opts?)`:**
  - it refuses to save an empty state over a cache that had data ("Empty data — save skipped"), unless `opts.allowEmpty` — the explicit deletes of workers (`ManagerBridge.deleteWorkers`) and clients (`deleteClientsNow`) pass it, so deleting the last one is saved too (`gsSave`'s own empty check lets it through as well);
  - before the first server load has settled it only keeps the edit on the device (cache + `UNSAVED_KEY()`) and the save waits for the load (an edit on the cached list never diffs against a server copy it was not made from);
  - otherwise it debounces 800 ms, then writes the cache, sets `UNSAVED_KEY()` and calls `gsSave(getDataObj(), {base, allowEmpty})`; the flag is cleared on success;
  - **merged save:** while the local data is not what this page last loaded or saved (the cache, or changes kept after a failed save), `base` is the stored save base: `saveSchedule` reads the server's copy fresh and merges first (`mergeOnBase`): a record edited or added here keeps this copy, one untouched here takes the server's (an edit made elsewhere stays), one deleted here is deleted, one deleted elsewhere and untouched here stays deleted, one added elsewhere (not in the base) is kept. The merged data becomes the app's (unless it was edited again during the save, or a worker window is open — then the next save merges again against the same base). With no stored base (a cache from before the save base existed, or one removed by a full `localStorage`) `base` is `'unknown'`: every record the server has keeps the server's copy, a record only on this device is saved, nothing is deleted, and when a local record differed from the server's copy the toast says "Changes kept on this device could not be merged with the server — the server copy was kept";
  - `savePending()` is true from the edit until its save has run (the new-version reload waits for it).
- **`gsSave(data, opts)`:** refuses a payload with no workers and no clients (unless `opts.allowEmpty`); otherwise `backend.saveSchedule(t, data, undefined, opts.base)`, which writes only the changed documents (two managers editing different workers never overwrite each other); a merged save's data comes back through `opts.onMerged`. Returns whether it saved. Toasts: "Saved" / "Save failed — kept on this device".
- **Shortcut:** Ctrl/Cmd+S saves.

Punches have their own path (`gsLoadPunchLog`, `mergeRemotePunches`, month windows) — see [admin.md](admin.md) → Punch log.

## Telemetry

- **Errors:** `reportError(message, source, stack)` — at most 40 per page, the same message at most once a minute. It is fed by:
  - `window` `error` and `unhandledrejection`;
  - every `console.error` / `console.warn` (wrapped), except the Firestore SDK's reconnect warnings (`SDK_RECONNECT_NOISE_RE`: the live listener's stream "transport errored" / "Could not reach Cloud Firestore backend" — the SDK reconnects by itself). Google Maps' notice that `google.maps.Marker` (the client map picker's pin) is deprecated (`MAPS_MARKER_NOTICE_RE`) is reported at most once a day per device (`_mapsNoticeSeenToday`, `localStorage.mapsMarkerNoticeAt`) — it still works; moving to `AdvancedMarkerElement` needs a Map ID from the Google Cloud console;
  - toasts matching `ERROR_TOAST_RE`;
  - the form error lines `firmEditFormError` / `userFormError` (`watchErrorLine`, a MutationObserver).
- **Timings:** `reportTiming(kind, totalMs, details)` adds `device`. Kinds:
  - `login` / `open` — `markFirstContent()` / `markFreshContent(screen)`, once per page;
  - `scan` / `scanFiles` — [scan.md](scan.md);
  - `form101` — every Form 101 build (`aiFillForm101`): the build time and what the form carried, as flags and counts only (`regen`, `docType`, `spouse`, `spouseNames`, `children`, `marital`, `extraPages`) — no personal data;
  - `gs:<action>` — slow calls.
- **Sending:** both go into a queue (`queueTelemetry`). `flushTelemetry()` sends it as one `logBatch` through the dispatcher: first 8 s after load, then every 5 s, and on page hide. It becomes Firestore `errors` / `timings` documents (one batch write); before the Firebase sign-in it is dropped.

Shown in Admin → Errors / Timings ([admin.md](admin.md)).

## PWA

- **Service worker:** `service-worker.js` (cache `schedule-mgr-vNNN` — bump the number on every deploy that changes the app). It leaves `/scan/` and `/scan-lab/` (the scanners' ONNX Runtime and models, tens of MB) to the browser's own cache, which revalidates them by ETag instead of downloading them on every page load, and on an update it deletes only its own old caches (`schedule-mgr-*`) — the scanners' model caches (`scan-models`, `scan-lab-models`) stay.
  - Network-first, with `cache:'no-store'`; the cache is only the offline fallback.
  - It never touches POSTs or other origins (Firebase, Cloud Functions, CDNs).
  - `.woff2` font files are the exception: cache first (they never change under the same URL).
  - `CORE` precaches the pages, `payroll.js`, `og.css`, the manager's manifest, app icons, `fonts/fonts.css` and the icon subset.
  - An offline navigation falls back to the matching page.
  - It has no push handlers: the app sends no push notifications.
- **Registration:** the page registers the worker with `updateViaCache:'none'` and calls `reg.update()`. When a new version takes control (`controllerchange`) it reloads once, when the page is idle: no upload running (`__uploadsInFlight`), no change waiting to be saved (`savePending()`) and no window open (`.overlay.open`); until then it checks again every second.
- **New version check** (`startVersionWatch(files)` / `showNewVersionBar()`; the new pages: `useVersionWatch`). An app left open keeps the code it loaded, even after a deploy. When the page comes back to the screen (`visibilitychange`), and every 30 min while it is shown, the files it runs are asked for their ETag with `HEAD` and `cache:'no-store'` (the service worker only handles GET): here the page itself, `og.css`, `payroll.js` and `firestore-backend.js` (the portals: the page, `og.css`, `firestore-backend.js`; the punch page: only itself and `og.css`). The first answer is the baseline; a changed ETag shows one compact line at the top of the screen (a dark pill under the status bar, so it never covers the bottom tab bar): "A new version is available · Update" (reload) and ✕. Nothing reloads on its own. Offline or a failed request: nothing happens.
- **Install:** `beforeinstallprompt` → "Install app" in the account menu; iOS gets instructions in a toast.
- **Push:** none. The page does not subscribe to push and the service worker has no push handlers (no sender exists).
- **Manifests:** `manifest.json` (manager, start `./schedule-manager.html`, copied as is) and `manifest-punch.json` (the punch page's, [punch.md](punch.md): built by Vite into `dist/assets/manifest-punch-<hash>.json`, so its paths are absolute — `id` and `start_url` `/worker-punch.html`, `scope` `/`, the icons `/icon-*.png`).
