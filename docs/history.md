# History

Chronological, narrative record of *why* things ended up the way they are —
bug-fix rounds, reverted approaches, and the reasoning behind design choices
that changed more than once. **CLAUDE.md and the other `docs/*.md` files describe only the
current state** (what a function does now, current data shapes, current
architecture); when a change is genuinely just "current behavior," it goes
there, not here. This file is where the debugging trail and the abandoned
alternatives live, so CLAUDE.md doesn't have to carry them forever.

Read this when: you're about to change something and want to know what has
already been tried and reverted, or why a rule is the way it is.

## Apps Script removed (2026-10-03)

After every firm was copied to Firestore ("Copy to Firestore") and every worker file moved from Drive to Storage ("Move files to Firebase", all firms at "Left 0"), the Apps Script backend was removed entirely:

- **Gone:** `apps-script/` (`Kod.js`, `appsscript.json`, `.clasp.json`), its copy `google-apps-script.js`, the `deploy-apps-script.yml` workflow and `scripts/refresh-clasp-login.sh`; the per-device `?backend=sheets` switch in all three pages; the Apps Script session token (`gsToken`, minted by the `login` function with `GS_SESSION_SECRET`) and the sliding-token refresh; `API_SECRET`; the `gs_upload_proxy` function (CORS relay to Apps Script); the `migrate_from_sheets` and `migrate_files` functions with their Admin → Firms buttons; the Errors / Timings merge with the sheets; the punch page's JSONP fallback.
- **Why it was safe:** the data and files were already in Firestore and Storage, and Firestore had been the default since stage 8. Old Drive file ids were all replaced by Storage paths by the file move.
- **AI tests:** `tests/auth/test_ai.py` used to run the real Apps Script AI actions in Node and require identical requests. Before deleting `Kod.js` every test case was run once and recorded in `tests/auth/ai_golden.json`; the test now compares against that file. `functions-auth/ai_prompts.json` stopped being generated and became the source of the prompts.
- **Left in place:** the spreadsheet (as an archive), the Apps Script deployment (until archived by hand in the Apps Script editor), the Secret Manager secret `GS_SESSION_SECRET` (unused), and the `workerTokens` collection (unused, still denied by the rules).
- **Fixed along the way:** the punch link showed "Connection problem" instead of "Invalid Link" for an unknown or regenerated token (the `punch` function answers `Unknown worker link`, which the page treated as no answer), so a regenerated link kept working from the device cache; and punches from the link were saved with `day: null` (the page sends no date) — the function now takes the day from the punch time in Israel.

The full Apps Script code and the earlier docs describing it (`docs/apps-script.md`) are in git history before this change.

## Scan crop cut printed text (fixed 2026-10-04)

A real Israeli ID front came out with its header row and the vertical number on the left cut off. Both edge searches (`refineQuadCorners`, and `finalTightenPass`'s former `_scanSideEdge`) took the nearest strong brightness jump as the card's edge, and a bold printed line a few pixels inside the edge is exactly that. `finalTightenPass` started 3 % inside the frame, so on an already tight page it always found the text first and cut it. A synthetic benchmark (a card with text by its edges on a textured table; the AI's guess exact, 2–4 % too tight or too loose, or jittered; three angles) reproduced it: 40 of 75 crops lost a corner for a blue ID card and 65 of 75 for white paper. The fix is the card edge test (`_edgeTools`, docs/scan.md): it needs card colour inside the jump and something else outside. It also adds a robust line fit and has `finalTightenPass` search from the border inward. Result: 0 of 75 cut for both, and an already tight page is no longer touched. Paper on an almost-white table can't be told from the table, so its corners stay the AI's guess. The `detectAlign` prompt now asks the model to place an unsure edge slightly outside the document.

A follow-up the same day: a scanned ID still kept a tilted black band (about 10 % of the height) under the card. The final pass only searched 6 % in from the frame and only cut straight across. `finalTightenPass` is now `refineQuadCorners` from the full frame (15 % inward, fitted lines, so a tilted band is cut along its tilt). The edge test now needs the outside stretch to be background without a card-coloured gap, because a bold header line plus the table beyond it had passed the old 80 % rule. A fitted line is kept only if the edge test passes along it. Benchmark, now 111 crops plus 9 tilted-band crops: 0 cut for a blue ID or for paper on dark or grey tables, every band removed, 2 of 111 cut for paper on an almost-white table (5 before).

The same day, the report "the preview is straight but the PDF photo is crooked" was traced to the review-screen thumbnails, not the PDF. They were 64 px squares with `object-fit:cover`, which hid the band at the bottom; the PDF shows the same image, whole. The thumbnails now use `contain`. The new `finalTightenPass`, run on a screenshot of that real scan, removed the band. The test device was likely still running the old `scan-pipeline.js`: it is loaded once per page, and Hosting served `.js` with its default `max-age=3600`. All `.js` files are now `no-cache`.


## Scan misread Hebrew names (fixed 2026-10-04)

A real ID came out with one surname letter wrong: ד read as ר, the classic look-alike pair. Two causes. Since the "every boxed field is re-read zoomed" change earlier the same day, the zoomed re-read of a name always replaced the full read, so a crop that was off or blurred won on its own. And the crop was blurred: the page is shrunk to 1800 px before anything else, a name line is ~25-30 px tall, and the crop was only that, stretched — the corner that tells ד from ר is 1-2 px.

The fix (docs/scan.md → Sharper field crops, Merging pages): field crops are cut from the photo as taken, through the page's own geometry steps; a zoomed text read no longer replaces the first read; and the holder's name is picked from every reading — the front's read, its zoomed re-read, the ספח / card back's copy (which `aiReadSefach` now returns) — with the Latin spelling or the MRZ name line, when the document has one, deciding between them.

Tried first and dropped: rebuilding a sharp copy of the whole page from the photo (replay the warps at up to 3200 px), then cropping from it. On a 4x-throttled CPU that took ~4 s per page (the per-pixel warp of the whole card), and for a ספח it would have added to the wait. Cutting only the field regions from the photo takes ~0.5 s for all of a scan's fields.

## Slow ספח read (fixed 2026-10-05)
The ספח read took 9–11 s, and once 22 s. Two dead ends first:
- Asking for fewer `fieldBoxes` saves nothing, because the prompt already asks for the address boxes only.
- Cutting the photo in half is risky: the cut can go through a child's row or the address.

The time goes into writing the long answer, so `readSefachPage` now asks for it in two halves at once (`aiReadSefach` with `part`: holder / family, docs/scan.md). Both halves use the same cached prompt. The cost is under a cent more per scan.

The first version kept a single read for `id_back` pages. The next live scan still waited 22 s, because the align model had classified a paper ספח as `id_back`. So every extra page is now split. The same scan also added `_meta` to `ai_read` replies (time at Anthropic, tries, tokens, docs/backend.md), so that a slow AI call in Timings shows where its time went.

## The edges training's checks on a new PC (2026-10-21)

- **"the PyTorch copy does not answer like the model"** — `train.py` checked the onnx2torch copy on the GPU, where PyTorch (2.14, CUDA 13) runs convolutions in TF32: the copy differed from ONNX Runtime by ~3e-3 against a 1e-3 bound, while on the CPU (or with TF32 off) by ~6e-7. The copy was right; the check now runs on the CPU before the model moves to the GPU, and the training keeps TF32's speed.
- **`UnicodeEncodeError: 'charmap' codec can't encode character '→'`** — a Hebrew Windows' console is cp1255, which has no "→"; `datasets_hf.py push` stopped after its first set. `home.py`, which every script imports, sets the scripts' output to UTF-8.
- **An exam on the training pages** — with no user's page kept apart, `exam.py` examined the models on every example (`exam or ex`), the ones they had just learned; it now examines MIDV's and SmartDoc's exam documents and never the training pages.
- **"Playwright does not support chromium on ubuntu26.04-x64"** — GitHub moved `ubuntu-latest` to Ubuntu 26.04 and the browser tests could not install Chromium; `tests.yml` runs on `ubuntu-24.04` until Playwright supports the new image.

## The scanner not made cross-origin isolated (2026-10-24)

A picked photo took 4.4 s in the lab, the accurate model on one core: without cross-origin isolation (`Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy`) a browser gives a thread no shared memory, so ONNX Runtime runs each model on one core. Headers for `/scan-lab/**` and the accurate model on up to 4 cores were written and reverted before merging (owner): Safari (iPhone) has no `credentialless`, so it would gain nothing there, and the site's scanner is a frame inside the manager page, which would need the headers on the whole app (popups, third-party frames, cookies-only resources).

## The punch link hardened (2026-10-24, audit batch 1)

The `punch` function trusted the page more than it should: `savePunch` wrote the page's `ts`, `time` and `date` as sent (a worker could backdate a punch by setting the phone's clock back, and a phone in another time zone stored a wrong `time`), and it used `set()`, so the link could rewrite a punch of its own worker that a manager or an accepted hours fix had changed since (by sending its id from `myMonth`). It is now create-only and checks `ts` against the server's clock (backend.md → `savePunch`). `logError` was accepted with no token, so anyone could fill the `errors` collection; it now needs a working link. `savePushSubscription` (push subscriptions for reminders that were never built) was removed with its explicit rules for `pushSubscriptions` and `workerTokens` (both denied by default). The supplier's `loadPunchLog` read every punch of its workers and filtered the 13 months in Python; the query is now bounded by `ts`. A fired worker's link keeps working, by the owner's decision.

*Review (audit fixes punch-pay):* a punch sent more than 3 days after its time (`MAX_LATE`) was refused ("Punch time too old"), and the page then took it out of its queue and its history — a phone left offline over a long weekend lost the worker's OUT on both sides, the next tap was recorded as an OUT of last week's IN (an 80 h shift), and the refusal showed as a green toast followed by "Synced". It is now stored with the warning "sent N days after the punch time (check its month's approved hours)"; a refusal is a red toast, and "Synced N" counts only the punches the server stored. Keeping every late punch with no bound at all let a phone whose clock was set back (a reset date, a wrong year) write live punches into old, possibly signed months with only a warning, so a punch more than 30 days late (`MAX_KEEP`) is refused again.

*Hours fix of a night with no IN (audit fixes punch-pay):* accepting a 22:00–06:00 fix for a shift that had only its 06:00 OUT put the new IN on the evening before, so the shift moved to the day before and the reviewed row disappeared. A first fix moved the worker's real OUT 24 h later instead (IN on the reviewed day, OUT the next morning) — that rewrote a real punch, changed the night's weekday (Saturday rate) and month, and with back-to-back nights doubled the next night and lost the first one's hours (the swallow check compared single punches, strictly inside the window). It was reverted: the real OUT never moves, the IN goes on the evening before, and the approval entries follow the shift instead (the fixed entry under the day before's key and month, the reviewed day keeping its remaining shifts' line); the overlap check now includes its bounds and refuses a shift inside another one.

## Payroll at the bounds of time (2026-10-24, audit batch 3)

Four payroll faults found by the site audit, fixed together (owner's decisions kept: overtime stays per shift, daily client billing per shift as before):

- **A night across a period's bound was paid nowhere.** `salaryEntriesFor` and the salary export cut the punches at the period's bounds (`periodPunches`) before pairing them, so Oct 31 22:00 → Nov 1 06:00 was an open shift (0 h) in October and an OUT without IN in November; This Week (and the super-admin's weekly summary of the firms) did the same to every Saturday night that ran into Sunday. The worker's My Hours cut the month the same way. Now each worker's punches are paired over the whole loaded log and a shift is kept in the period of its opening punch (`periodShifts`; the punch page's `myMonthFigures` and `firmsPayableRows` alike). `tests/accounting` compares with the old tab's code, which had the fault: its generated months now leave out the shifts that cross a bound, and the new rule is checked by hand there.
- **A pair's length came from its `HH:MM` strings**, so the night the clocks go back (Sun 2026-10-25) a 22:00–06:00 shift counted 8 h instead of 9 (in March 1 h too many), and an OUT forgotten until a day later counted 1 h. `analyzeDayPunches` now takes it from the time stamps (`pairMins`), the strings only as a fallback. `tests/payroll` compares with a frozen snapshot of the old copies: a bucket across a clock change or over 24 h is now checked against its time stamps instead. *Review (audit fixes punch-pay):* that changed the pay of months already closed — the 27 such buckets of the generated past months, and every punch edited before `editedPunchTs`, whose stamp could sit a day off its pair (an OUT the next morning corrected to 17:00 counted 33 h instead of 9 h; `tests/accounting` went red on its `all` period). The stamps now count only for a pair that opened from 1 November 2026 (`PAIR_STAMPS_FROM`); before that date every pair gives the old numbers (an edited pair more than 24 h apart was first also kept on its strings after that date, but every edit that could leave a stamp a day off is before it, so that exception only hid a real forgotten OUT after an edited IN, and was removed), which `tests/payroll` (the past months, to the agora) and `tests/accounting` (a month with a clock change, a forgotten OUT and an old edit) check. A migration of the edited stamps was not done: what an old edit meant can't be told from the stored data, and the old numbers are what was paid.
- **The alerts sorted warnings by their English text** (`/still at work/`, `/open shift|>12h/`), so in Hebrew every worker on shift showed as a red alert and the amber ones as red. `analyzeDayPunches` now returns a code beside each warning, and `accAlerts` sorts by it.
- **Today counted a running shift twice** (an `analyzeDayPunches` that already counts today's open shift up to now, plus the same time added again: 8 h at noon for an IN at 08:00), and missed a night guard after midnight (only today's punches were read). It now reads the last 24 hours for who is on shift and today's hours.
- **Review fixes.** Reading the last 24 hours first let a forgotten IN from yesterday morning run on to now (about 24 h added to today's, and the worker on shift all morning), and a double-tapped IN counted twice; now only the worker's last shift runs up to now, and one opened before midnight only within 16 hours (`MAX_OPEN_H`). Lengths from time stamps also made the punch window's time edit risky: it moved `ts` to the new time on the punch's own day, so an OUT punched the next morning and corrected to 17:00 made a 33 h shift; `editedPunchTs` now picks the day before / after when that keeps the OUT after its IN and within 24 h (an IN before its OUT likewise), and the punch's `date` / `day` follow it.

With them, the salary CSV and the punch log CSV got a UTF-8 BOM (Excel showed Hebrew as mojibake) and a guard against cells that Excel would run as formulas (`csvText`).
