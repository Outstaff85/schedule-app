# History

Chronological, narrative record of *why* things ended up the way they are —
bug-fix rounds, reverted approaches, and the reasoning behind design choices
that changed more than once. **CLAUDE.md and the other `docs/*.md` files describe only the
current state** (what a function does now, current data shapes, current
architecture); when a change is genuinely just "current behavior," it goes
there, not here. This file is where the debugging trail and the abandoned
alternatives live, so CLAUDE.md doesn't have to carry them forever.

Read this when: you're about to touch scan-alignment code and want to know
what's already been tried and reverted, or you're debugging a scan-quality
regression and want the full history of a specific threshold/constant.

## AI document scan flow — alignment/crop-tightening history (2026-09-26 → 2026-09-30)

*Current state of this flow is described tersely in CLAUDE.md under
"AI document scan flow" — this section is the detailed history of how it
got there.*

`onScanFileSelected`/`onScanFilesSelected` → **manual corner-adjustment editor** (`renderScanQuadEditor`/`initScanQuad`/`attachQuadDrag`, drag 4 SVG handles) on the raw downscaled photo → `confirmScanQuad()` perspective-warps the quad flat via `warpQuadImage()` (homography math: `computeSquareToQuadHomography`/`applyHomography`/`bilinearSample`, output capped at 1568px long edge) → the cropped page is **queued**, not processed yet (`window.__pendingScanPages`, `renderPendingPagesPrompt()`) → once the user is done adding pages, `processAllPendingPages()` sends the whole queue through `autoPreAlignScan()` (cheap Haiku corner detection) + `preAlignScan()` (server contrast enhance + blur check) + `aiReadDoc`/verify/merge + `finalTightenPass()` tightening, once → `renderScanPagesPrompt()` → `openWorkerModalFromScan()`. (`refineWithAiAlign()` — a second tightening pass on `aiReadDoc`'s own `imageAlign` — was removed 2026-09-30; see its own removal note further down.)

- **Real-time progress bar during scan processing (added 2026-09-30, per user request):** `renderScanProgress(label,pct)` updates `#aiScanStage` with a `.progress-bar-real` (percentage-width bar) and a label at each major step, replacing the old static spinners that only changed once per full page. Previously a single-page scan's internal sub-steps (align, enhance, read, verify, tighten) were invisible mid-page — now the bar visibly advances at each step boundary, with percentages subdividing a page's 0-100% span across its real sequential work. The static Russian intro text was removed from `#aiScanOverlay` (it was visible even mid-processing, prompting the progress request). Verified via a headless-browser test: intercepting every `#aiScanStage` write during a single mocked page confirms 6 distinct percentages appear at the right steps, not just a jump from 0% to 100%.
- **Collect-then-batch (added 2026-09-26, per user request):** cropping a page no longer sends anything to the server by itself. `confirmScanQuad()`/`skipScanQuad()`, when `window.__scanEditPurpose==='collectPage'` (the normal case — set by `onScanFileSelected`), just push `{b64,mediaType}` onto `window.__pendingScanPages` and show `renderPendingPagesPrompt()` (thumbnail queue, "add page" / "process N pages", every thumbnail removable since nothing's been classified yet). Only `processAllPendingPages()` (that screen's "process" button) talks to the server — it mirrors `onScanFilesSelected`'s own classify/merge loop (first `israeli_id`/`passport` page found becomes primary, verified via `verifyDigitFields`/`verifyIdChecksum`; later pages merge missing core fields via `mergeIsraeliIdFields`/`CORE_FIELDS`/`missingCore` — now module-scope, shared by both loops — until none are missing; anything past that needs no further AI call), but runs `autoPreAlignScan()` then `preAlignScan()` per queued page first (see both functions' own comments — enhance+blur-check on the already-cropped image, same as the reordered single-page flow below). One blurry page aborts the loop and is dropped from the queue on its own (the rest of the already-cropped queue is preserved, not lost) — the user re-crops just that one page and presses "process" again. Resumable: `renderScanPagesPrompt()`'s own "add page" button also routes through `onScanFileSelected` → the same pending queue, so adding "just one more page" after already reviewing a first batch still batches, picking up the existing primary/otherPages instead of starting over.
- **`autoPreAlignScan()` revived (2026-09-26, per user request — "drop the classical-CV variants, hand alignment to a cheap AI model instead, a bit of token cost is fine"):** called from `processAllPendingPages()` on every queued page, right before `preAlignScan()`. It was dormant since 2026-09-21 (see its own comment for that history) on the theory that the manual corner editor made an AI-guessed starting point unnecessary — but this same day's real-photo diagnostic (see `preprocess_scan`'s own note below) showed manual crops staying rough in practice and the classical OpenCV detector failing on real backgrounds regardless of hardening. `aiDetectAlign` (Haiku, cheap — small prompt, no field extraction) reads the document's rotation+corners directly from the vision model, which generalizes to messy real photos far better than hand-tuned edge heuristics; `autoPreAlignScan()` then rotates (`alignScanImage`), pixel-refines the guess (`refineQuadCorners`, pure local pixel math, no extra AI call), and warps (`warpQuadImage`) — falling back to the untouched image on any missing/invalid response, same safety net as before. `preAlignScan()`'s own classical-CV pass still runs afterward, now on this already-better-aligned image, as a free additional (if largely redundant) safety net — left in place since it costs nothing and occasionally still helps on a cleaner background. Verified with a mocked `aiDetectAlign` response (classical CV deliberately mocked to fail, matching the real diagnostic) through the full real batch pipeline: a rough ~40%-of-frame rotated synthetic crop came out straightened and tightly cropped to just the card.
  - The temporary `pushScanDebug()`/`window.__scanDebugLog` diagnostic instrumentation (added 2026-09-26, used to chase the uncropped/tilted photo and black-sliver bugs) was **removed 2026-09-27** once the root cause was found and fixed (`finalTightenPass()` below) — no longer present in the code.
  - **`refineQuadCorners()` hardened for precision (2026-09-26, ongoing):** the residual tilt/black-sliver traced to two main causes, fixed in two stages:
    - **Stage 1 (2026-09-26)** — (1) each edge sample snapped to the nearest whole PIXEL step in its search window, and a real photo's own optics/JPEG blur mean the true edge often falls *between* pixels — a systematic sub-pixel bias per side adds up across the whole quad into a visibly crooked result even when every individual sample looks "close enough"; fixed with a parabolic subpixel interpolation around each sample's peak gradient, plus more samples per side (12→20) and a tighter margin (0.18→0.12, sampling closer to the true corners for more/better line-fit data). (2) the fixed gradient-magnitude floor (18) rejected every sample on a real worn/low-contrast/glare-affected card edge (measured peaks as low as ~13-17 in a degraded synthetic test), silently discarding the whole per-side refinement and leaving the AI's raw (imprecise) corner guess in place untouched — lowered to 12. An adaptive per-point threshold (relative to that same point's own local noise floor) was tried first and reverted: it let pure sensor/JPEG noise with no real edge at all snap to false "edges" (verified up to ~17px of spurious drift on a flat noise-only test image, vs 0px before), which the plain lower floor does not (verified still 0px drift on the same noise test — noise's own peak gradients topped out around 11 in testing, safely under the new 12 floor). Verified via headless-browser tests with known ground-truth corners: a clean high-contrast synthetic edge refines to ~0.02° of the true rotation angle (was already accurate before this change); a low-contrast/blurred/noisy synthetic edge — designed to fail under the old N=12/margin=0.18/threshold=18/no-subpixel settings — now also refines to ~0.02° (previously fell back to the raw, ~1°-off AI guess untouched); a pure-noise (no real edge) image still produces 0px drift, matching the pre-change safe-fallback behavior.
    - **Stage 2 (2026-09-27)** — real-device retest showed the ospח page now cropping/straightening correctly, but the front תעודת זהות (Israeli ID) page still coming out visibly tilted with a black sliver: its busier surface (holographic watermark pattern) most likely makes `aiDetectAlign`'s own initial corner guess less precise than on the plainer ospח side. Root-caused via synthetic tests with a deliberately large (up to ~110px on a 1000px-wide test image, ~11% of frame) initial-guess error on one or more corners: (1) `maxDrift` (the safety cap rejecting a computed corner that lands "too far" from the AI's own guess, on the theory that a big jump means a bad line fit rather than a real correction) at its old 0.12-of-frame value rejected a *individually verified-accurate* correction (<1px error) on some corners while accepting others, producing an inconsistent, visibly warped quad — measurably worse than either the fully-raw guess or the fully-corrected result; raised to 0.35. (2) at the same large initial error, the per-point search radius (`SEARCH`, ~2% of frame) was often too narrow to even reach the true edge from a badly-off sample point, so the affected side's line fit failed outright (returned null) rather than merely landing outside `maxDrift` — independent of the `maxDrift` fix above; widened to ~4% of frame. Both changes verified together via headless-browser tests: a sweep of initial-guess errors from 10px up to 110px on a 1000px-wide synthetic image now refines to within ~6px (was: correct up to ~70px, then a sudden jump to 76-126px error beyond that, i.e. no real correction) while a pure-noise (no-edge) image still produces exactly 0px of drift (unchanged, no new false-positive risk from the wider search radius).
    - **Stage 3 (2026-09-28)** — a real worker's ospח scan (worn card, printed header text near the top edge) still came out with a chunk of both top and bottom text missing from the final embedded photo. Root-caused with the actual real photo (not a synthetic test): fed a deliberately *accurate* starting quad into `refineQuadCorners()` directly and found it still pulled a corner ~40px (≈7.5% of frame) off — not from noise, but because the per-point search picked whichever offset had the SINGLE STRONGEST gradient anywhere in the ~38px search window, with no regard for how far that point was from the starting guess. On a real card, a bold printed line can easily out-contrast the card's own (often faint/worn) physical edge, so the search reliably preferred the wrong signal whenever both existed. Fixed: search outward from the starting position (`s=0`) and take the FIRST point that both exceeds the `>12` gradient floor AND is a local peak (≥ both neighbors) — a nearer, real edge no longer loses to a stronger but farther false one just for being fainter. The flat `>12` threshold itself is unchanged, only which qualifying point wins. Verified against the existing regression suite (`test-refinequad-noise.js`, `test-biggerjitter.js`) with no change in behavior (0px drift on pure noise; large deliberate 10-110px initial errors still refine to ~5-6px) — this fix only changes tie-breaking among *multiple* qualifying peaks, so single-peak cases are unaffected. On the same real photo, this fix alone did not eliminate a large corner correction — further investigation found the true edge there is a *genuinely tilted* line, not a false-positive at all (the guess used in that specific test simply wasn't axis-aligned with the real card's tilt in the photo). That pointed further upstream: `refineWithAiAlign()` (below) warped straight to `aiReadDoc`'s own `imageAlign.corners` with **no local pixel check at all** — unlike `autoPreAlignScan()`, which always runs its AI guess (`aiDetectAlign`) through `refineQuadCorners()` before trusting it. Fixed by closing that asymmetry — see `refineWithAiAlign()`'s own comment below. Between the two fixes, a second real card (the front תעודת זהות from the same report — missing its header row and a truncated ID number in the final PDF) was tested directly: `refineQuadCorners()` alone (old or new peak-selection, tested both) barely changed the result starting from an accurate guess, confirming THIS card's real failure was `refineWithAiAlign`'s missing self-check, not the peak-selection bug Stage 3 itself fixes — feeding it a deliberately bad guess (mimicking the reported symptom) and running it through the fixed `refineWithAiAlign()` recovered nearly all the previously-missing header/footer text. Root cause considered closed for both documented real cases as of this fix, pending any further real-world recurrence.
  - **`refineWithAiAlign()` local self-check (2026-09-28)** — runs `align.corners` (currently trusted as-is) through `refineQuadCorners()` — the same real-pixel-edge verification `autoPreAlignScan()` already applies to its own AI guess (`aiDetectAlign`) — before warping to it, instead of trusting a single AI vision call with zero local sanity check. Verified on a synthetic test: a deliberately bad guess (~35px off each side, matching the magnitude measured on a real photo) recovers to the true rectangle's edge (within ±6px) instead of keeping the bad crop verbatim. All three call sites (`runOcr()`'s single-page path, `processAllPendingPages()`'s primary-page and merge-page branches) pass the same image the AI's corners are fractional-relative-to, so no coordinate-space changes were needed at the call sites themselves.
  - **`refineWithAiAlign()` REMOVED (2026-09-30, per user request)** — after the `_scanSideEdge()` over-crop fix below, the user questioned whether this whole second geometric-tightening pass (re-warping on top of `aiReadDoc`'s own, independently-imprecise `imageAlign.corners`, arriving *after* `autoPreAlignScan()` already produced a locally-verified crop) was still worth the risk it carried. Tested against the real front-ID photo from the original bug report: fed the function a realistic imprecise second guess (the same magnitude documented in this function's own 2026-09-28 self-check test above, remapped into the coordinate space of the image `autoPreAlignScan()` already produced) and it cropped off the card's header row and part of the left-edge text that `autoPreAlignScan()`'s own crop had kept fully intact — confirming that trusting a second, independently-imprecise AI guess for a *final* crop is a real net risk, not merely redundant work, now that `finalTightenPass()`'s own peak-selection bug (below) is fixed and it's reliable enough as the sole remaining safety net. All three call sites (`runOcr()`, and `processAllPendingPages()`'s primary-page and merge-page branches) now use the image as-is (or, for the primary/merge pages, go straight to `finalTightenPass()`) instead. `quadAreaFrac()` (only ever used by this function's trust-floor check) was deleted alongside it as now-dead code. Left the historical entries above intact as an accurate record of why this was built and hardened in the first place — useful context if a future real-world regression makes this worth reviving in some form.
  - `_preAlignThenOcr()`/`runOcr()` are DORMANT as of this change — nothing in the live UI sets `__scanEditPurpose==='preOcr'` anymore (that's what those two functions gated on); left defined, working, in case an immediate no-batch fast path is wanted again later.
- **`preAlignScan()` runs after the manual crop, not before** (reordered 2026-09-26, per user request, for server economy) — it's called on `warpQuadImage()`'s already-cropped-to-just-the-document output (now from inside `processAllPendingPages()`'s loop), so its resize/enhance/blur-check all run over far fewer pixels than when they covered the whole original photo including background. Trade-off: the user crops on a photo without the contrast/sharpness boost yet, and a blurry photo is only caught *after* the user has positioned the rectangle (and, with the collect-then-batch change above, potentially after cropping several *other* pages too — only the offending one is dropped).
- The corner editor runs **before** OCR, not after — the user positions the rectangle themselves on the raw photo; no AI-guessed starting rectangle. `initScanQuad()` reads the displayed `<img>`'s `clientWidth/clientHeight` to build the coordinate space — this must happen after both image decoding and layout are complete. A single `requestAnimationFrame` (the old fix) assumes one frame suffices for the browser to decode a large data-URI photo on all hardware; on slower/mobile devices this wasn't guaranteed, and the bug recurred even with the rAF defer. `renderScanQuadEditor()` now uses `img.decode()` (resolves only when the image is fully decoded, regardless of frame count), followed by one more rAF for layout — it falls back to the rAF-only approach if decode() throws or isn't supported. **Critical:** on some mobile browsers, `decode()` can apparently never settle (neither resolve nor reject) for a large data: URI, which prevented `initScanQuad()`/`attachQuadDrag()` from ever running, leaving the crop rectangle stuck non-interactive. The call is now capped at 1.2s with `setTimeout()` — if decode hangs, the timeout fires anyway and lets the editor become usable (fallback to uncropped original if crop never ran). Reading `clientWidth` before both are complete reads `0`, which locks the crop rectangle at a degenerate point and makes `warpQuadImage()` throw — silently caught, falling back to the *uncropped* original photo. The 4 corner drag handles are radius=13 (26px diameter, shrunk from 20 across several requests on 2026-09-26/27: 20→18→15→13) drawn offset ~6.5pt inward from the true corner toward the quad's own centroid (`paintQuad()`, inset raised from 3.5pt on 2026-09-27 — still hard to grab a corner sitting right at the photo's edge) — purely a visual nudge; `window.__quadRect[key]` (the actual crop-math coordinate `attachQuadDrag()`'s pointermove writes to) is untouched, and pointerdown hit-testing still keys off the handle's `data-c` dataset attribute rather than its drawn position, so the offset can't desync the drag from the true corner. Pointerdown hits only the visible circle (no padding), so a larger radius makes dragging more reliable on small screens — this is the reason the radius was never dropped further despite repeated requests to shrink it, in favor of moving the handle inward instead.
- **Whole-edge drag (added 2026-09-27, per user request — "let me move the whole horizontal/vertical line, not just one corner at a time"):** 4 invisible `<line>` elements (`.quad-side-handle`, `stroke-width:40` — widened from 24 on 2026-09-30, per request, for an easier finger touch target; the visible quad outline itself stays `stroke-width:2`, unaffected, since it's drawn on a separate `<polygon>` — drawn *before* the corner circles in DOM order so a corner handle still wins the hit-test where they overlap) sit along each of the quad's true edges (positioned in `paintQuad()`, keyed off `SIDE_CORNERS` — `{top:['tl','tr'], right:['tr','br'], bottom:['br','bl'], left:['bl','tl']}`, shared with `attachQuadDrag()`). Dragging one translates BOTH of that edge's corners by the same raw pointer delta (captured at pointerdown, applied cumulatively as the pointer moves, each clamped independently into `[0,imgW]x[0,imgH]`) — a rigid parallel shift of that whole side while the other two corners (and the adjacent sides meeting them) stay fixed, the standard "drag an edge" gesture from a photo-crop tool. Verified via a headless-browser test: dragging the top edge's handle by a given pixel delta moves `tl`/`tr` by exactly that delta while `br`/`bl` stay untouched.
- `preprocess_scan` (the Python endpoint): geometric auto-crop (`_find_document_quad`/`_warp_quad`, OpenCV contour detection) is **re-enabled** (2026-09-26) — real scans were coming out with the manual crop's own rough background/skew untouched, because `refineWithAiAlign()`'s AI-based tightening (below) requires its guessed quad to cover ≥50% of the frame before trusting it, which a rough manual crop routinely fails, so nothing was actually getting tightened in practice. Safe to re-enable for a different reason than why it was originally disabled: it used to run **before** the manual corner editor, so it could lock onto one of two documents photographed together (e.g. a passport + its ספח insert) and silently discard the other; since the 2026-09-26 reorder this function only ever runs **after** the manual editor, so the input is already a single document — there's no second document left to lose. A confident match (passes `MIN_QUAD_AREA_FRAC`/`MAX_QUAD_AREA_FRAC`) tightens the crop; anything low-confidence (very low-contrast background, no plausible-sized contour at all) leaves the image untouched, same as before.

**Hardened for real phone photos (2026-09-26, same day):** the clean-synthetic-image version above worked in testing but a manager's actual rescan on a real device still came out uncropped — real photos carry glare, sensor/JPEG noise, uneven lighting, and worn/scuffed cards that a plain fixed-threshold Canny genuinely struggles with (this isn't a bug so much as a known limitation of simple contour detection on messy real input). `_find_document_quad()` now: (1) applies CLAHE (local contrast normalization) before edge detection, so a real glare/shadow-uneven background doesn't swamp the document's own edges; (2) denoises with `cv2.bilateralFilter` (smooths noise while preserving true edges, unlike a plain Gaussian blur, which softens both) — `sigmaColor=40` chosen by testing against a battery of degraded synthetic cases (glare, motion blur, sensor noise, a worn/scuffed card, low card/background contrast) and picking the value that passed the most of them; (3) uses `_auto_canny()` (median-intensity-based threshold, a standard technique) instead of fixed 50/150 — a real photo's overall exposure varies too much for one fixed pair of numbers; (4) falls back to the largest plausibly-sized contour's `minAreaRect` when no clean 4-point convex polygon is found (a rounded card corner or a bit of noise routinely turns one straight edge into 5-6 slightly-bent points, failing the old strict `approxPolyDP`-must-be-4-points check even though the contour itself is clearly the document). Re-verified against the same battery: 6 of 7 degraded cases now detect correctly (only an inherently ambiguous low-card/background-contrast case still safely declines, matching the "leave it untouched, don't risk a bad guess" design). Enhancement then runs on the (possibly now auto-tightened) image before the blur check. The blur threshold was calibrated on a pre-enhancement, full-frame photo; enhancement can inflate variance scores, and the input is now a cropped-to-document image rather than the full frame — either change alone could shift what the check actually measures, so if obviously blurry scans start passing, `BLUR_VARIANCE_THRESHOLD` may need adjustment.
- Multi-file / multi-page uploads (`onScanFilesSelected`, picking several files or a multi-page PDF at once): still its own separate path with **no manual crop step at all** — each page goes straight to `aiReadDoc` for classification (an already-filled Form 101 is dropped and always regenerated fresh; the first ID/passport page becomes primary; a ספח page's blank-filling fields — `dob/sex/address/city/houseNumber/maritalStatus` — merge into the primary record regardless of which physical card came first), landing in the same `renderScanPagesPrompt()` review screen the batch-crop path above also uses.
- Worker's own mobile number is a plain modal field (`#wPhone`), not scanned — printed on the PDF via a synthetic `worker_phone` field (no real AcroForm field there).
- Each page's own raw parsed data is kept in `window.__aiPageParsed` (parallel to the `renderScanPagesPrompt()` thumbnail strip). Removing a page (`removeExtraScanPage()`) doesn't just drop its thumbnail — it recomputes the primary record from scratch via `rebuildPrimaryFromPages()`/`mergeScanPage()`, so a bad/misread extra page's merged fields (address, city, marital status, an `idMismatch` flag, ...) don't silently survive its own removal.
  - **`processAllPendingPages()` unified with this same merge logic (2026-09-27)** — it used to build `foundParsed` with a hand-rolled `p`-direct-assignment (primary page) and a bare `mergeIsraeliIdFields()` call (merge page), a *different* algorithm than `rebuildPrimaryFromPages()`'s `initPrimaryFromFirstPage()`/`mergeScanPage()` — so removing a page via `removeExtraScanPage()` could recompute a different-looking primary record than how the batch loop originally built it. Now routes through the same two functions. Also a real fix on its own: `mergeIsraeliIdFields()` alone never backfills a missing `idNo` from a later page (`idNo` isn't in `ID_CORE_FIELDS`) — `mergeScanPage()` does. Verified via a headless-browser test: a primary page with a blank `idNo` correctly gets it backfilled from a later merge page.
- **`refineWithAiAlign()` tightening pass** (`aiReadDoc`'s `imageAlign`, tightened the user's own manual crop, never replaced it, fell back to the untouched image on any missing/implausible corners) — added to `processAllPendingPages()` (2026-09-26, per user request: "manual crop, then auto-fit right when the batch is sent for processing") for the primary page and for any page whose `aiReadDoc` response actually ran (the merge-page branch); it was free — piggybacked on the `imageAlign` field of an `aiReadDoc` call the batch loop was already making for field extraction, no extra AI cost. **Removed 2026-09-30** — see its own removal note above (under `refineQuadCorners()`'s history) for why: it added real over-crop risk without the resolution/accuracy benefit its "free tightening" framing implied.
  - **`finalTightenPass()` added 2026-09-27** — a real-device test's debug log showed `aiDetectAlign` finding a reasonable quad and `refineWithAiAlign` applying its own tightening, yet the final embedded photo still had a thin black background sliver on the left/right edges. Root cause: that run's `refineWithAiAlign` corners were full-width (`x:0` to `x:1`, only trimming top/bottom) — whatever thin sliver `autoPreAlignScan`'s own corner detection left on the *other* axis was never re-examined by anything downstream. Rather than chase why one specific run's AI corners came out full-width, this adds an unconditional final safety net after every page's alignment chain (primary page, merge page, and the "no aiReadDoc call needed" page that skips `refineWithAiAlign` entirely) that treats the image as already axis-aligned (safe by this late stage, after the full perspective warp) and scans each of the 4 sides **independently** for a real edge just inside a small starting margin, trimming only the sides where one is confidently found (`_scanSideEdge()` — 16 samples per side, median offset, same gradient/subpixel technique as `refineQuadCorners`, but per-side rather than per-corner). This independence is the actual fix for the reported bug: `refineQuadCorners`' own line-**intersection** approach requires both sides meeting at a corner to have signal before it can move that corner at all, so a photo already perfectly cropped top/bottom (no edge signal there — correctly left alone) could never have its left/right sides corrected even when those had a clear, confidently-detected edge of their own. Verified via headless-browser tests: a sliver on both left/right sides is trimmed correctly; a sliver on only one side is trimmed independently of the others; a low-contrast sliver is still found; an already-tight image and a pure-noise (no-edge) image both produce a safe no-op with zero re-encode cost.
    - **`_scanSideEdge()` over-crop fix (2026-09-30)** — reported on a real front תעודת זהות scan: the final embedded photo was cropped noticeably *into* the card, clipping the top header text. Root cause: `_scanSideEdge()`'s peak selection was still the OLD "pick the single strongest gradient anywhere in the search window" approach — the exact bug `refineQuadCorners()` fixed on 2026-09-28 (Stage 3, above), which was never ported to this sibling function even though `finalTightenPass()` runs unconditionally as the very last step of the whole alignment chain, i.e. any residual over-crop from this bug is the last thing to touch the image before it's embedded. A bold printed header/footer line can out-contrast the card's own faint physical edge, so the global-max search reliably jumped past the true (nearer, fainter) edge onto that text. Fixed identically to Stage 3: search outward from the starting position and take the first local peak that clears the existing `>12` flat floor and `>2×median` relative check, instead of whichever point anywhere in the window scores highest. Verified via a synthetic repro (thin low-contrast real edge near the margin, bold false text edge further inward): old code cropped to 741px width (jumped onto the text), fixed code correctly stops at 789px (the real edge, expected ~788px). Existing `finalTightenPass`/`refineQuadCorners` regression tests (`test-final-tighten.js`, `test-final-tighten2.js`, `test-refinequad-noise.js`, `test-biggerjitter.js`, `test-skip-identity.js`, `test-real-finaltighten.js`) all produce identical output to before this fix — this only changes which point wins when multiple peaks qualify, same as Stage 3.
  - **`_isNearIdentityQuad()` optimization (2026-09-27)** — a single scanned photo can pass through several sequential `warpQuadImage()` calls in this chain (`autoPreAlignScan`, `finalTightenPass`) plus the server's own `_shrink_for_embed()` at PDF-embed time — each one a JPEG decode+re-encode, and thus generation loss, even when that particular pass found nothing worth cropping/rotating. `autoPreAlignScan()` checks the quad it's about to warp with against `_isNearIdentityQuad()` (all 4 corners within ~1% of the untouched full frame) and skips the warp entirely when it would be a lossy no-op copy (`refineWithAiAlign()` had its own equivalent check too, before its removal on 2026-09-30). `finalTightenPass()` already had its own equivalent skip (comparing against its own starting margin). Verified via headless-browser tests: an identity quad is correctly detected and skipped (same bytes back), while a real crop still goes through unchanged.
  - **Server-side geometric auto-crop (`_find_document_quad`/`_warp_quad` in `functions/main.py`) made DORMANT again (2026-09-27)** — was re-enabled 2026-09-26 back when the client-side tightening wasn't reliable enough on a rough manual crop; now that `autoPreAlignScan`/`refineQuadCorners`/`finalTightenPass` (above) run client-side *before* this endpoint ever sees the image, running a classical-CV quad detector on an already near-final crop is both a wasted CLAHE/bilateral/Canny/contour pass on every scan AND a regression risk — with little background left to find a document/background boundary against, it can lock onto a strong internal element (the photo, the chip icon, a text block) instead and crop INTO the document. Left defined, unused, matching the same dormant-but-kept pattern as `_preAlignThenOcr()`/`runOcr()` on the client — revive if a future client-side regression makes it worth it again.
  - **Trust floor lowered 50% → 8% of frame (2026-09-26, same day as the hardening above)** — real-world testing (a real photo extracted from an actual generated PDF) showed the classical OpenCV detector (`_find_document_quad`, above) failing to close a clean contour around the card even after CLAHE/bilateral/auto-Canny hardening: the largest edge-based contour found was only ~7% of frame, and a brightness-threshold (Otsu) alternative also tried during debugging leaked into the background along one edge, both symptomatic of a real (not pure-black, not perfectly lit) background rather than a bug. `quadAreaFrac(align.corners)<0.5`'s original 50% floor assumed the manual crop already left mostly-document in frame (a pure tightening pass) — real usage crops far more loosely (~20-35% document-in-frame observed), so that floor rejected the AI's own correct card-boundary guess every single time, which is the opposite of what it was meant to help with. Lowered to 0.08 — still guards against the one real failure mode (the AI locking onto a small internal sub-element, e.g. just the portrait photo, which sits far under 8% of even a rough crop) without penalizing an honestly loose manual crop. Not independently re-verified end to end (would need a real `aiReadDoc` call against a real photo, which costs real Anthropic API usage) — reasoned from the same real photo's OpenCV-detector failure above, but if document photos are still coming out uncropped after this ships, that's the next number to look at, alongside whether `aiReadDoc`'s own `imageAlign` guess is landing anywhere near the true card boundary at all for this kind of photo.

## Data resilience — unsaved changes + retries (2026-10-01)

- **Lost data on failed save (2026-10-01):** a manager added a new worker to the roster and clicked save, but the network hiccupped mid-request. The client showed "GS save failed — saved locally," which seemed safe, but the next time the app loaded it showed the old cached roster from before the add — the worker typed in was gone. Root cause: `gsSave()` failed and returned `false`, but `loadData()` (called later, e.g. on page reload or tab switch) unconditionally replaced ALL local data with the server's version via `applyData()` without checking if the local `workers` array had unsaved changes waiting. Unlike a conflict scenario (where the server won, intentionally), a network failure meant the server never even got the message — throwing away local changes was the bug. **Fix:** track unsaved changes with `UNSAVED_KEY()` (a `localStorage` timestamp set when a save starts, cleared when it succeeds). On `loadData()`, call the new `applyServerLoad()` instead of `applyData()` directly — it checks `hasUnsavedLocal()` and if true, immediately re-saves via `autoSave()` instead of replacing with the older server copy. The unsaved flag is also cleared when a conflict is detected and resolved (server wins), so that scenario still works correctly. Verified via a headless-browser test: a worker added + save failed → cache untouched with unsaved flag set; next `loadData()` preserves the added worker and re-saves it; later `gsSave()` conflict detection clears the unsaved flag so the next load DOES use the server version as intended.
- **Vague network errors (2026-10-01):** when `gsLoad()` failed, the app said "Could not load from GS" — useful for ultra-fast debugging, but a manager calling for tech support couldn't explain what went wrong. The server might have been down, the network might have been offline, or the response might have been non-JSON garbage. Server-side `logError` telemetry showed only that `gsLoad` was called; it never included the actual error. **Fix:** `gsLoad()` now (1) retries automatically twice (delays: 1s, 3s), (2) extracts a meaningful reason on each attempt (HTTP status, JSON parse error, missing expected fields, error text from response), (3) stores the final reason in `gsLoad.lastError`, (4) reports via `reportError()` so it appears in the super-admin's Errors sheet. The client-side toast also includes the first 80 chars of the reason. A phone picking a file from camera/gallery can cause the browser to drop and reload the tab, and the very first request after coming back often fails transiently — the retry logic catches this case. Verified via headless-browser tests with mocked failures (network error, HTTP 500, non-JSON response, missing workers field): reasons extracted correctly, retries fire with the right delays, and `reportError()` is called.
- **Page reload during upload (2026-10-01):** a deploy happened while a manager's document was uploading to Google Drive. The service worker updated, triggered a reload, and the upload got cut off mid-stream. The document file landed partially-written in Drive, and later PDF-generation or re-scanning against it broke. **Fix:** track active XHR uploads with `__uploadsInFlight` counter (incremented at `xhrPostJSON()` start, decremented on `loadend` event — fires on success or error, always). When the service worker's `controllerchange` event (indicating a new SW version took over) triggers a reload, delay it via `reloadWhenIdle()` until `__uploadsInFlight===0`. Verified via a headless-browser test: `__uploadsInFlight` increments/decrements correctly with overlapping uploads, and a simulated `controllerchange` event delays the reload until the counter hits zero.
- **Caught failure reporting (2026-10-01):** the app had error telemetry for uncaught exceptions (`window.onerror`, `unhandledrejection`) — those reached `reportError()` and the Errors sheet. But most application failures were *caught* by the app itself: a form validation error showing a red line, a toast saying "save failed," a `console.error()` in some handler — none of those reached the Errors sheet. A super-admin reviewing the Errors pane thought the app was stable, but users were hitting silent failures constantly. **Fix:** send caught failures too — wrap `console.error()` and `console.warn()` to capture and report, watch error-line DOM elements with MutationObserver, and scan toasts for error keywords via regex. The reporting cap was raised from 20 to 40 messages per session (to accommodate more error sources without hitting the hard limit, same 1-minute deduplication rule). Verified via headless-browser test: a `console.error()` call, a toast matching the error regex, and a form field's text mutation all trigger `reportError()` with the right source tags.

## Worker-document upload proxy — Content-Type header bug (2026-09-30)

**`gs_upload_proxy` function added 2026-10-02** — CORS-friendly relay between browser XHR (with real `xhr.upload.onprogress` listener) and Apps Script `saveWorkerDoc`/`saveWorkerAssets`. A single function instead of two because it's a generic relay; validation happens in Apps Script's own `doPost()`.

**Bug fix (2026-09-30, discovered during testing):** users reported "mid-upload logout" errors with "session expired" message even on fresh, seconds-old sessions — initially suspected a TTL/session-timeout issue. Root cause found through the Errors sheet's `authFailure` diagnostic records (`action=saveWorkerDoc, outcome=retrying`): the client's `xhrPostJSON()` deliberately sends no explicit `Content-Type` header (a historical holdover from when it posted straight to Apps Script, where the header doesn't matter). The browser defaults to `text/plain`. **Flask/Werkzeug's `get_json(silent=True)` without `force=True` refuses to parse a body whose Content-Type isn't `application/json`/`*+json` and returns `None`** — so `payload` was silently `{}` on every call, with no `action` or `token` fields. `gs_upload_proxy` then forwarded an empty POST body to Apps Script, whose `requireAuth({})` correctly (if misleadingly) threw "session expired" because `body.token === undefined`. The browser's retry logic made it look like a transient session issue rather than a consistent header problem. **Fix:** use `get_json(silent=True, force=True)` — parses the JSON regardless of Content-Type header. The bytes are always valid JSON (the client always sends `JSON.stringify(bodyObj)`), so trusting the header is the only change; nothing about validation or security changes. A future port of this function (e.g., to another runtime) must account for the `xhrPostJSON()` design choice not to send an explicit header.

### Backend changes with their reasons

**Worker photos (2026-10-01):** a worker's `avatarB64` (~10k chars) no longer lives in the workers JSON cell, which is one Sheets cell per firm (50,000-char limit) — about 4–5 workers with photos used to make every save fail as `tooLarge`. `saveSchedule()` strips photos out with `_splitAvatars()` before the size check and writes them to `Avatars_<tenantId>` via `_syncAvatars()` (rewritten only when the set of photos changed; a photo over `AVATAR_MAX_CHARS`=49000 is dropped). `loadSchedule()` merges them back with `_mergeAvatars()` for logged-in callers only — a worker's punch link (no `auth`) gets no photos — so the client sees the same worker objects as before and needed no change. A row saved before this still has inline photos; they load as-is and move on that firm's next save. `deleteTenant()` deletes the firm's `Avatars_` sheet. The daily `Backups` snapshot copies the workers JSON, so it no longer includes photos. The supplier-portal worker actions write through `_writeScheduleRow()` without touching photos.

**PunchLog per-tenant split (2026-10-02):** `loadPunchLog()` used to read the ENTIRE shared `PunchLog` sheet on every call — every firm's rows interleaved chronologically with no per-tenant split — filtering to the caller's own tenant only *after* reading, so one firm's growing history slowed down every other firm's requests too (flagged as a known scaling risk in this file's own earlier notes). Fixed by splitting into one sheet per tenant: `_punchSheetName(tenantId)` → `'PunchLog_' + tenantId` (tenantId is always a `Utilities.getUuid()` value, never user-controlled text, so it's already a safe sheet name — no sanitization needed). `savePunch`/`loadPunchLog`/`updatePunch`/`deletePunch`/`_findPunchRow` all now open only the caller's own sheet — a wrong-tenant punch ID simply isn't found (the sheet itself is already scoped), rather than being found-then-rejected by a `TenantId`-column check as before. `deleteTenant()`'s cleanup now deletes the tenant's own `PunchLog_<tenantId>`/`PunchLogArchive_<tenantId>` sheets outright instead of scanning/deleting matching rows one at a time (also falls back to the old row-scan against the legacy shared sheet, for a tenant that predates migration). `migratePunchLogToPerTenantSheets()` — ONE-TIME, run manually from the Apps Script editor — splits the legacy shared sheet's rows by `TenantId` into the new per-tenant sheets; never clears/deletes the legacy sheet (left in place as a safety net); safe to re-run, skips any tenant whose new sheet already has rows rather than duplicating. **Archiving:** `archiveOldPunches(tenantId, cutoffDate)` moves punches older than the cutoff (default ~12 months, computed in `archiveOldPunchesAllTenants()`) out of the live `PunchLog_<tenantId>` sheet into `PunchLogArchive_<tenantId>`, keeping the live sheet's size — and therefore `loadPunchLog()`'s read cost — bounded for a long-running firm regardless of total history; salary/accounting queries almost never look back further than the current/previous month. `archiveOldPunchesAllTenants()` iterates every `PunchLog_*` sheet in the spreadsheet (skips `PunchLogArchive_*` and the legacy shared sheet by name-prefix check) and is wired to a weekly trigger via `setupPunchArchiveTrigger()` (run once manually, same pattern as `setupDailyBackup()`). Verified via a Node `vm`-sandboxed test running the real `apps-script/Kod.js` source against a mocked multi-sheet `SpreadsheetApp`: per-tenant read/write isolation (one tenant's punches never appear in another's `loadPunchLog()`, and `updatePunch`/`deletePunch` can't touch another tenant's row by ID), correct migration of a legacy 2-tenant shared sheet with the legacy sheet left untouched, re-running the migration doesn't duplicate rows, and `archiveOldPunches()` correctly separates old rows from recent ones without losing any.

### Troubleshooting stories (fixed)

#### Worker document (Form 101 PDF/scan) upload fails: "network unavailable" or a session/auth error, worker record still created (fixed 2026-10-01)

**Symptom:** creating or rescanning a worker succeeded (the worker record itself saved fine, autoSave ran), but the Form-101 PDF and scan/signature sidecar never made it to Drive — the blocking upload spinner ended in a "network unavailable"-style error, or an auth/session error telling the manager to log in again, even right after a fresh login.

**Root cause:** `xhrPostJSON()` (added 2026-09-30 for real upload-byte progress — see its own comment) was the only GS_URL caller in the file that explicitly set `Content-Type: application/json` on the request. Every other `fetch(GS_URL, {method:'POST', body:...})` call deliberately omits any explicit Content-Type so the browser defaults to `text/plain` and the request stays a CORS "simple request" (no preflight). Apps Script Web Apps only implement `doGet()`/`doPost()` — there's no `doOptions()` — so a request that DOES trigger a preflight gets its OPTIONS silently blocked by the browser before the real POST is ever sent, surfacing to the caller as a bare "network error" with nothing in the Apps Script `Errors` sheet (the server never saw the request at all). Since `saveWorkerDoc`/`saveWorkerAssets` are the only two calls routed through `xhrPostJSON()`, this broke exactly (and only) the document-upload path while every other GS_URL call kept working normally — the reported symptom.

Separately, `xhrPostJSON()` used raw `XMLHttpRequest`, which never goes through the `window.fetch` wrapper below that detects `SESSION_EXPIRED_ERROR` and retries/cleanly logs out — so on the rarer occasion the session token really was invalid, these two calls surfaced the raw `SESSION_EXPIRED_ERROR` text as a failed-upload error instead of the same retry-then-clean-redirect-to-login flow every other call gets, which is what produced the "auth error, need to log in" variant of the symptom.

**Fix (part 1):** removed the explicit `Content-Type` header from `xhrPostJSON()` (now matches every other GS_URL call), and added the same `SESSION_RETRY_DELAYS_MS`-based retry + `reportAuthFailureXhr()` telemetry + clean session-clear-and-reload flow that `checkExpired()` gives plain `fetch()` calls. Verified via a headless-browser test: `xhrPostJSON()` sends no `Content-Type` header, and a mocked `SESSION_EXPIRED_ERROR` response triggers exactly the expected 2 retries before clearing the session (matching `SESSION_RETRY_DELAYS_MS.length+1` total attempts) rather than surfacing immediately as a raw error.

**Recurred after part 1 (fixed 2026-10-01, part 2):** the "network error" kept happening even with the header removed. Real root cause, missed the first time: per the Fetch/XHR spec, merely **attaching any listener to `xhr.upload`** (e.g. `xhr.upload.onprogress`, which `xhrPostJSON()` did whenever a caller passed an `onProgress` callback) unconditionally forces a cross-origin request into CORS-preflight mode — an entirely separate trigger from request headers, spec'd as the "upload listener flag." Apps Script still has no `doOptions()` to answer that preflight, so it fails exactly the same way, regardless of Content-Type. This means **real byte-level upload progress via `xhr.upload.onprogress` is fundamentally impossible against a bare Apps Script Web App** — no header combination avoids it once an upload listener is attached. `xhrPostJSON()` temporarily dropped the `onProgress` parameter entirely; `saveWorkerDoc`/`saveWorkerAssets`'s progress bar in `aiFillForm101()` used a fake ticker (creeps 20%→85% on a timer while the request is in flight, jumps to 100% on completion) instead of real bytes.

**Real progress restored (2026-10-02) via a Cloud Function proxy:** since Apps Script itself can never answer a CORS preflight, the fix was to stop asking it to — `functions/main.py` gained `gs_upload_proxy()` (same `CorsOptions(cors_origins="*", cors_methods=["post"])` pattern already used by `fill_form_101`/`preprocess_scan`, which DO answer preflight correctly), and `saveWorkerDoc`/`saveWorkerAssets` now XHR-POST to this Cloud Function (`GS_UPLOAD_PROXY_URL`) instead of `GS_URL` directly. The browser can freely attach `xhr.upload.onprogress` against the Cloud Function (its preflight gets answered), and the Cloud Function itself does a plain server-to-server `requests.post()` to Apps Script — no browser involved on that leg, so no CORS applies at all. `xhrPostJSON()` regained its `onProgress` parameter, but only attaches the upload listener when one is actually passed — every other GS_URL caller (which never passes `onProgress`) still never touches `xhr.upload`, so nothing else is newly exposed to the preflight trigger. Verified via headless-browser tests: real progress ticks flow through for `GS_UPLOAD_PROXY_URL` calls with `onProgress` passed; a call with no `onProgress` never touches `xhr.upload` even under a mock XHR that throws on access; the full `aiFillForm101()` upload path targets `GS_UPLOAD_PROXY_URL` for both `saveWorkerDoc`/`saveWorkerAssets`.

#### Session-expiry false logouts — ROOT CAUSE FOUND AND FIXED (2026-10-01)

The `Errors` sheet showed `authFailure: action=logError, attempt=2, outcome=logged-out`. `reportError()` (the client's `window.onerror`/`unhandledrejection` telemetry) sent `logError` with **no session token**, `doPost()` required auth for it and answered "session expired", and the `window.fetch` wrapper treated that like a real expiry: two retries, still without a token, then logout. So **any client-side JS error or unhandled promise rejection logged the user out**, and the error itself was never recorded. That fits every "kicked to login mid-scan" report (a scan is where transient errors/rejections are most likely), including the OCR-burst case below that had stayed open. Fixed three ways: `logError` is accepted with just `API_SECRET` server-side, `reportError()` sends `secret` + token, and the fetch wrapper skips logout handling for `logError`/`authFailure`/`login`. Verified with a headless test where the server still answered "session expired" to `logError`: the user stayed logged in. Also checked in a Node vm against the real `Kod.js`: `logError` with the secret and no token is recorded, and without the secret it is rejected. The sections below are the earlier investigation, kept for history.

#### Session-expiry false logouts during document scan (reported 2026-09-27; the `saveWorkerDoc`/`saveWorkerAssets` upload case root-caused and fixed 2026-09-30 — see below; the earlier mid-scan/OCR-call case remains open)

**Symptom:** a manager gets kicked to the login screen ("as if the session dropped") specifically while uploading a scan — reported to happen right after a *fresh* login (not near the real 6h token TTL) and right after selecting/uploading the photo (before OCR review, i.e. the very first `aiReadDoc` round-trip of the scan — most consistent with the multi-file/PDF path, `onScanFilesSelected()`, which calls `aiReadDoc` immediately per page with no manual-crop step in between).

**What was ruled out:** real 6h session expiry (happens on a fresh login too); a string mismatch between the client's `SESSION_EXPIRED_ERROR` and the backend's literal error text (byte-compared, identical); `SESSION_SECRET` rotation (would break every request, not just scan ones); request/JSON-parse corruption from a large base64 image (would surface as a generic parse error, not the literal "session expired" text the user actually sees).

**Root cause not yet confirmed** — a real production recurrence with server-side telemetry is needed. Two things ship in the meantime:
- **Widened retry** (`schedule-manager.html`'s `fetch` wrapper, was: retry once immediately, added 2026-09-21): now retries up to twice more (3 attempts total) before giving up, with a short delay before the last retry (`SESSION_RETRY_DELAYS_MS = [0, 500]`) — a single immediate retry wasn't enough to clear whatever transient hiccup this is, and a scan's burst of parallel/sequential `aiDetectAlign`/`aiReadDoc`/`aiVerifyField` calls is exactly the worst case for a spurious mid-flow logout to lose real user progress.
- **`authFailure` diagnostic** (new POST action, unauthenticated by design — see Backend section) — every time a GS_URL call gets rejected as "session expired," the client fire-and-forget-reports the failing action name, which retry attempt it was, and the outcome (`retrying` vs `logged-out`) to the `Errors` sheet. **Next real recurrence: check the `Errors` sheet for `source=authFailure` rows** — the `failedAction` there is the actual trigger (confirm it's `aiReadDoc`/`aiDetectAlign`/etc. as suspected, not something unrelated), and whether it recovers on retry (`outcome=retrying` followed by a normal request) vs. genuinely never recovers (three `retrying`/`logged-out` rows in a row) is the key fact still missing to actually root-cause this.
- **Richer `authFailure` telemetry + fresh-token retry (2026-10-01):** the client now also sends the token it used (`sentToken`), `bodyKB`, `hasSession` and `viaProxy` (XHR/proxy path); the server's `_tokenRejectReason()` logs *why* the token was rejected (`missing` / `malformed` / `bad-signature` / `expired Nmin ago` / `valid-now`) and never logs the token itself. Retries after a session-expired response now rebuild the request with the **currently stored** token (`withCurrentToken()` in the fetch wrapper, same in `xhrPostJSON()`), not the one the original request was built with. On the next recurrence, the `Errors` sheet row's `reason=` tells which case it is: `missing` means the token never reached Apps Script (a proxy/body problem), `valid-now` means a transient server-side rejection.
- **`aiVerifyFields` batching (2026-09-28)** — see "Optimizations (2026-09-28)" above: `verifyDigitFields()` no longer fires 2-3 concurrent `aiVerifyField` calls per page, cutting one real source of concurrent Apps Script executions during a scan burst. If Apps Script's per-account concurrent-execution quota was ever a contributor here, this alone may reduce (not necessarily eliminate) how often the issue shows up — still worth checking `authFailure` rows on any future recurrence rather than assuming this fixed it.

**Sliding session expiration (added 2026-09-30) — defensive improvement, turned out NOT to be what was wrong:** first shipped on the theory that the 6h TTL (`SESSION_TTL_MS`) is a hard wall counted from **login time** and never extended by activity. That theory didn't hold up — a full scan→review→upload session takes on the order of 2-3 minutes in practice, nowhere near 6 hours, so an unextended TTL couldn't be the actual cause. Kept anyway (still a reasonable thing to have — a session genuinely near its 6h wall no longer drops mid-task for unrelated reasons), but superseded by the confirmed root cause below as the explanation for this specific report. `requireAuth()` (`apps-script/Kod.js`) reissues a fresh token on every authenticated request, attached to the response as `refreshedToken`/`refreshedExpiresAt` via `_withRefreshedToken()`; client-side `applyRefreshedToken(json)` (`schedule-manager.html`) picks it up in both the `window.fetch` wrapper and `xhrPostJSON()`'s `onload`; `supplier-portal.html` got the same pickup via its own small `window.fetch` wrapper.

**Actual root cause, confirmed and fixed (2026-09-30):** the `Errors` sheet's `authFailure` diagnostic (finally checked after a real recurrence) showed `action=saveWorkerDoc, outcome=retrying` — i.e. the very FIRST attempt of the upload call was already being rejected as "session expired," which a stateless HMAC token check has no legitimate reason to do seconds after a fresh, successful scan. The real bug: `xhrPostJSON()` (used only for `saveWorkerDoc`/`saveWorkerAssets`, which since 2026-10-02 post to `GS_UPLOAD_PROXY_URL`, a Flask-based Cloud Function, not Apps Script directly) deliberately sends no explicit `Content-Type` header — a rule that made sense when it posted straight to Apps Script (which parses `e.postData.contents` as JSON regardless of Content-Type) but was never revisited after the target changed to a Flask app. The browser then defaults to `Content-Type: text/plain`, and Flask/Werkzeug's `request.get_json(silent=True)` **without `force=True` refuses to parse a body whose Content-Type isn't `application/json`, silently returning `None`** — so `gs_upload_proxy()`'s `payload = req.get_json(silent=True) or {}` evaluated to `{}` on every single call: no `action`, no `token`. That empty object is what actually got forwarded to Apps Script (`requests.post(GS_URL, json=payload)`), whose `doPost()` then called `requireAuth({})` — `body.token` is `undefined`, so it threw "session expired," exactly matching the reported symptom, on an exactly-valid, seconds-old token that simply never arrived. Fixed in two places: `functions/main.py`'s `gs_upload_proxy()` (and, as defense in depth, `fill_form_101`/`preprocess_scan` too) now calls `req.get_json(silent=True, force=True)`, parsing the body regardless of Content-Type; `xhrPostJSON()` also restores an explicit `Content-Type: application/json` header, but only when posting to `GS_UPLOAD_PROXY_URL` specifically (never to bare `GS_URL`, where it would reintroduce the CORS-preflight problem documented in the entry above this one — Apps Script still has no `doOptions()`). Verified with a Flask/Werkzeug test: a `text/plain` body reproduces the empty-`{}`-parse bug under `get_json(silent=True)` without `force`, and parses correctly with `force=True`; an `application/json` body (what `fill_form_101`'s client call already sends) behaves identically either way, confirming the fix is safe for every existing caller. **This closes the upload-specific case.** The original 2026-09-27 report (a kickout during the OCR burst itself — `aiReadDoc`/`aiDetectAlign`/`aiVerifyField`, which all go straight to `GS_URL`, never through this proxy) is a different code path and remains unconfirmed — if it recurs, check `authFailure` rows for a `failedAction` other than `saveWorkerDoc`/`saveWorkerAssets` before assuming this same fix covers it.

#### New worker appears, then disappears from the list; its Form 101 stays in Drive (fixed 2026-10-01)

Cause: the 2026-10-01 login-speed change grew `SCHEDULE_HEADERS` to 8 columns (`workerCount`/`clientCount`), but `saveSchedule()` still wrote its own 6-value row into an 8-column range, so **every save of an existing firm threw** ("The data has 6 but the range has 8") and nothing reached the sheet. #### "Could not load from GS" after picking a file on a phone (fixed 2026-10-01)

On a phone, opening the camera/gallery to pick a file can make the browser drop and reload the tab; the first `loadSchedule` right after coming back often failed, and `gsLoad()` turned any failure (network, Apps Script HTML error page, quota) into an immediate "Could not load from GS" toast. ## Scan crop cut printed text (fixed 2026-10-04)

A real Israeli ID front came out with its header row and the vertical number on the left cut off. Both edge searches (`refineQuadCorners`, and `finalTightenPass`'s former `_scanSideEdge`) took the nearest strong brightness jump as the card's edge, and a bold printed line a few pixels inside the edge is exactly that. `finalTightenPass` started 3 % inside the frame, so on an already tight page it always found the text first and cut it. A synthetic benchmark (a card with text by its edges on a textured table; the AI's guess exact, 2–4 % too tight or too loose, or jittered; three angles) reproduced it: 40 of 75 crops lost a corner for a blue ID card and 65 of 75 for white paper. The fix is the card edge test (`_edgeTools`, docs/scan.md): it needs card colour inside the jump and something else outside. It also adds a robust line fit and has `finalTightenPass` search from the border inward. Result: 0 of 75 cut for both, and an already tight page is no longer touched. Paper on an almost-white table can't be told from the table, so its corners stay the AI's guess. The `detectAlign` prompt now asks the model to place an unsure edge slightly outside the document.

A follow-up the same day: a scanned ID still kept a tilted black band (about 10 % of the height) under the card. The final pass only searched 6 % in from the frame and only cut straight across. `finalTightenPass` is now `refineQuadCorners` from the full frame (15 % inward, fitted lines, so a tilted band is cut along its tilt). The edge test now needs the outside stretch to be background without a card-coloured gap, because a bold header line plus the table beyond it had passed the old 80 % rule. A fitted line is kept only if the edge test passes along it. Benchmark, now 111 crops plus 9 tilted-band crops: 0 cut for a blue ID or for paper on dark or grey tables, every band removed, 2 of 111 cut for paper on an almost-white table (5 before).

The same day, the report "the preview is straight but the PDF photo is crooked" was traced to the review-screen thumbnails, not the PDF. They were 64 px squares with `object-fit:cover`, which hid the band at the bottom; the PDF shows the same image, whole. The thumbnails now use `contain`. The new `finalTightenPass`, run on a screenshot of that real scan, removed the band. The test device was likely still running the old `scan-pipeline.js`: it is loaded once per page, and Hosting served `.js` with its default `max-age=3600`. All `.js` files are now `no-cache`.


## Scan misread Hebrew names (fixed 2026-10-04)

A real ID came out with one surname letter wrong: ד read as ר, the classic look-alike pair. Two causes. Since the "every boxed field is re-read zoomed" change earlier the same day, the zoomed re-read of a name always replaced the full read, so a crop that was off or blurred won on its own. And the crop was blurred: the page is shrunk to 1800 px before anything else, a name line is ~25-30 px tall, and the crop was only that, stretched — the corner that tells ד from ר is 1-2 px.

The fix (docs/scan.md → Sharper field crops, Merging pages): field crops are cut from the photo as taken, through the page's own geometry steps; a zoomed text read no longer replaces the first read; and the holder's name is picked from every reading — the front's read, its zoomed re-read, the ספח / card back's copy (which `aiReadSefach` now returns) — with the Latin spelling or the MRZ name line, when the document has one, deciding between them.

Tried first and dropped: rebuilding a sharp copy of the whole page from the photo (replay the warps at up to 3200 px), then cropping from it. On a 4x-throttled CPU that took ~4 s per page (the per-pixel warp of the whole card), and for a ספח it would have added to the wait. Cutting only the field regions from the photo takes ~0.5 s for all of a scan's fields.
