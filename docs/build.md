# Build: the new stack and dist/

The move to React ([react-migration-plan.md](../archive/docs/react-migration-plan.md)) is done (stages 0–7). Two kinds of page build into `dist/`:

- **New pages** — React + TypeScript + Tailwind + shadcn/ui in `src/`, built by Vite: the test page `/next` (`next/index.html` → `src/next/`), the worker punch page (`worker-punch.html` → `src/punch/`), the manager app (`schedule-manager.html`) and the scanner lab (`/scan-lab/`: `scan-lab/index.html` → `src/scan/lab/`; docs/scan-plan.md → Scanner lab); they keep their old file names, so `/punch`, the workers' links and the service worker's list stay the same. `client-portal.html` and `supplier-portal.html` (`/client`, `/supplier`) are small static pages that only send to the manager app, where a client or supplier works (permissions plan, stages 3–4).
- **The manager app** — `schedule-manager.html` at the repo root, a Vite entry since React migration stage 8c-2: its markup and inline `<style>`, and one module, `src/manager/page/entry.ts` (the data layer and logic through `src/manager/globals.ts`, the page's own script — the typed modules of `src/manager/page/`, the React pieces `src/manager/main.tsx` — one bundle). The files it loads as they are carry `vite-ignore` in the HTML (Vite leaves them and drops the attribute) and are copied into the build: `og.css` (after the page's own styles, as before), `payroll.js`, the fonts, the icon subset, the manifest and icons; it also loads `firestore-backend.js`.

Firebase Hosting serves `dist/`, which `npm run build` makes from both.

## The tokens in the new stack

`og.css` stays the one copy of `docs/design/system/tokens.json` in the code. A new page links `/og.css` (and `/fonts/fonts.css`) in its HTML entry; Vite bundles both into the page's CSS. `globals.css` defines no token: its `@theme inline` block points Tailwind's color names at the tokens — the shadcn/ui names (`background` → `--ground`, `foreground` → `--ink`, `card` → `--plate`, `popover` → `--glass-menu`, `primary` → `--glass-strong`, `secondary` → `--glass`, `muted` → `--surface-2`, `muted-foreground` → `--ink-2`, `accent` → `--glass-active`, `destructive` → `--red`, `border` → `--hairline`, `input` → `--glass-edge`, `ring` → `--accent`) and the Odinson Glass names (`plate`, `plate-on`, `glass`, `glass-edge`, `sheet`, `faint`, `info`, `ok`, `warn`, `bad`, `fig`). `og.css` is unlayered, so where a name is both a token and a Tailwind theme variable (`--font-sans`, `--font-mono`, `--radius-sm` … `--radius-xl`) the token wins: `rounded-lg` is 16px and `font-sans` is DM Sans. A class like `bg-plate` or `text-muted-foreground` is the way to color a new component; `tests/design/check.js` fails when a file in `src/` or `next/index.html` defines a token.

## `npm run build`

1. `tsc --noEmit` — the TypeScript check; an error stops the build.
2. `vite build` — builds every page in `input` into `dist/` (`dist/next/index.html`, hashed files in `dist/assets/`) the manager page among them (`dist/schedule-manager.html`, its module hashed in `dist/assets/`); `dist/` is emptied first.
3. `node scripts/copy-static.mjs` — copies the files loaded as they are (the manager page's `vite-ignore` links, `firestore-backend.js`, the fonts, icons, i18n…) into `dist/` byte for byte. The list (`staticFiles`) is every file tracked by git (every file on disk when there is no git) except: the top-level `firebase.json`, the rules and index files, the pages' HTML entries at the top level (`worker-punch.html`, `schedule-manager.html`) and `manifest-punch.json` (built by Vite with the punch page), `docs/`, `archive/`, `functions/`, `functions-auth/`, `tests/`, `node_modules/`, `dist/`, `src/`, `next/`, `scripts/`, `package.json`, `package-lock.json`, `tsconfig.json`, `vite.config.mts`, `components.json`; anything under a dot folder or named with a dot first; and any `*.md`, `Screenshot_*.jpg|png`, `*-local.html`, `*.log`, `*.pyc` or `__pycache__`. A file Vite also built stops the copy with an error.

**Generated scripts.** `payroll.js` (the manager page's copy of `src/lib/payroll.ts`, docs/accounting.md → Payroll module) and `firestore-backend.js` (of `src/lib/firestore-backend.ts`, docs/backend.md → Browser data layer) are not built here: they are committed, so the page also works from the repo root. Step 1 is followed by `node scripts/build-globals.mjs --check`, which builds each in memory (Vite library mode, one IIFE, not minified; `Payroll` as a global, `initFirestoreBackend` set on `window` by `src/lib/firestore-backend-global.ts`) and stops the build when a committed file differs; `node scripts/build-globals.mjs` (or `npm run build:globals`, `npm run build:payroll`) writes them. Never edit either file by hand.

`tests/build/check.js` then checks `dist/`: every listed file is there and identical to the repo's, the built `schedule-manager.html` loads `og.css`, `payroll.js`, the fonts, the icons and the manifest as they are (and no `vite-ignore` is left), `service-worker.js`, `og.css`, `manifest.json`, `payroll.js` and the icons are on the list and `worker-punch.html` / `schedule-manager.html` / `manifest-punch.json` are not, `client-portal.html` / `supplier-portal.html` are copied and only send to `/schedule-manager.html`, the punch page's built manifest has absolute paths and its icons and start page are in `dist/`, nothing that must never be public is in it (functions, tests, docs, `src/`, sources and config, dot files), `dist/next/index.html`, `dist/worker-punch.html`, `dist/schedule-manager.html` and `dist/scan-lab/index.html` point at their built scripts (`scan-lab/` and `scan/` have none of their files copied: right after the build `dist/scan-lab/` is the built lab page alone and `dist/scan/` is not there — the deploy puts the models in), the scanner's surfaces are kept apart (below, The scanner's entries → the surface guard), and `firebase.json` serves `dist`.

### The scanner's entries

The scanner (docs/scan.md, docs/scan-plan.md → S9) is built into two pages, each on its own **surface** — its own folder of models and ONNX Runtime, put there at deploy:

- **The site's scanner** — no page of its own: the manager page's module loads it on demand (`src/scan/open.tsx` → `import('./Scanner')`, its own chunk) over `siteSurface()` (`src/scan/engine/surface.ts`: base `/scan/`, browser cache `scan-models`).
- **The scanner lab** — `/scan-lab/` (`scan-lab/index.html` → `src/scan/lab/`; `scan-lab` is in `EXCLUDED_TOP`, so nothing of it is copied) over `labSurface()` (`src/scan/lab/surface.ts`: base `/scan-lab/`, cache `scan-lab-models`). The lab's surface is a module of its own that only the lab imports, so the chunks the site's scanner shares with the lab never hold the lab's folder.
- **The module worker.** Both start the same background thread, `src/scan/engine/worker.ts`, built by Vite as an ES module chunk (`vite.config.mts` → `worker: { format: 'es' }`; `new Worker(new URL(…), { type: 'module' })`). It names no folder: the surface comes in its `load` message.
- **ONNX Runtime at run time, from the surface's folder.** Nothing of ONNX Runtime is bundled: `src/scan/engine/ort.ts` imports `<base>ort/ort.all.min.mjs` (1.22, the CPU) or `<base>ort130/ort.all.min.mjs` (1.30, the GPU) with `/* @vite-ignore */`, and its `.wasm` and loader `.mjs` come from the same folder (`wasmPaths`). The models (`lite.onnx`, `sa24_w16.onnx`, `yunet.onnx`, and `doctype.onnx`, `mrz.onnx`, `he.onnx` when `models.json` lists them), `models.json` and `he-layouts.json` come from `<base>` too.
- **Put there after the build**, not by Vite: `scripts/scan-lab/fetch-models.sh dist/scan-lab` (the lab's version, `scripts/scan-lab/models-version`) and `scripts/scan/fetch-models.sh dist/scan` (the site's, `scripts/scan/models-version`), each in `deploy.yml` and the lab's in `scan-lab-preview.yml` (backend.md → Deploys). Each script ends by checking that every file its page loads is there (the models `models.json` lists, `he-layouts.json` with the Hebrew reader, both ONNX Runtime builds' `ort.all.min.mjs`, `.wasm` and loader `.mjs`; each copies its `THIRD-PARTY.txt` too) and that `models.json` names its `models-version`; one missing stops the deploy. A local `npm run build` has no models: the browser tests stand in for them.
- **The surface guard** (`tests/build/check.js`): from each page's module it follows the chunks it reaches (imports, dynamic imports, preload lists, the worker's URL). No chunk the manager page loads may name `/scan-lab/` — except the manager's own module, where Admin → Scanner reads `/scan-lab/models.json` for the lab's version and Admin → Scanner lab opens `/scan-lab/` in a new tab, neither loading a model; any other `/scan-lab/…` there fails too. The lab page's module names `/scan-lab/`. Both pages reach the scanner's worker as a module worker; its chunk is an ES module (not wrapped as a classic script) with no `importScripts` and no surface folder of its own.

## Other commands

- `npm run dev` — the Vite dev server. It serves the repo root, so the manager page opens at the same paths as on Hosting (`/schedule-manager.html`, `/og.css` …) and the new ones at theirs (`/next/`), with instant reload for `src/`.
- `npm run typecheck` — only the TypeScript check.
- `npm run preview` — serves `dist/` after a build.
- `npm run check:build` — `tests/build/check.js`.

## Hosting and CI

What Hosting serves (`firebase.json` → `hosting.public` is `dist`, the rewrites, the `no-cache` headers, the `ignore` list) and every workflow — `deploy.yml` builds, checks `dist/` and deploys it on a push to `main` (a failed build or check deploys nothing), `tests.yml` runs every suite on a pull request — are in [backend.md](backend.md) → Deploys; the suites themselves in [tests.md](tests.md). The service worker (`service-worker.js`) is copied as is; it is network-first for every same-origin GET and keeps a copy of each file it fetched, so a new page opened once online also opens offline with its hashed files (the punch page relies on it — keep its code free of lazy chunks).

## The manager's React pieces

Stage 6 moved the manager app (`schedule-manager.html`) to React one tab at a time; the page is copied byte for byte and every tab and window is a React root inside it:

- **Loading.** Since stage 8c-2 the React pieces are part of the page's one module: `src/manager/page/entry.ts` imports `src/manager/main.tsx` after the page's own script (the modules of `src/manager/page/`), so the page's bridge (`provideBridge`, page/bridge.ts) is there when they mount; `npm run dev` serves the page from the source like the other entries.
- **Styles.** `src/styles/manager.css`, imported as a string and put in a `<style>` right before the page's `og.css` link: Tailwind's theme and utilities with the shadcn names (`theme.css`) and no preflight (the page has its own reset), not in a cascade layer (the page's unlayered `* {margin:0; padding:0}` would beat layered utilities), and a small reset scoped to the React roots (`[data-island]`). og.css comes after it, so og.css still wins where they meet, as on the new pages.
- **Data and actions.** The page gives its bridge once — `provideBridge(…)` in `src/manager/page/bridge.ts`; the React pieces read it with `bridge()` (`src/manager/bridge.ts` is the contract and the registry; `window.ManagerBridge` is set too, for the browser tests only — React migration 8f): the language and its loaded dictionary (`lang()`, `dict()` — the pieces call `adoptLanguage`, no `I18nProvider`), a tab's snapshot (`today()`, `schedule()`, `workers()`, `clients()`, `suppliers()`, `accounting()` with `accData()`), and the page's actions (Today: `openWorker`, `openNotices`, `openSuppliers`, `addWorker`, `refresh`; ## Adding a new page

Add its HTML entry (like `next/index.html`: links `/fonts/fonts.css` and `/og.css`, one `<script type="module">` to its code in `src/`) to `input` (and `optimizeDeps.entries`) in `vite.config.mts`, its folder name — or, for an entry at the top level that replaces an old page (`worker-punch.html`), its file name — to `EXCLUDED_TOP` in `scripts/static-files.mjs`, the entry to the built pages `tests/build/check.js` checks, its route to the Hosting rewrites, and a browser check.
