# Supplier portal (`supplier-portal.html`, `src/supplier/`)

**Inside the manager app since 2026-10-19** (docs/permissions-plan.md → stage 3): a supplier signs in on the one login page and stays in the manager app, in the same frame. Its tabs (`portalTabs`, `src/manager/portal.ts`): **Today** (the dashboard, portal tab `dashboard`), **Workers** (`workers`), **Commission** (its hours and pay, portal tab `hours`) and, with an hours or schedule tick (claim `hp`), **Hours** (the hours review). Each is drawn into the page's one `#sectionPortal` by `src/manager/Portal.tsx` with this portal's own screens (`Dashboard`, `Workers`, `Hours`, `HoursReview`) and its reads (`useSupplierData`, the `supplier` function) — the gate (`startPortal`, `src/manager/page/gate.ts`) loads no firm data for it (`runInitApp` never runs), so nothing reads Firestore (a browser check counts the Firestore requests: none). The gate still writes this portal's session key, which its screens read, checks the Firebase sign-in and reads the tabs from the ID token (`supplierSections()`, `hourPerms()`). `supplier-portal.html` (`/supplier`) only sends to the manager app (`src/supplier/main.tsx`); a session kept here is taken over by the manager page's gate (`adoptPortalSession`). The page's own frame code (`App.tsx`) stays until stage 4. The rest of this file describes the screens and the data, which are unchanged.

The page for a supplier (staffing agency) login, routed at `/supplier`. A separate page on purpose: it never loads the manager app's rate, GPS or scan code. The real boundary is on the server — the supplier gets data through allow-lists and can only write through narrow actions.

A page of the new stack (stage 4 of [react-migration-plan.md](react-migration-plan.md); [build.md](build.md)): `supplier-portal.html` at the repo root is its Vite entry (built into `dist/supplier-portal.html` and `dist/assets/`, never copied as an old page; the same file name, so `/supplier`, the manager app's hand-over and the service worker's list stay the same); its code is `src/supplier/`. Forms on React Hook Form + Zod, the pay table on TanStack Table (the Data Table), reads through TanStack Query; SheetJS from cdnjs, loaded only when an Excel export or the timesheet import needs it (`loadScript(XLSX_URL)`).

Who creates a supplier login and how: [admin.md](admin.md) → Users pane. The supplier entity and commission: [suppliers.md](suppliers.md), [accounting.md](accounting.md).

## Session and requests

- The session is kept in its own key `localStorage.supplierPortal_session`, so a manager login on the same browser is never touched. It holds `{uid, role, tenantId, supplierId, username}`; `getSession()` drops one without `uid` or with a role other than `supplier`.
- **One login for every role** (user request 2026-10-11): the portal has no login screen. A supplier signs in on the manager app's login page, which hands the session over (`goToSupplierPortal`, [app-core.md](app-core.md) → Login). Without a kept session a small script in the HTML head goes to `schedule-manager.html` before anything loads; after loading, **`passGate()`** (`App.tsx`, once per load) also checks the Firebase sign-in (`loadBackend().currentUser()`) and, when it is gone, drops the session and goes to the login page. The gate also reads the login's tabs (`supplierSections()`, claim `ss`) and hours ticks (`hourPerms()`, claim `hp`).
- **The frame:** `Shell` with the 11C brand and "Supplier Portal"; the tabs (on a computer under the title bar, on a phone the bottom bar); at the right the Language button and the account menu (`AccountMenu`: the login's name, "Supplier", **Sign out** → `logout()`: the portal's session and the Firebase sign-in — one per browser for the whole site — end, the login page opens).
- **Requests:** `supplierCall(body)` (`api.ts`) posts to the `supplier` function (`SUPPLIER_FN_URL`, europe-west3) with `Authorization: Bearer <Firebase ID token>` and resolves with the JSON reply; a session error in the reply logs out. Actions: `loadSchedule`, `loadPunchLog`, `supplierAddWorker`, `supplierUpdateWorker`, `supplierDeleteWorker`, `supplierSubmitHours`, `supplierListHours`.
- The new version check (`useVersionWatch`: the page's own HTML, which names its hashed bundle, and `firestore-backend.js`) offers **Update** in a toast after a deploy.

## Data (`useSupplierData()`)

One TanStack Query read (`['supplier', 'data']`): `loadSchedule` and `loadPunchLog` in parallel → `{workers, clients, punches, showPay, commission}`. It is cached across a language change (the page is redrawn, the data is not loaded again) and refreshed (`refreshData()`) after every write. What the server sends a supplier (`functions-auth/portal.py` `strip_worker`):

- **workers** — only those with `supplierId` = this supplier, and only these fields (`SUPPLIER_WORKER_FIELDS`): `id, name, docGiven, docSurname, docId, docType, docDob, docSex, address, houseNumber, city, maritalStatus, healthFund, workStartDate, phone, docChildren, clientIds, supplierId, startDate, expiryEnabled, expiryMonths, expiryWarnMonths, avatarB64, colorIdx, notes, createdAt, schedule`, plus `supplierRate` = this supplier's commission ₪/h override or `null` (default 5), and `supplierDayRate` = its fixed ₪/day commission for a worker paid by the day (`supplierRates[sid].dayRate`; sent only if the worker is paid daily — `null` otherwise). With **"Sees own workers' pay"** (the login's `showPay`, claim `pay`, on unless the owner turned it off) also `SUPPLIER_PAY_FIELDS`: `payMode, hourlyRate, regRate, otRate, shabbatRate, clientRates, dayOverrides`; without it no wage at all. Never `supplierRates` (other suppliers' commissions), never the worker's punch-link `token` (a supplier must not be able to punch for its workers), never a stored-file link (`docUrl`, `docFileId`, `assetsFileId`);
- **clients** — `{id, name, object}`; with "sees pay" also the worker-pay rates `defaultHourlyRate, defaultOtRate, defaultShabbatRate` (`CLIENT_PAY_FIELDS`) — never client billing (`billRate`, `rateMode`, …), GPS or company numbers;
- **showPay** — whether this login sees pay;
- **commission** — this supplier's own rate list `[{from, mode, rate}]` (`sp.commission`, set by the firm owner);
- **suppliers** — always empty;
- **punches** — only this supplier's workers, only `id, workerId, workerName, type, time, date, site, clientId` (plus `ts`); no GPS, distance or notes. The last 13 months.

## Tabs

The tabs a supplier login may use are ticked in Admin → Users (`users.supplierSections` → claim `ss`, read by `supplierSections()` in `firestore-backend.js`; none stored = all three): a tab without its tick is hidden and the page falls back to the first allowed one. The `supplier` function enforces it: worker add / edit / delete need **My Workers** (`workers`), sending and listing hours need **My Hours** (`hours`) — else "Not allowed for this login". The open tab is kept in `store.ts` (a reload opens the first tab).

- **Dashboard** (`Dashboard.tsx`): `Figures` — On site now (workers whose last punch is IN), My workers, punches today — then a "Today's log" `Section` with today's punches as small plates (green IN / red OUT, the client, the time), paged by 10 (`PagedList`).
- **My Workers** (`Workers.tsx`; `PageHead` with **New** in plain glass, `og-new`): a "Workers" section with the count and the Select button (`SelectHead`), then a `Plate` per worker — name and the `NewBadge` (3 days after `createdAt`), phone · clients, the commission (₪/h or ₪/day, `plateRate`), green while the worker is on site; a tap, a double click or a long press opens the edit form; ⋮ and a swipe left: Edit, Delete; paged by 10. **Delete never asks**: the plate goes behind the Undo snack (`undoDelete`) and `supplierDeleteWorker` runs only after its 5 s (Undo brings it back, nothing is sent); Select's bulk bar deletes the ticked workers the same way. After each change the data is refreshed.
  - **Add / edit** (`WorkerWindow` → `WorkerForm`): a `Window` (a bottom sheet on a phone) with a React Hook Form + Zod form drawn like the manager app's editors — Accordion section plates, one open at a time, a closed one shows its summary: Person (given name + surname, phone + ID/passport number) and Address (address + city); Save is the one primary. The given name is required (Zod, "Name required"; a save without it opens Person). The name fields fall back to splitting `name` for an older record. No document scan here (a deliberate scope cut). Saved with `supplierAddWorker` / `supplierUpdateWorker`.
- **My Hours** (`Hours.tsx`): a month (a Select: this one and the 11 before it).
  - **Pay** (only with `showPay`): `Figures` (Hours, Pay, My commission), then a **Data Table** — per own worker with hours that month: Worker, Hours, Days, Rate (₪/h, or ₪/day for a daily-paid worker), Pay, My commission, with the totals row; a tap on a column head sorts; paged by 10; on a phone each row is a plate ("8.0h · 1 day · ₪50/h · Pay ₪400" and the commission).
  - **Export**: a worker (a Combobox) for **Detail** (`exportDetail`: the worker's shifts that month, Date / In / Out / Hours + total) and **Summary** (`exportSummary`: per worker with hours that month, its commission by `myMonthCommission()`, the rate by `myRateLabel`), each Excel or a print page (the print page's data through `esc()`, `src/lib/utils.ts`).
  - **Send hours for approval**: a worker (a Combobox) and "Add shift" rows of date (a Date Picker) / in / out (each new row takes the next day — `addSendRow`); **Load from Excel** (`parseTimesheetFile`, `.xlsx/.xls/.csv`) adds rows from a timesheet: columns by header — Date, In, Out (English or Hebrew), and an optional Worker column (a name or an ID number, `timesheetRowIsFor`) so one sheet can hold several workers; only the picked worker's rows are added, to check and send like typed rows, and the toast says how many rows of other workers were left; a daily-paid worker needs only a date — one day, 08:00–16:00; a row that can't be sent is outlined red and explained, nothing is sent; **Send for approval** (the one primary) → `supplierSubmitHours`.
  - **Sent for approval** (`useSentHours` → `supplierListHours`, refreshed after a send): each batch as a plate with an amber / green / red status badge and its date, paged by 10.
- **Approvals** (shown only with an hours or schedule tick — `hourPerms`, read from the ID token): the shared React hours screen `HoursReview` ([hours-review.md](hours-review.md) → The screen in the new stack) over the `hours` function — its own workers' days approved, disputed or given a proposed fix (by its ticks), the month approved at once.

Hours use `groupPunchesIntoShifts` / `analyzeDayPunches` (the short check: no warnings, no rounding) from `src/lib/payroll.ts`. Pay uses the same pay functions as the manager app (`effectiveRates`, `shiftPayFor`, `isDailyPay`, `dailyRate`, `dayOverride`, `localYMD` — imported from `src/lib/payroll.ts` with this page's `clients`, docs/accounting.md → Payroll module), so a worker's pay is the same figure as in the manager's Salary table. Commission is independent of pay (`myMonthCommission`): a worker with an override of his own (`hasOwnCommission`: `supplierRate`, or `supplierDayRate` for a daily-paid worker) uses `myCommission` — days × `supplierDayRate`, else hours × `supplierRate`; otherwise each shift is priced by the supplier's own rate on its date (`myRateOn` / `myShiftCommission`, copies of the manager app's `supplierRateOn` / `supplierShiftCommission`: by the hour, by the day once per day, or 5 ₪/h).

## Windows

The worker window closes like every window: a tap outside it (or a swipe down on a phone), no ✕ or Cancel button ([components.md](components.md) → `Window`).

## What a supplier can write

Only these actions:
- `supplierAddWorker` — a new worker with `supplierId` forced to the caller's own, `clientIds: []`, `schedule: []`, `createdAt` (now, ISO — the "NEW" badge for 3 days, shown in the app and in the portal's worker list), and only the editable fields;
- `supplierUpdateWorker` / `supplierDeleteWorker` — only a worker whose `supplierId` is the caller's; otherwise "Worker not found";
- `supplierSubmitHours` `{workerId, clientId, entries:[{date dd/MM/yyyy, inTime, outTime}]}` — shifts for its own worker, at most 62 rows, invalid rows dropped, a client that isn't the worker's dropped; written as a `pending` batch (`supplierId`, `createdBy`) for the owner to approve; `supplierListHours` → its batches with `status`, `uploadedAt`, `decidedAt` and the rows;
- editable fields (`SUPPLIER_EDITABLE`): `docGiven, docSurname, phone, docId, address, houseNumber, city, docDob, docSex, maritalStatus, healthFund, startDate, notes, status`; `name` is rebuilt from given name + surname.

A supplier cannot call `saveSchedule`, the app's hours-import actions (it sends hours only through `supplierSubmitHours`) or the AI reads (refused on the server), and has no client billing data to show; wages only with "sees pay". The page never reads Firestore: `tests/e2e/main.test.js` checks the `supplier` function's replies for tokens, client billing and GPS.
