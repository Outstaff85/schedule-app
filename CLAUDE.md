# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Session language:** the user communicates in Russian. Before starting any work, and throughout the session, Claude's own conversational output (explanations, status updates, questions) should be in Russian — this is independent of what language the app's UI/code is in (see the UI-text rule below).

**UI text language:** all new user-facing UI text (tab labels, buttons, messages, etc.) added going forward must be in English, not Russian. The `Бухгалтерия` (Accounting) tab and its related labels were added in Russian by mistake — don't repeat that; new labels should be English even though most of the existing app is Hebrew (`lang="he"`) with that one Russian pocket. Existing Hebrew/Russian text doesn't need to be retranslated unless asked.

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served as static files from Firebase Hosting. There is no build step, no bundler, no package.json, and no test suite — the two pages are self-contained HTML files with inline `<style>` and `<script>`.

**Multi-tenant (merged to `main` 2026-09-18, PR #34):** this app is now multi-tenant — a super-admin creates "firms" (tenants) with their own login, and each firm's data (schedule, punches, Drive docs) is isolated. See `MULTI_TENANT_PLAN.md` for the full data model, auth design, and status, including the newer super-admin firm activate/deactivate/delete actions added right after the merge. `apps-script/Код.js`/`google-apps-script.js` now require session tokens on top of the legacy `API_SECRET`, and `schedule-manager.html` has a login screen plus `gsAuth()`/`gsAuthQuery()` wrappers sending that token on every request. **Everything below this notice was written for the pre-multi-tenant single-tenant app and has not been fully updated** — sheet layouts (e.g. `Schedule` described below as one global key/value row) and auth details may now be stale; cross-check against `MULTI_TENANT_PLAN.md`'s "Data model" and "Auth" sections before relying on specifics below.

- `schedule-manager.html` — the manager/admin app (shifts, workers, clients, payroll, exports). RTL, Hebrew (`lang="he"`), ~3200 lines.
- `worker-punch.html` — the worker-facing clock-in/out app, opened via a per-worker tokenized link. ~1000 lines.
- `service-worker.js` — PWA offline shell (network-first, cache fallback).
- `manifest.json` / `manifest-punch.json` — separate installable-PWA manifests for the two apps.

- `apps-script/appsscript.json` — Google Apps Script project configuration (timezone, runtime version, web app access rules, OAuth scopes). Declares required OAuth scopes: `spreadsheets` (Sheets read/write), `script.external_request` (HTTP calls to Anthropic API), `drive` (storing worker PDFs and accessing Google Drive). Configures the Apps Script project deployed to `script.google.com`.
- `apps-script/.clasp.json` — Google Apps Script CLI (clasp) configuration linking the local source to the deployed project via `scriptId`.
- `form101_fillable.pdf` — Israeli tax form template. No longer fetched by the client — `functions/assets/form101_fillable.pdf` (a copy) is what the Cloud Function actually fills. Kept at the repo root only as the source copy to re-sync from if the template is ever updated. See "Form 101 PDF generation (server-side)" below.
- `form101-field-map.md` — verified field-by-field map of `form101_fillable.pdf` (every AcroForm field's name/rect/Hebrew label/meaning, plus the printed comb-boxes the template ships with no field behind). Built by rendering the PDF and cross-checking coordinates against the visible labels — not guessed from the code. **Consult and update this file whenever touching `functions/main.py`'s field rects or the PDF template changes**; drift between this map and the code is what caused the "scanned passport → Form 101 fields land in the wrong place" bug it documents (see its "Known-fixed bugs" section).
- `heebo-hebrew.ttf` — Heebo Hebrew+Latin TTF font subset (OFL licensed). No longer used client-side — `functions/assets/heebo-hebrew.ttf` (a copy) is what the Cloud Function embeds. Kept at the repo root only as the source copy.
- `functions/` — Python Cloud Functions (`main.py`, two HTTP endpoints): `fill_form_101` fills Form 101 server-side via PyMuPDF (see "Form 101 PDF generation (server-side)" below), `preprocess_scan` does OpenCV+Pillow scan preprocessing (see "Server-side pre-filter before `autoPreAlignScan`" below). Has its own `venv/` (gitignored) required by `firebase deploy --only functions` on this CLI version — Python deploys expect a pre-built virtualenv, they don't create one.
- `MULTI_TENANT_PLAN.md` — design doc + status tracker for the in-progress multi-tenant/login feature (see the notice above). Data model, auth design, migration steps, and the Drive/Form-101 follow-up.

## Commands

There is no npm/build/lint/test tooling. Development is edit-the-HTML-and-reload.

- Local preview: `firebase emulators:start --only hosting` (uses `firebase.json` rewrites), or just open the HTML files directly in a browser.
- Deploy: Push to `origin/main`; GitHub Actions workflows automatically deploy both static hosting and backend on every commit:
  - `.github/workflows/deploy.yml` — deploys `schedule-manager.html`, `worker-punch.html`, and supporting files to Firebase Hosting (project alias `schedule-odinson`, see `.firebaserc`). **No manual `firebase deploy` step is used** — a push to main is what triggers the deploy. This workflow does not cover `functions/` or `apps-script/` — those have their own workflows below; a session rooted outside this repo (see the auto-commit hook note above) may also end up running `firebase deploy --only hosting` manually since it can't rely on the push-triggers-deploy flow working as expected until that's confirmed.
  - `.github/workflows/deploy-apps-script.yml` — deploys Google Apps Script source (anything in `apps-script/`) via `clasp push --force` and `clasp deploy` to the configured Apps Script project (requires `CLASP_CREDENTIALS` and `CLASP_DEPLOYMENT_ID` GitHub secrets).
  - `.github/workflows/deploy-functions.yml` (added 2026-09-21) — deploys the Python Cloud Functions (`functions/`) on any push to `main` touching `functions/**`, or via manual `workflow_dispatch`. Builds a fresh venv in CI (`python -m venv venv && pip install -r requirements.txt` — the committed `functions/venv` note below is about the *local* dev machine; CI never reuses it, gitignored either way), installs `firebase-tools` via npm, and runs `firebase deploy --only functions --project schedule-odinson` authenticated via `GOOGLE_APPLICATION_CREDENTIALS` pointed at the `FIREBASE_SERVICE_ACCOUNT` secret (the same secret the Hosting workflow uses). **Not yet confirmed working end-to-end**: that service account was provisioned for Hosting deploys and may lack the IAM roles a 2nd-gen Python Cloud Functions deploy needs (Cloud Functions Admin, Service Account User, Cloud Run Admin, Artifact Registry Writer, Eventarc Event Receiver) — if the first real run fails on a permissions error, grant those roles to it in GCP Console → IAM, project `schedule-manager-498317`, and re-run. On failure the workflow opens/updates a GitHub Issue titled "Cloud Functions deploy failing" with the likely causes (mirroring the apps-script workflow's self-diagnosing pattern), so watch for that issue rather than needing to notice a red X in Actions. `firebase.json`'s `functions[0].runtime` is pinned to `"python312"` (added alongside this workflow) so the deployed runtime is deterministic and doesn't depend on whatever Python version happens to be on the CI runner or a dev's local machine (the local `functions/venv` was built against Python 3.14, which is unrelated to and does not need to match this).
- Routing: `firebase.json` rewrites `/` → `schedule-manager.html` and `/punch` → `worker-punch.html`.

When bumping the service worker's cache (`CACHE` constant in `service-worker.js`, currently `schedule-mgr-v25`), increment the version string (e.g. `v25` → `v26`) or clients will keep serving stale cached HTML after deploy. The `CORE` list (files precached on install/offline fallback) also now includes `icon-192.png`/`icon-512.png`, in addition to the two HTML pages and both manifests — both manifests' `icons` arrays reference these same two files (previously empty, which left the PWA install/home-screen icon blank). PostToolUse hook auto-commits and pushes to the **current branch** (`git push origin HEAD`, not hardcoded to `main`) on every file edit (see `.claude/settings.json` for the hook configuration) — so whichever branch is checked out is what receives the auto-commits.

**This hook only fires in a Claude Code session whose own project root IS this repo.** It's a project-level `.claude/settings.json`, and Claude Code loads project settings from the session's working directory at session start — not from whatever directory a session later `cd`s into via Bash. A session opened elsewhere (e.g. rooted at the user's home directory) that reaches this repo only through absolute paths / `cd` inside Bash calls never loads this file at all — confirmed 2026-09-20: an entire session's worth of Edit/Write calls produced zero auto-commits, traced to the session's actual root (`~/.claude/settings.json`) having no hook, while this file did/does. No config fix exists for that case; the session has to actually be opened with this repo as its working directory (or `--add-dir`/equivalent) for the hook to load. If you're debugging "the hook isn't firing" again, check the session's own root settings file before assuming this config is broken. **A global `~/.claude/settings.json` PostToolUse hook (matcher `Write|Edit|NotebookEdit`, scoped via `"if": "Edit(H:/schedule-app/**)"`) was added at one point to patch exactly this gap, then removed again on 2026-09-21** — it duplicated this project-level hook's commit+push whenever a session *was* rooted here (both hooks fired on every edit), and it couldn't help cloud sessions anyway (claude.ai/code sessions only ever see this checked-in project file, never the user's personal global settings). The gap for locally-rooted-elsewhere sessions is accepted as-is rather than patched again. This project's commit/push command hook carries `"if": "Edit(H:/schedule-app/**)"` (added 2026-09-21) so it only actually runs when the edited file is inside this repo — previously the matcher (`Write|Edit|NotebookEdit`) fired on *any* such tool call in the session regardless of path, so an edit to an unrelated file elsewhere on disk (e.g. the user's own `~/.claude/settings.json`) still ran `git add -A` for no reason (harmlessly, since it found nothing to commit, but wastefully).

**CLAUDE.md-sync agent hook moved from per-edit to per-PR (2026-09-21), to cut agent token spend.** It used to run after *every single* auto-commit (`PostToolUse` on `Write|Edit|NotebookEdit`, diffing just `HEAD~1..HEAD`) — one paid agent call per edit, most of which touch nothing doc-worthy. It now runs once, right before a PR goes up for review: `PostToolUse` on `Bash` with `"if": "Bash(gh pr create*)"`, diffing the PR's *entire* range (`git diff origin/main...HEAD`) against CLAUDE.md in one shot. This is the same hook that used to live only in the user's personal global `~/.claude/settings.json` (see the note above) — it's now defined here instead, in the checked-in project settings, so it also covers cloud sessions (which never see the user's personal global settings) rather than only this user's local machine.

**`PreToolUse` hook blocks force-push and direct pushes to `main` (added 2026-09-21).** Matcher `Bash`, `"if": "Bash(git push*)"`. Denies (via `hookSpecificOutput.permissionDecision: "deny"`) any `git push` containing a force flag (`--force`, `--force-with-lease`, `-f`), any push whose command text names `main` as a target, or any push while the current branch is `main` — enforcing in tooling what the "PR merge policy" section above already states in prose (land changes via a PR from `My_Work_Befor_PR`, never a direct/forced push to `main`). Implemented in Python (not `jq`, which isn't installed in this environment) via an inline `python -c` script.

**`SessionStart` hook surfaces `git status` as context at session start (added 2026-09-21).** No matcher (fires once per session start). Runs `git status --short` plus the current branch inside `$CLAUDE_PROJECT_DIR` and injects it via `hookSpecificOutput.additionalContext`, so a session opening this repo immediately sees whether the working tree is dirty and which branch it's on, without needing to run `git status` itself.

**Claude must never merge a pull request without asking first.** After opening a PR, ask the user whether to merge it (as before) rather than merging automatically or staying silent about it — merging itself only happens on an explicit yes. Pushing commits to a feature branch (what the hook above does, and what Claude should keep doing when asked to commit) needs no such check-in; it's specifically the merge-to-`main` step that always needs the user's go-ahead.

**Active work branch:** `My_Work_Befor_PR` is the standing work branch for this project — both local sessions and cloud sessions (claude.ai/code) should check it out (or start/resume the cloud session on it) at the beginning of work, instead of working directly on `main`. Do not create a new ad-hoc branch per session; keep using `My_Work_Befor_PR` until the user says otherwise. This keeps every edit hook auto-commit (local and cloud alike) landing in the same branch.

**PR merge policy:** when a session's work has a pull request open, land it by actually merging that PR on GitHub (merge button or the GitHub API) — never by closing the PR after pushing the same content to `main` directly. Direct-to-main pushes from the per-edit auto-commit hook are fine for iterating within a branch; only merging the PR itself makes GitHub's merged/closed counts (and anyone watching the repo) reflect what actually shipped. `My_Work_Befor_PR` (see above) is where that iteration happens before the PR into `main` is merged.

## Architecture

### Backend: Google Apps Script

Both HTML files talk to the **same** Google Apps Script Web App endpoint (`GS_URL`, a `script.google.com/macros/.../exec` URL hardcoded near the top of the `<script>` block in each file), authenticated with a hardcoded shared secret (`API_SECRET` = `'odinson-7Kq2x9'`). The Apps Script project (backed by a Google Sheet) is the actual database. Source code is in `apps-script/` (tracked here and auto-deployed via GitHub Actions when pushed to `main`). Configuration is in `apps-script/appsscript.json` (project settings: timezone, runtime, web app access). The project ID in `apps-script/.clasp.json` links the local source to the deployed Apps Script via clasp. Requests are plain `fetch()` calls with an `action` field selecting the server-side operation:

**GET endpoints:**
- `loadSchedule` — fetch workers/clients/weekStart/savedAt.
- `loadPunchLog` — fetch punch entries (with optional worker/date/type filters).
- `calcSalary` — compute daily/worker hours from punch log.

**POST endpoints (write actions, require `API_SECRET` unless noted):**
- `login` — authenticate with username/password (no token required; returns session token, role, tenantId, tenantProfile, and expiry). Only reachable action without a prior session.
- `createUser` (super-admin only) — create a new firm (tenant) with initial Users login; accepts companyName, deductionsFileNumber, phone, street, streetNumber, city, username, password; returns userId and tenantId. **All field values are formatted as plain text (`setNumberFormat('@')`) BEFORE being written** (via `setValues()` after formatting), matching the critical formatting in `updateTenant` — this prevents Google Sheets from auto-coercing digit strings to numbers and dropping leading zeros (Israeli phone numbers, deductions file numbers), which would corrupt what Form 101 prints on the firm's very first save.
- `updateTenant` — edit firm profile (companyName, deductionsFileNumber, phone, street, streetNumber, city); super-admin can edit any firm, a firm's own login edits only itself. **Returns refreshed tenant profile** (`{ok: true, profile: {...}}`) — the client caches the profile once at login, so this response refreshes that cache without requiring re-login to see edits. **Critical:** All field values are formatted as plain text (`setNumberFormat('@')`) BEFORE being written to prevent Google Sheets from auto-coercing digit strings to numbers and dropping leading zeros — a silent data loss for Israeli phone numbers (03-…, 052-…) and deductions file numbers (תיק ניכויים, 8 digits starting with 0) that corrupts what Form 101 prints. Format must be applied before setValue, not after (post-setValue formatting leaves the already-coerced number unchanged).
- `loadTenantProfile` — fetch the current tenant's profile on-demand. Returns `{ok: true, profile: {...}}` if tenantId is set, or `{ok: true, profile: null}` for super-admin sessions with no active tenant context. Used to refresh the cached profile without requiring edit or re-login.
- `listTenants` (super-admin only) — fetch all firms with their worker/client/active counts and last-save timestamp.
- `setTenantActive` / `deleteTenant` (super-admin only) — activate/deactivate/delete firms and their logins.
- `saveSchedule` — persist workers/clients/weekStart; includes optimistic concurrency control (rejects if `baseSavedAt` conflicts with server version). `clients.radius` always coerced to NUMBER (default 100m).
- `savePunch`, `updatePunch`, `deletePunch` — punch-clock entries with GPS data.
- `savePushSubscription` — web push subscription registration.
- `aiReadDoc` — server-side AI document OCR via Anthropic API (passport/Israeli ID extraction, stored in Script Properties: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` — **default model is `claude-sonnet-5`**, not the cheaper Haiku model). Document reading is critical: errors flow directly into real Form 101 tax submissions, so accuracy is more important than cost. The difference (~½¢ per scan vs Haiku) is negligible (~$1 per 100 workers). The related lightweight `aiDetectAlign` sibling below remains on Haiku. Calls the vision model with `max_tokens: 8000` and prompt-caching enabled (`anthropic-beta: prompt-caching-2024-07-31`). The limit was raised through successive iterations (800 → 1600 → 3000 → 8000) to handle real-world complexity: 800 was sufficient before the response schema added `fieldBoxes` (bounding boxes for digit field re-verification) and `children` array; real documents with address, 2–3 children, and pretty-printed JSON exceeded 800 and got truncated mid-object (breaking JSON parsing). 1600 was thought to give ample headroom, but production Israeli IDs with Hebrew text (names, addresses, children) still got truncated — Hebrew text is token-inefficient compared to Latin (Claude's tokenizer needs noticeably more tokens per Hebrew character). 3000 was also insufficient. To prevent truncation while avoiding margin loss during parsing, the prompt now explicitly instructs: "Return ONLY the JSON object, compact with no extra whitespace or line breaks between fields" (added to the system prompt). This ensures the model doesn't pretty-print the JSON with indentation/newlines even after the "no markdown" instruction. 8000 is a very large margin for a structured single-document JSON extraction (realistically in the hundreds to low thousands of tokens) while staying far below the model's real 128,000-output-token ceiling. max_tokens only caps output and doesn't force the model to spend that many, so it doesn't materially increase per-scan cost on scans that were already comfortably under the old limits. **Truncation detection:** When JSON parsing fails in the catch block, the function now checks Anthropic's `stop_reason` field: if it's `'max_tokens'`, the function returns a specific, actionable error message ("Ответ ИИ обрезан лимитом max_tokens — увеличьте лимит" / "Response truncated by max_tokens limit—increase the limit") rather than a generic parsing error. This allows operators to distinguish an actual truncation event (user-actionable: increase `max_tokens`) from JSON parsing failures caused by model/format issues. Response includes four top-level objects:
  - **`fieldBoxes`** — bounding boxes for all-digit fields (idNo, dob, expiry, passportNo — whichever apply to this document type) found on the original image exactly as provided (not on the straightened `imageAlign` version). Each field present in the response has a box: `{x0, y0, x1, y1}` where each coordinate is a fraction 0–1 of the image's width/height, representing the tight rectangle around just the printed characters (a few pixels of margin, not the field label or surrounding box). Fields omitted entirely if their extracted value was empty. Used for re-cropping and double-checking exactly those digit values, so precision matters more than for `imageAlign`.
  - **`photoBox`** (added 2026-09-21) — same coordinate space/convention as `fieldBoxes` above, but locates the person's own portrait photo printed on the document (tight around the photo itself, not its frame/border), if one is visible; omitted if no portrait photo is present. Used client-side by `cropPortraitAvatar()` (`schedule-manager.html`) to crop that region out of the scan, force it square, downsize to 160×160 and re-encode as JPEG — persisted as `w.avatarB64` on the worker record and shown in place of the colored-initials circle everywhere a worker avatar renders (see `workerAvatarInner()`). Unlike the full scan/signature sidecar (`saveWorkerAssets`, see below), this thumbnail IS stored directly in the workers JSON blob — small enough (a few KB) not to trigger the "don't bloat the sheet with base64 images" concern that keeps full-size scans out of it.
  - **`imageAlign`** — object describing how to straighten and crop the original photo: `{rotate: 0 | 90 | 180 | 270, corners: {tl, tr, br, bl}, crop: {x0, y0, x1, y1}}` where `rotate` is the clockwise degrees needed (must be exactly 0, 90, 180, or 270) to make the document upright and right-reading. **`corners`** are the document's four actual physical corners as `{tl: {x, y}, tr: {x, y}, br: {x, y}, bl: {x, y}}` — coordinates given as fractions (0–1) of the original pre-rotation image, traced even if the photo was taken at an angle (forming a skewed quadrilateral, not necessarily axis-aligned), never cutting off text/photo/edges. **`crop`** is an axis-aligned bounding box fallback covering the same area, kept only for older clients that don't use `corners`.
  - **`children`** — (Israeli IDs only) if the ספח (appendix card) with registered children is present, extracted as array of `{name, idNo, dob}` per child; empty array if absent or no children listed.
- `aiDetectAlign` — lightweight sibling of `aiReadDoc` used by the client's `autoPreAlignScan()` pre-pass: calls Anthropic vision model via a minimal prompt (`max_tokens: 200`, no prompt-caching) that returns ONLY `{rotate, corners}` (same shape as `aiReadDoc`'s `imageAlign`, no `crop` fallback), skipping field extraction entirely. Uses its own separate Script Properties configuration: `ANTHROPIC_ALIGN_MODEL` (default `claude-haiku-4-5-20251001`) — deliberately distinct from `ANTHROPIC_MODEL` used by `aiReadDoc`. The alignment task is simple (90° rotation + four corners), so cost optimization via Haiku is more important than accuracy; upgrades to the main `ANTHROPIC_MODEL` should not automatically increase the cost of this pre-pass. Exists purely so the client can auto-straighten a photo cheaply/quickly before the slower, fuller `aiReadDoc` call. Added to the `WRITE` actions list (requires `API_SECRET`) like `aiReadDoc`, since it also calls the paid Anthropic API.
- `aiVerifyField` — high-accuracy re-read of a single already-extracted digit field (idNo, dob, expiry, or passportNo), using a tightly cropped image of just that field built client-side from `aiReadDoc`'s own `fieldBoxes` and zoomed in so the model sees the same digits at much higher effective resolution than embedded in the full document photo. A wrong digit in the ID number or a date corrupts a real Form 101 submission, so this **uses the same accuracy-first `ANTHROPIC_MODEL` as `aiReadDoc`** (not the cheap Haiku align model) — deliberately not optimized for cost, with the same reasoning as `aiReadDoc` above (difference of ~½¢ per verification vs Haiku, negligible per 100 workers). Calls `max_tokens: 50` since it extracts just one field. `body.kind` selects the expected shape: `'digits9'` (Israeli ID, exactly 9 digits), `'date'` (DD/MM/YYYY or DD.MM.YYYY), or `'passportNo'` (alphanumeric, format varies by issuing country). Returns `{ok: true, value: <extracted text>}` or `{error: ...}`. Gracefully returns empty string if the field is genuinely illegible even zoomed in, rather than guessing — this prevents confidence mismatches that lead to corrupt tax submissions. Added to the `WRITE` actions list (requires `API_SECRET`) like `aiReadDoc` and `aiDetectAlign`, since it calls the paid Anthropic API. Implemented in `apps-script/Код.js` and routed via the `doPost` switch statement.
- `saveWorkerDoc` — store an assembled worker PDF (Form 101 + signature + ID scan) into Google Drive under "Schedule manager APP/<CompanyName>/Workers", idempotently named by the client-supplied `fileName` (built from worker name + doc number). Multi-tenant: files are stored in a firm-specific folder (resolved by cached Drive folder ID on the Tenants row, `driveFolderId`; falls back to name lookup with ownership tagging to prevent collisions when two firms share the same company name). Re-uploading with the same `fileName` replaces the previous file. Accepts optional `body.previousFileId` to directly trash a file by its stable ID (preferred when available, since the OCR'd name/doc-number baked into `fileName` can drift across rescans and no longer match the old file name); falls back to matching by `fileName` for callers that don't know their previous file's ID yet. **Automatic dedup on save:** extracts the document number (ID/passport number) from the new `fileName` via `extractDocNumberFromFileName()` and trashes all other files in the folder sharing the same document number, preventing rescans from piling up as duplicates even when OCR reads the name differently each time. Returns file's shareable link URL (link-access only, not publicly indexed, for privacy of ID/passport scans) and file ID. **Trashed folder recovery:** Resolves the company folder via cached `driveFolderId` first (stable ID path); if the folder is found but sitting in Drive Trash (not permanently deleted), `_companyFolder()` automatically restores it with `setTrashed(false)` instead of treating it as lost and creating a duplicate folder. This prevents orphaning of existing worker documents and ensures a firm's document history remains accessible when the folder is manually/accidentally trashed but can be recovered (only permanent delete would trigger fallback folder creation by name).
- `deleteWorkerDoc` — delete a stored worker document from Google Drive (called when a worker is deleted in the app, so removing a worker doesn't leave orphaned documents behind). Accepts `body.fileId` or `body.fileName`. Prefers a direct `fileId` lookup via `DriveApp.getFileById()`, then marks the file as trashed. Falls back to looking up the file by `fileName` inside that tenant's firm-specific "Schedule manager APP/<CompanyName>/Workers" folder, then trashes all matches (loop over iterator with `setTrashed(true)`). Returns `{ok:true}` on success, or `{error:...}` if neither `fileId` nor `fileName` provided or if a Drive operation fails. Gracefully returns success (`{ok:true}`) if the Drive folder structure doesn't exist yet (no cleanup needed).
- `saveWorkerAssets` — store raw ID/passport scan image + optional signature PNG + optional extra pages as a small private JSON sidecar file in an `Assets` subfolder of the worker's PDF folder (i.e. `Schedule manager APP/<CompanyName>/Workers/Assets`, resolved via `_workerAssetsFolder(tenantId)` — a thin wrapper around `_companyFolder(tenantId)` that gets/creates that `Assets` subfolder; never shared — nothing ever opens it directly, only `loadWorkerAssets()` below reads it). Kept in a separate subfolder from the PDFs (moved here from directly inside `Workers`) so a manager browsing Drive only sees documents meant to be opened, not internal regeneration data; `loadWorkerAssets`/`deleteWorkerDoc` read/trash by file ID regardless of folder, so this move doesn't affect already-existing sidecar files created before it. This enables a later edit (income type, marital status, address, ...) to regenerate the exact same Form-101 PDF with new values without asking the manager to re-scan the physical document. Scan/signature data is never stored in the Schedule sheet's workers JSON blob (which would bloat it with base64 images for every worker). Accepts `body.scanB64` (base64-encoded scan image, required), `body.scanMediaType` (defaults to 'image/jpeg'), `body.sigPng` (optional base64-encoded signature PNG), `body.extraPages` (optional array of `{b64,mediaType}` — extra scanned pages from a multi-file packet, e.g. an Israeli ID's ספח appendix card or a contract page, stored verbatim as `[]` if omitted; added 2026-09-21 fixing a bug where these pages only ever made it into the PDF on the very first generation right after scanning — `regenerateWorkerDoc()` had nowhere to read them back from, so any later edit that triggered auto-regeneration silently dropped them from the rebuilt PDF), `body.fileNameBase` (used to construct the sidecar filename, defaults to 'worker'), and optional `body.previousFileId` for idempotent replacement — if provided, trashes that previous file before writing the new one, preventing duplicate sidecars from piling up on regenerate. **Automatic dedup by document number (added 2026-09-21), mirroring `saveWorkerDoc`'s own dedup:** `previousFileId` only catches a rescan of the *same* worker record — two separate worker records accidentally created for the same real person (there's no duplicate-worker check on creation) each get their own `assetsFileId`, so without this, every such "duplicate worker" scan piled up its own sidecar file forever even though `saveWorkerDoc` already correctly deduped the PDF itself across worker records via the doc-number-in-filename trick. Now extracts the document number from `fileNameBase` via `extractDocNumberFromFileName()` and trashes any other file in the `Assets` folder sharing that number, the same way `saveWorkerDoc` does for the main `Workers` folder. Returns `{ok:true, id: <sidecar file ID>}` or `{error:...}`. The returned sidecar file ID is stored in the worker object as `w.assetsFileId` for later retrieval by `regenerateWorkerDoc()`.

- **Digit field verification functions (Israeli ID checksum validation):** NEW functions added to catch OCR digit misreads before they corrupt tax forms:
  - `isValidIsraeliId(id)` — pure checksum validation using Luhn-style algorithm: alternating weights 1,2,1,2,... across the 9 digits, fold any product ≥10 by subtracting 9, valid iff the sum mod 10 === 0. Returns boolean. No AI call, fast arithmetic-only validation catching most single-digit OCR misreads.
  - `cropFieldImage(b64, mediaType, box)` — extracts a tight crop from an image for a single field based on bounding-box `{x0,y0,x1,y1}` (fractions 0–1 of image dimensions). Returns `null` if box is missing/degenerate. Upscales the cropped region to at least 500px on the long edge so the zoomed-in field is clearly legible for re-verification. Used to prepare images for `verifyField()` re-reads.
  - `verifyField(b64, mediaType, box, kind)` — calls backend `aiVerifyField` action (targeted re-read of a single field using a tight crop) after cropping via `cropFieldImage()`. `kind` is `'digits9'` (Israeli ID), `'date'` (DD/MM/YYYY or DD.MM.YYYY), or `'passportNo'` (alphanumeric). Uses the same accuracy-first `ANTHROPIC_MODEL` (not cheap Haiku) because wrong digits corrupt tax submissions. Returns `{ok: true, value: <extracted>}` or `{ok:false, error:...}`. Gracefully returns empty string if illegible rather than guessing.
  - `verifyDigitFields(parsed, b64, mediaType)` — wrapper that takes the AI scan's `fieldBoxes` bounding boxes (if present) and re-verifies critical digit fields (idNo, dob, expiry for Israeli ID; passportNo for passport) by calling `verifyField()` for each field found. If a re-read comes back well-formed (correct digit count/format), replaces the original extracted value. If malformed/illegible, keeps the original value. Replaces `parsed.idNo`, `parsed.dob`, etc. in-place if the re-read is accepted. Used by both single-photo `runOcr()` and multi-file `onScanFilesSelected()` flows right after `aiReadDoc` returns.
  - `verifyIdChecksum(parsed, b64, mediaType)` — for `type==='israeli_id'` only, validates the ID number against its check digit via `isValidIsraeliId()`. - **AI document scan / Form 101 flow** (`onScanFileSelected`, `onScanFilesSelected`, `autoPreAlignScan`, `runOcr`, `renderScanQuadEditor`, `openWorkerModalFromScan`, `aiFillForm101`): photo/PDF is first turned into a plain image (`onScanFileSelected` renders a PDF's first page to canvas via pdf.js if needed). Before the full OCR call, `autoPreAlignScan(b64,mediaType)` makes a **fast, cheap, fully-automatic pre-pass**: it calls the `aiDetectAlign` backend action (small prompt, `max_tokens:200`, no prompt-caching — rotation/corners only, no field extraction), then applies the returned `rotate`/`corners` locally via `alignScanImage()` (rotate) + `warpQuadImage()` (perspective flatten) with **no user interaction** — the goal is to hand the slower `aiReadDoc` OCR call a flatter, cropped image that's easier to read accurately than a raw angled phone photo. Best-effort: any failure in `autoPreAlignScan` (network error, bad AI response, image decode failure) silently falls through to OCR-ing the original unmodified photo, so it never blocks the scan. The (now pre-straightened) image is then **sent to the AI** for OCR and its own corner detection in one call (`aiReadDoc`). That second call's `imageAlign` (with detected document corners, `imageAlign.corners`) is validated via `validQuadCorners()` and pre-filled into a **manual corner-adjustment editor** (`renderScanQuadEditor`/`initScanQuad`/`attachQuadDrag`) — used to build the final scan image embedded in the worker's PDF; the user can drag 4 circular SVG handles to refine corners if needed, or skip adjustment entirely. Corners are tracked in on-screen pixels (`window.__quadRect` with keys `tl`, `tr`, `br`, `bl`) during dragging (Pointer Events, each handle moves independently), stored as fractions relative to image dimensions. "Готово" (`confirmScanQuad`) applies a full **perspective warp** (projective homography, not just affine crop+rotate) to flatten the document quad into a rectangular image via `warpQuadImage()`, making even angled photos look scanner-flat; "Пропустить" (`skipScanQuad`) skips warp and uses the image as-is. Perspective-warp implementation uses classic homography math: `computeSquareToQuadHomography()` solves the 8-coefficient transformation from 4 point correspondences (Heckbert algorithm), `applyHomography()` applies it per pixel, and `bilinearSample()` interpolates source pixels during resampling to avoid artifacts. The warp caps output size at `MAXDIM=1568px` on the long edge — Anthropic's vision models don't benefit past this limit (internally resized), and this ceiling (raised from 1400px) better captures detail on small print (dates, 9-digit ID numbers) on worn/creased documents; the higher limit enables `verifyDigitFields()` to work reliably on poor-quality scans without sacrificing performance or cost. Helper `rotatePointFrac()` rotates corner coordinates in fraction-space to keep them in sync with image rotation. `alignScanImage(b64,mediaType,align)` is the shared canvas-based primitive for pre-warp gross orientation (rotate in 90° steps + rectangular crop, no perspective correction); affine-only, crop fractions measured against pre-rotation image. UI displays loading spinner with progress bar during OCR scan (`@keyframes spin`, `.progress-bar`). The flow uses **Anthropic Vision API** server-side (`aiReadDoc` action) — client-side OCR (Tesseract.js, MRZ parser) removed for better accuracy and lighter JS footprint. Detected corners often include perspective distortion from the photo angle; perspective warp corrects this automatically when user confirms, producing a clean rectangular scan suitable for Form 101 PDF embedding.
  - **Server-side pre-filter before `autoPreAlignScan`** (`preAlignScan()` in `schedule-manager.html`, `preprocess_scan` in `functions/main.py`): tried FIRST, before the AI-seeded `autoPreAlignScan`/`aiDetectAlign` pass described above. POSTs the raw photo to the Python Cloud Function's `preprocess_scan` endpoint, which does two things with plain OpenCV + Pillow (no AI call, no cost): (1) rejects an obviously-too-blurry photo via Laplacian-variance blur detection (`BLUR_VARIANCE_THRESHOLD=15`, calibrated against a real Israeli ID photo — see below) before any paid API call is spent reading it — the client shows a "снимите ещё раз" retake prompt and never calls `aiDetectAlign`/`aiReadDoc` at all in that case; (2) attempts to find the document's quad via classic contour detection (`cv2.findContours`+`approxPolyDP`) and perspective-warp it flat itself. If a confident quad is found (`MIN_QUAD_AREA_FRAC=0.20` of frame, convex, 4-sided), the client uses that straightened+contrast/sharpness-enhanced image directly and **skips `autoPreAlignScan`/`aiDetectAlign` entirely** — the whole point, since that Haiku call is no longer needed. If no confident quad is found, the client falls through to the unchanged `autoPreAlignScan()` AI-seeded path (still using the Pillow-enhanced image as input, so that improvement applies either way). Any network/decode failure in `preAlignScan()` itself falls through fully unchanged to `autoPreAlignScan(b64,mediaType)` on the original raw photo — same best-effort convention as the rest of this flow.
    - **Why OpenCV isn't a full replacement for `aiDetectAlign`, only a first-pass filter — confirmed empirically, not just in theory.** Built synthetic test photos (a rendered `form101_fillable.pdf` page skewed onto a background) and tested against a real Israeli ID photo before wiring this in. Findings: (1) pure `cv2.findContours` **cannot tell an upside-down document from a right-side-up one** — it found the quad's geometry perfectly in a rotate-180° test but produced a fully mirrored/upside-down result, because geometry alone has no way to know which edge is "up" without reading the content; `aiDetectAlign` exists specifically because it *does* read the content (a rough understanding of the document, not just its edges). (2) On a **low-contrast background** (light desk vs. white card), raw contour detection failed outright, locking onto a small internal box (a checkbox area) instead of the document's true outline — `MIN_QUAD_AREA_FRAC=0.20` is a direct guard against exactly that failure mode (a spuriously small "quad" can't clear a 20%-of-frame area minimum). Given both failure modes, `preprocess_scan` never attempts rotation correction at all — it only crops/deskews an already-roughly-upright photo — and always falls back to the unchanged `aiDetectAlign` path when its own confidence checks don't clear, rather than trying to replace what plain geometry structurally cannot do. Separately, `aiReadDoc`'s own `imageAlign` (used to build the *final* embedded scan image, see below) is untouched by any of this and remains the source of truth for the document's final orientation regardless of which pre-pass ran — so even a worst-case wrong OpenCV crop only risks a slightly harder read for `aiReadDoc`, not a corrupted final scan image.
    - **Latency tradeoff, accepted knowingly:** `opencv-python-headless` is a large dependency (~60-90MB) — on a cold Cloud Function instance (likely most of the time, given this app's low scan volume — Cloud Functions scale to zero after ~15min idle), `import cv2` alone can take 1-3s, making a cold-start call to `preprocess_scan` take 2-5s total versus ~100-250ms once warm. This is comparable to or slower than the `aiDetectAlign` call it replaces on a cold hit, but faster once the function instance is warm from a recent scan. Not worth paying for `min_instances` to keep it permanently warm at this app's volume — the existing "Выравниваю фото…" spinner already covers this either way.

    - **Israeli ID ספח (appendix) card continuation — order-independent (fixed bug):** the front card (dob, sex) and the ספח appendix card (address, city, children) can be selected in either order in a multi-file upload. `CORE_FIELDS=['dob','sex','address','city']` + `missingCore(p)` track whether *any* of them is still blank on `foundParsed`, not just address/city — the original version only checked address/city, so a ספח-first upload (ID's two sides as separate files, ספח happening to be selected/sorted first) set `foundParsed` from the ספח alone — which already has address+city — making the check pass immediately and never sending the actual front card through `aiReadDoc` at all: dob/sex silently stayed blank even though the front card was sitting right there in the file list, just relegated to "other pages" unread. Fixed by generalizing to `needMore=missingCore(foundParsed)`, re-checked after every subsequent page's merge (not just once), so it keeps trying later pages — regardless of which physical card came first — until every core field is filled or pages run out. Foreign passports carry every field on one page, so this never fires for that path (nothing is ever missing after the first hit). **The ספח page's own photo used to be silently discarded once its data was merged** (2026-09-21 bug: the merge branch did `continue` before reaching `otherPages.push()`, so a worker's assembled PDF never actually contained the ספח image even though its address/city/children data made it into the worker record) — fixed by always falling through to the push regardless of whether a merge happened, so the ספח image now rides along in `window.__aiPacketOtherPages` like any other extra page. **Considered and rejected: a separate ID-number cross-check warning between the front card and the ספח.** Both print the same מספר זהות, so an initial version compared the ספח's OCR'd `idNo` against `foundParsed.idNo` and warned on any mismatch. Removed per user feedback (2026-09-21): the ספח's single read never goes through the same zoomed re-verification (`verifyDigitFields`) as `foundParsed.idNo` does, so a raw mismatch is more likely a plain ספח misread than a real problem — a separate warning here would mostly cry wolf. The existing `idChecksumOk===false` warning (from `verifyIdChecksum()`, already run unconditionally on `foundParsed` before this merge loop) is the one signal actually meant to catch a wrong ID number; don't duplicate it with a second, noisier check.
    - **Worker's own mobile number:** not read from the document (no ID/passport prints it) — just the ordinary `#wPhone` field in the unified worker modal (no separate scan-panel input anymore). Printed on Form 101's page-1 "מספר טלפון נייד" box — no AcroForm field ships there either (verified the same way as the other custom boxes, via `page.get_drawings()`/`get_text("words")`; `WORKER_PHONE_RECT` in `functions/main.py`), so `worker_phone` is a new field created the same way as `employer_phone`. `aiFillForm101()`'s payload sends `workerPhone` (from `targetWorker.phone`, written by `saveWorker()`). `phone` is in `FORM101_WATCHED_FIELDS` (`saveWorker()`) so editing an existing worker's phone auto-regenerates their PDF like address/marital/etc. already did.
    - **Extra pages collected:** every remaining page (contract, extra pages, etc.) that doesn't classify as ID/passport is collected into `window.__aiPacketOtherPages` (array of `{b64,mediaType}`).
    - **Digit field re-verification:** Just like the single-photo `runOcr()` flow, the first ID/passport found has its critical digit fields re-verified via `verifyDigitFields()` if the backend `aiReadDoc` response includes `fieldBoxes` bounding boxes, immediately followed by `verifyIdChecksum()` for Israeli IDs. This zoom-in re-verification catches OCR digit misreads that could corrupt Form 101 tax submissions — equally important whether the document came from one photo or a multi-file upload.
    - **Progress & error handling:** Progress is shown as "Читаю страницу N из M…" in `#aiScanStage`; a failure on one page doesn't abort the loop (best-effort, same convention as `autoPreAlignScan`). If no page classifies as `israeli_id`/`passport`, the scan overlay shows an error with a retry button. Both `window.__aiScanImage` and `window.__aiPacketOtherPages` are reset at the very top of `onScanFilesSelected()` so state never leaks between scans, and `window.__aiPacketOtherPages` is cleared again in `aiFillForm101()`'s `finally` block after every attempt.
    - **Form 101 generation modes & multi-file assembly:** `aiFillForm101(isId, mode, workerId, btnEl)` accepts `mode='download'` (unused by the UI now — every save goes through `mode='upload'`, see the unified-modal note above) or `mode='upload'` (assemble Form 101 + signature + scanned ID image into one PDF and upload to Google Drive via `saveWorkerDoc` action). `btnEl` is optional — pass an explicit button element (or `null`) to bypass the default `event.target`-based lookup used for real button clicks. Helper `bytesToBase64(bytes)` converts large buffers to base64 in chunks to avoid stack overflow on multi-MB PDFs (common for high-res ID scans). **Multi-file packet assembly:** the old single-use "append `window.__aiScanImage` as an extra page" block was extracted into a reusable closure `appendScanPage(b64,mediaType,caption)` (fit-to-page, light frame, Latin-only caption using `stdFont` Helvetica, no Cyrillic/Hebrew support). It's called once for `window.__aiScanImage` (captioned "Document scan", unchanged behavior) and then once per entry in `window.__aiPacketOtherPages` (captioned "Document") — so a multi-file upload's contract/extra pages ride along in the final PDF exactly as uploaded, appended after the (always freshly generated) Form 101 pages.
  - **Rescan deduplication (previousFileId strategy):** When uploading in `mode='upload'`, the function resolves the target worker *before* uploading so it can pass `previousFileId` to the backend's `saveWorkerDoc` action. The function resolves the worker ID in this order: (1) explicit `workerId` parameter (passed by `saveWorker()`/`regenerateWorkerDoc()`), or (2) `window.__aiRescanWorkerId` global flag (set by a rescan flow to indicate this upload is replacing a previously-uploaded document). The resolved worker's `docFileId` (if it exists) is sent as `previousFileId` — this lets the backend trash the exact old file by stable ID, rather than relying on the OCR'd filename which can drift between scans. After successful upload, `window.__aiRescanWorkerId` is cleared. This pattern supports rescans: a rescan of an existing worker can set `window.__aiRescanWorkerId=workerId` before calling `aiFillForm101`, ensuring the old PDF is replaced (not duplicated) in Google Drive even if the OCR'd name or document number changed between scans. Fresh scans from the main Workers page "Scan passport" button explicitly clear `window.__aiRescanWorkerId=null` at entry (inline in the button's `onclick` handler) to prevent state leakage from a previous incomplete rescan flow and ensure the subsequent scan creates a new worker, not an overwrite.
  - **Error handling and failure visibility:** `aiFillForm101(isId, mode, workerId, btnEl)` now returns a **boolean** result: `true` on successful upload or download, `false` on any failure (network error, PDF generation error, etc.). On failure when `mode='upload'` and a worker is resolved, the function sets `targetWorker.docUploadFailed=true` and calls `autoSave()` + `render()` + `renderWorkersPage()` to immediately persist the flag and display the updated UI. This flag enables the manager to see a "no document" badge on the worker's card/row, making silent background failures visible without relying solely on a toast message that's easy to miss (especially on mobile where connection issues are most common). On success, the flag is reset to `w.docUploadFailed=false`. **Attended vs. unattended uploads:** User-initiated uploads (clicking the "Загрузить" button directly) are *attended* — the user sees the modal, watches the upload, and the toast feedback is on-screen and noticed. Automatic uploads that run in the background after `saveWorker()` creates a new worker from a scan are *unattended* — nobody is actively watching, so the single toast can easily be missed, especially on a flaky connection. The unattended path uses `autoUploadWithRetry(isId, workerId)` (see below) to give transient failures a second chance.
  - **Automatic upload retry for background uploads (attended via modal overlay):** `autoUploadWithRetry(isId, workerId)` is an `async` helper function called by `saveWorker()` when a worker is first created from a scan with `window.__aiPendingWorkerUpload` set. It calls `aiFillForm101(isId, 'upload', workerId, null)` once; if that fails (returns `false`), it waits 1500ms and tries again automatically before giving up. The retry is designed to handle transient CDN hiccups (e.g., a temporary network flake or pdf-lib/fontkit timeout while loading from a CDN during a mobile connection) without requiring user intervention. The function is `await`-ed by `saveWorker()` with `showWorkerUploadingOverlay()` keeping the modal open and focused on upload state — the manager is explicitly shown the spinner until the retry loop finishes. If both attempts fail, the worker retains the `docUploadFailed=true` flag (set by `aiFillForm101`'s catch block), which renders the "no document" badge for the manager to notice and retry manually via the "Пересканировать" rescan button (a user-attended flow). This two-tier strategy (automatic retry for transient issues, manual fallback for persistent problems) reduces spurious "upload failed" notifications while catching real issues that need attention.
  - **Scan results normalization:** After AI extraction, child-name fields are normalized via `_nrm(s)` — collapses multiple spaces, trims whitespace, ensuring clean data in `window.__aiScanChildren` array. This array is populated from Israeli ID scans (if the ID has registered children in its ספח appendix) and displayed in the Form 101 UI.
  - **Form 101 pre-fill UI:** After scanning, users set optional fields and optional signature before PDF generation:
    - **For Israeli ID:** `aiIdWork` (date started), `aiIdFund` (health fund), `aiIdMarital` (marital status) — populate the corresponding PDF fields. Includes signature pad placeholder.
    - **For foreign passport:** `aiPpWork` (date started), `aiPpFund` (health fund) — populate the corresponding PDF fields. Includes signature pad placeholder.
    Each scan path is independent; user customizes before generating the PDF.
    - **Firm profile warnings in Form 101 UI:** `firmProfileWarnHtml()` is called in both the Israeli ID and foreign passport Form 101 sections (after the "Форма 101" header, before the pre-fill input fields) to display any firm profile completeness warnings. The warning prompts users to complete required firm profile fields (companyName, deductionsFileNumber, phone, street, city) before generating forms. Rendered in-place via `refreshFirmProfileWarnings()` without a full page re-render, allowing instant clearing when the user saves their profile edits. Additionally, `aiFillForm101()`'s employer-details block records `firmProfileMissing()` into a function-scoped `firmMissing` array; if it's non-empty and the PDF was produced successfully, the end of the `try` schedules a warning toast naming the blank fields, 2600ms out so it doesn't overwrite the success toast's own 2500ms. It fires on every generation path (download, upload, and the background `saveWorker()` upload) — the background path is the one where the inline panel warning isn't on screen at all. Nothing is shown when generation throws, since the toast sits inside the `try`, not the `finally`.
  - **Form 101 PDF generation (server-side):** `functions/main.py` (Python + PyMuPDF, Firebase Cloud Function `fill_form_101`) builds the filled PDF now — `aiFillForm101()` in `schedule-manager.html` only assembles a JSON payload (surname/given/dob/sex/no/isIsraeli/address/city/marital/workStart/healthFund/incomeType/otherIncomeType/children/employer profile/signature PNG base64/extra scan pages) and POSTs it to `FORM101_FN_URL`, getting back `{pdfBase64, fileName}`. Everything else — the Apps Script Drive upload (`saveWorkerDoc`), the download-blob trigger, the `targetWorker` write-back, `regenerateWorkerDoc()`/`regenerateAllWorkerDocs()`, the AI scan/OCR flow — is unchanged; only the "turn values into PDF bytes" step moved. See `form101-field-map.md` for the field-by-field rect/label map `functions/main.py` fills against.
    - **Why this moved off the client:** the previous client-side pdf-lib implementation had a confirmed bug — its own appearance-stream generator silently drops a glyph of multi-word RTL (Hebrew) text (e.g. `employer_name` "אודינסון בע"מ" rendered missing its leading א). pdf-lib's own generation was worked around at the time (blank the widget's appearance, redraw the text by hand); moving to PyMuPDF removes the underlying bug rather than working around it.
    - **PyMuPDF has no RTL/BiDi shaping of its own either** — confirmed empirically: `page.insert_text()` draws a raw Hebrew string's codepoints left-to-right in string order, which reads fully mirrored (both word order and each word's own letter order) for *any* Hebrew value, not just multi-word ones like pdf-lib's bug. Every Hebrew-capable field is therefore unconditionally corrected with `bidi.algorithm.get_display()` (the `python-bidi` package — handles mixed Hebrew+digit runs correctly, e.g. a street number inside a Hebrew address stays in reading order) before being drawn. This is a stricter rule than the old JS code's (which only redrew *multi-word* values, since pdf-lib's own bug only hit those).
    - **Real AcroForm fields, not flattened text — same technique as before, ported.** Every field (existing template fields and the ones the template ships no widget for — `tax_year_box`, `id_box`, `work_start_date`, `employer_*`, `children_*_N`) stays a real, independently-editable form field. For Hebrew-capable fields, `Form101Builder` still generates the field's own appearance first (so the field is genuinely fillable/editable in Acrobat) and then blanks it and draws the bidi-corrected text by hand on the page — see `_blank_appearance()`/`_draw_rtl_text()` in `functions/main.py`, the direct Python port of the old `setH()`/`addNewHebrewField()` blank-and-redraw trick. Comb (digit) fields don't need the redraw — LTR digit runs render correctly through PyMuPDF's own generated appearance, same as pdf-lib's `setComb()`/`addNewCombField()` never needed it either.
    - **Coordinate system:** the rects in `functions/main.py` are copied verbatim from the old pdf-lib code's PDF-native bottom-left-origin coordinates, then converted to PyMuPDF's top-left-origin ones via `pdf_rect()`. One exception: `CHILD_ROW_Y` is used as top-origin directly without conversion — a quirk of how those values were originally derived in the pdf-lib version (they already represented top-origin row boundaries once run through that code's own `pageH - CHILD_ROW_Y[i+1]` math), preserved rather than re-derived.
    - **Checkbox marks:** same blue-checkmark-instead-of-template-X approach as before (`Form101Builder.check()`), including the page-1-vs-page-2 nudge distinction (`resident_h` is the one page-2 checkbox) — ported 1:1 from the old `chk()`/`pageForWidget()`/`NUDGE`/`PAGE1_EXTRA_Y` logic.
    - **New-widget xref gotcha:** a `pymupdf.Widget()` just passed to `page.add_widget()` keeps `xref==0` on that same Python object — any further xref-level operation (blanking its appearance) needs the "live" Widget PyMuPDF hands back from re-reading the page's own widget list (`Form101Builder._refetch()`). Silent no-op, not an error, if you skip this and try to use the original object's `.xref`.
    - **`functions/venv`:** the Firebase CLI's Python deploy path expects a pre-built virtualenv at `functions/venv` (`python -m venv venv` + `pip install -r requirements.txt` inside `functions/`) — it does not create one itself, and `firebase deploy --only functions` fails with `spawn ".../venv/Scripts/activate.bat" ENOENT` without it. Gitignored; rebuild locally before deploying from a fresh clone.
    - **`firebase.json`'s hosting `ignore` list includes `functions/**`** — without it, `firebase deploy --only hosting` sweeps the entire `functions/venv` (thousands of files) into the public hosting bucket. Found and fixed once already; don't drop that ignore entry.

### worker-punch.html

- Reads a per-worker `token` from the URL (`URL_TOKEN`) to jump straight to that worker's punch screen; without a token it shows a worker picker (`renderWorkerGrid`).
- `getLastEntry(log, wid)` returns the most recent punch entry for a worker **across all days** (not just today). This determines whether to show "Clock IN" or "Clock OUT" in the UI, and powers the "In since" / "Last: X (out)" status in the worker grid.
- `openHistory()`'s per-day hour totals pair punches into shifts chronologically **before** grouping by date (mirroring `groupPunchesIntoShifts` in schedule-manager.html — sorts the worker's whole log, opens a shift bucket on each `in`, closes it on the next `out`, tags the bucket with its *opening* punch's date), then groups those shift buckets by date for display. Grouping by each entry's own calendar day first (the previous approach) split an overnight IN→OUT pair into two unpaired halves — the IN alone on day N, the OUT alone on day N+1 — so the hours silently disappeared from the worker's own history even though they were correctly counted in the manager's payroll view. worker-punch.html doesn't import `groupPunchesIntoShifts` itself (per the file's no-shared-build convention below); this is its own from-scratch port of the same algorithm and must be kept in sync with it the same way `esc()`/`GS_URL` are.
- GPS anti-spoofing lives in `analyseGps`/`getLocation`: flags zero/low accuracy, impossibly fast movement between two readings (`haversine` distance ÷ time), suspicious device speed, and instant geolocation responses (`GPS_REQUEST_MS`) as signs of a mocked location, before allowing a punch within `SITE.radius` of the client site.
- Offline-safe punches: `doPunch()` always writes to `localStorage` (`punchLog`) and also queues to `punchQueue` (`getQueue`/`saveQueue`/`queueEntry`) when the Sheets `savePunch` call fails, for later resync.
- `updateScheduleManager` reaches into the *same-origin* `schedMgr_v1` localStorage key to reflect a punch back into the manager app's cached schedule — this only works when both apps share local storage (i.e. same browser/device), it's not a sync mechanism across devices.

### Shared conventions across both files

- No modules/imports — everything is global functions/consts inside one inline `<script>` per file. When adding functionality, follow this style rather than introducing bundling.
- **XSS protection (CRITICAL):** All user-supplied text is wrapped in `esc()` — a helper that HTML-escapes `&<>"'` to prevent injection. Use it on every `${...}` expression inside template strings building HTML from data. The `esc()` function is the single source of truth for HTML-safe interpolation (defined after `uid()`). This is a foundational security requirement. Both files have the same `esc()` definition and it must be kept in sync.
- Both files duplicate constants and helpers: `GS_URL`/`API_SECRET`, `reportError`, `showToast`, `getPunchLog`/`savePunchLog`, `urlB64ToUint8` (`worker-punch.html` has `urlB64ToUint8WP`), `esc()` function, and data analysis functions like `groupPunchesIntoShifts` and `analyzeDayPunches`. This duplication is intentional (no shared build). A fix in one file (API URL rotation, `esc()` improvement, payroll logic) must be mirrored in the other to avoid drift.
- Push notifications: both files subscribe via `savePushSubscription` action; `service-worker.js` handles `push` events and `notificationclick`.
- **Auto-deploy on commit:** `.claude/settings.json` runs a `PostToolUse` hook on `Write|Edit|NotebookEdit` that stages, commits (with co-author trailer), and pushes to `origin/HEAD` automatically after every file change made by Claude Code. Each push to `origin/main` triggers GitHub Actions deploy workflows (no manual `firebase deploy` or `clasp` commands needed).

## Troubleshooting

### A tenant's phone / deductions file number prints without its leading zero on Form 101

`createUser`/`updateTenant` (`google-apps-script.js`/`apps-script/Код.js`) both correctly guard against Google Sheets auto-coercing a digit string to a number (which drops a leading zero) via `range.setNumberFormat('@')` **before** `setValue()` — this protection works and is not the bug. What can still be wrong is **pre-existing data** written before this protection existed, or via a path that doesn't use it (e.g. `migrateToMultiTenant()`'s initial tenant row) — that phone/deductions cell is already stored as a plain Sheets number, permanently missing its leading zero, and stays that way until something rewrites it. Fix: open Super-admin → Фирмы → edit (pencil) that firm and re-save the phone/deductions field through the normal form — `updateTenant`'s protected write path fixes the stored value going forward (verified live for the Odinson tenant, whose phone had exactly this problem from its 2026-09-18 migration).

### "Deploy Cloud Functions" CI fails with "Missing permissions required for functions deploy"

Failure looks like:
```
Error: Missing permissions required for functions deploy. You must have permission
iam.serviceAccounts.ActAs on service account schedule-odinson@appspot.gserviceaccount.com.
```

Confirmed live on the workflow's first-ever run (2026-09-21, manually triggered via `workflow_dispatch` right after `deploy-functions.yml` was merged — see its entry above). Cause: the `FIREBASE_SERVICE_ACCOUNT` secret was provisioned only for Hosting deploys (`deploy.yml`'s `FirebaseExtended/action-hosting-deploy@v0`) and was never granted the **Service Account User** role (`roles/iam.serviceAccountUser`) on `schedule-odinson@appspot.gserviceaccount.com` — the default runtime identity 2nd-gen Cloud Functions deploy under, which is a separate, narrower grant than general project IAM roles.

Fix (GCP Console, needs a human with project IAM-admin rights — cannot be done via `gh`/CLI from this repo): go to IAM & Admin → Service Accounts → `schedule-odinson@appspot.gserviceaccount.com` → **Permissions** tab → **Grant Access** → add the identity behind the `FIREBASE_SERVICE_ACCOUNT` secret (its `client_email` field) → role **Service Account User**. This is *not* the same as adding a role on the project's main IAM page — it must be granted directly on that specific service account's own permissions tab, since `iam.serviceAccounts.ActAs` is a per-resource grant. After granting, re-run via `gh workflow run "Deploy Cloud Functions" --ref main` (or wait for the next push touching `functions/**`) to confirm.

**This is not a one-time fix — it recurs per runtime service account.** Confirmed on the 3rd real run (2026-09-21): after granting Service Account User on `schedule-odinson@appspot.gserviceaccount.com` and separately granting project-level roles (Cloud Functions Admin, Service Usage Consumer, Cloud Build Editor, Artifact Registry Writer, Cloud Run Admin, Eventarc Event Receiver — needed to get past successive "API not enabled"/403 errors during the deploy's early steps), the deploy got much further (source uploaded, function update attempted) but failed again with the *same* `iam.serviceaccounts.actAs` error against a *different* service account: `<PROJECT_NUMBER>-compute@developer.gserviceaccount.com` (the **Compute Engine default service account** — this is the actual runtime identity 2nd-gen Cloud Functions run under by default, since they're built on Cloud Run under the hood; it's a different account from the App Engine default one the first error named). Fix is the same pattern, repeated: Service Accounts → `<PROJECT_NUMBER>-compute@developer.gserviceaccount.com` → Permissions → Grant Access → same `FIREBASE_SERVICE_ACCOUNT` identity → **Service Account User**. If a *third* distinct service account shows up in a future `actAs` error, grant it the same way — this is a known repeating pattern for first-time 2nd-gen Functions deploy setups, not a sign something is configured wrong.

The workflow's `firebase deploy` command also now passes `--force` (added alongside this note) to auto-accept the Artifact Registry image cleanup-policy prompt firebase-tools otherwise fails on non-interactively (`Error: Functions successfully deployed but could not set up cleanup policy...` — cosmetic/orthogonal to the actAs errors above, but would have been the next failure once those are fixed).

### "Deploy to Apps Script" CI fails with `invalid_grant` / `invalid_rapt`

Failure looks like:
```
"error":"invalid_grant","error_description":"reauth related error (invalid_rapt)"
```

Cause: this is a Google Workspace account (`stas@odinson.ltd`), and Workspace periodically forces OAuth re-authentication for the Apps Script scopes `clasp` uses. That invalidates the refresh token stored in the `CLASP_CREDENTIALS` GitHub secret. The re-auth step is a real Google browser login — it cannot be scripted/automated away.

Fix: run `scripts/refresh-clasp-login.sh` on a machine with a browser (not in CI). It logs in via the dedicated Web OAuth client at `H:\Tokens\Google api.json` (Cloud Console project `schedule-manager-498317`, redirect URI `http://localhost:8085`, already registered in Cloud Console — no need to touch the console again unless that client is deleted/recreated), pushes the fresh token to the `CLASP_CREDENTIALS` secret via `gh secret set`, then re-triggers the deploy via `gh workflow run "Deploy to Apps Script"` (`workflow_dispatch` trigger added to `deploy-apps-script.yml` for this purpose).

Note: `clasp login --creds` requires a `redirect_uris` array *inside* the creds JSON itself (not just registered in Cloud Console) or it fails immediately with "Invalid redirect URL" before even opening a browser.

**Auto-notification:** `deploy-apps-script.yml` itself detects this failure — if the `clasp push`/`clasp deploy` step fails, a step opens (or comments on an existing) GitHub Issue titled "Apps Script deploy failing — clasp token needs refresh", pointing straight at `scripts/refresh-clasp-login.sh`. You don't need to notice the red X in Actions; the Issue notification carries the fix.
