# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served as static files from Firebase Hosting. There is no build step, no bundler, no package.json, and no test suite — the two pages are self-contained HTML files with inline `<style>` and `<script>`.

- `schedule-manager.html` — the manager/admin app (shifts, workers, clients, payroll, exports). RTL, Hebrew (`lang="he"`), ~3200 lines.
- `worker-punch.html` — the worker-facing clock-in/out app, opened via a per-worker tokenized link. ~1000 lines.
- `service-worker.js` — PWA offline shell (network-first, cache fallback).
- `manifest.json` / `manifest-punch.json` — separate installable-PWA manifests for the two apps.
- `google-apps-script.js` — the backend Apps Script source code (backed by Google Sheets database). Deployed separately to `script.google.com` but tracked here for reference/documentation.
- `apps-script/appsscript.json` — Google Apps Script project configuration (timezone, runtime version, web app access rules, OAuth scopes). Declares required OAuth scopes: `spreadsheets` (Sheets read/write), `script.external_request` (HTTP calls to Anthropic API), `drive` (storing worker PDFs and accessing Google Drive). Configures the Apps Script project deployed to `script.google.com`.
- `apps-script/.clasp.json` — Google Apps Script CLI (clasp) configuration linking the local source to the deployed project via `scriptId`.
- `form101_fillable.pdf` — Israeli tax form template filled in-app via pdf-lib with fontkit support for Hebrew. See AI/document-scan flow below.
- `heebo-hebrew.ttf` — Heebo Hebrew+Latin TTF font subset (OFL licensed, bundled same-origin). Required for proper Hebrew glyph rendering in Form 101 PDF filling when embedding custom fonts via fontkit; loaded via `_loadHeeboFont()` (offline-safe, cache-first).

## Commands

There is no npm/build/lint/test tooling. Development is edit-the-HTML-and-reload.

- Local preview: `firebase emulators:start --only hosting` (uses `firebase.json` rewrites), or just open the HTML files directly in a browser.
- Deploy: Push to `origin/main`; GitHub Actions workflows automatically deploy both static hosting and backend on every commit:
  - `.github/workflows/deploy.yml` — deploys `schedule-manager.html`, `worker-punch.html`, and supporting files to Firebase Hosting (project alias `schedule-odinson`, see `.firebaserc`). **No manual `firebase deploy` step is used** — a push to main is what triggers the deploy.
  - `.github/workflows/deploy-apps-script.yml` — deploys Google Apps Script source (anything in `apps-script/`) via `clasp push --force` and `clasp deploy` to the configured Apps Script project (requires `CLASP_CREDENTIALS` and `CLASP_DEPLOYMENT_ID` GitHub secrets).
- Routing: `firebase.json` rewrites `/` → `schedule-manager.html` and `/punch` → `worker-punch.html`.

When bumping the service worker's cache (`CACHE` constant in `service-worker.js`, currently `schedule-mgr-v3`), increment the version string (e.g. `v3` → `v4`) or clients will keep serving stale cached HTML after deploy. PostToolUse hook auto-commits and pushes to main on every file edit (see `.claude/settings.json` for the hook configuration).

## Architecture

### Backend: Google Apps Script

Both HTML files talk to the **same** Google Apps Script Web App endpoint (`GS_URL`, a `script.google.com/macros/.../exec` URL hardcoded near the top of the `<script>` block in each file), authenticated with a hardcoded shared secret (`API_SECRET` = `'odinson-7Kq2x9'`). The Apps Script project (backed by a Google Sheet) is the actual database. Source code is in `apps-script/` (tracked here and auto-deployed via GitHub Actions when pushed to `main`). Configuration is in `apps-script/appsscript.json` (project settings: timezone, runtime, web app access). The project ID in `apps-script/.clasp.json` links the local source to the deployed Apps Script via clasp. Requests are plain `fetch()` calls with an `action` field selecting the server-side operation:

**GET endpoints:**
- `loadSchedule` — fetch workers/clients/weekStart/savedAt.
- `loadPunchLog` — fetch punch entries (with optional worker/date/type filters).
- `calcSalary` — compute daily/worker hours from punch log.

**POST endpoints (write actions, require `API_SECRET`):**
- `saveSchedule` — persist workers/clients/weekStart; includes optimistic concurrency control (rejects if `baseSavedAt` conflicts with server version). `clients.radius` always coerced to NUMBER (default 100m).
- `savePunch`, `updatePunch`, `deletePunch` — punch-clock entries with GPS data.
- `savePushSubscription` — web push subscription registration.
- `aiReadDoc` — server-side AI document OCR via Anthropic API (passport/Israeli ID extraction, stored in Script Properties: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`). Calls Anthropic's vision model with `max_tokens: 800` and prompt-caching enabled (`anthropic-beta: prompt-caching-2024-07-31`). Response includes an `imageAlign` object (for both document types) describing how to straighten and crop the original photo: `{rotate: 0 | 90 | 180 | 270, crop: {x0, y0, x1, y1}}` where `rotate` is the clockwise degrees needed (must be exactly 0, 90, 180, or 270) to make the document upright and right-reading, and `crop` is the document's tight bounding box as fractions of the original (pre-rotation) image (each value 0–1, excluding background/hand/wallet but never cutting off text/photo/edges). For Israeli IDs, also includes extraction of registered children from the ספח (appendix card) if present, returned as `children` array with each child's name, ID number, and DOB.
- `saveWorkerDoc` — store an assembled worker PDF (Form 101 + signature + ID scan) into Google Drive under "Schedule manager APP/Workers", idempotently named by the client-supplied `fileName` (built from worker name + doc number). Re-uploading with the same `fileName` replaces the previous file. Accepts optional `body.previousFileId` to directly trash a file by its stable ID (preferred when available, since the OCR'd name/doc-number baked into `fileName` can drift across rescans and no longer match the old file name); falls back to matching by `fileName` for callers that don't know their previous file's ID yet. Returns file's shareable link URL (link-access only, not publicly indexed, for privacy of ID/passport scans) and file ID.
- `deleteWorkerDoc` — delete a stored worker document from Google Drive (called when a worker is deleted in the app, so removing a worker doesn't leave orphaned documents behind). Accepts `body.fileId` or `body.fileName`. Prefers a direct `fileId` lookup via `DriveApp.getFileById()`, then marks the file as trashed. Falls back to looking up the file by `fileName` inside the "Schedule manager APP/Workers" folder (the same folder used by `saveWorkerDoc`), then trashes all matches (loop over iterator with `setTrashed(true)`). Returns `{ok:true}` on success, or `{error:...}` if neither `fileId` nor `fileName` provided or if a Drive operation fails. Gracefully returns success (`{ok:true}`) if the Drive folder structure doesn't exist yet (no cleanup needed).
- `logError` — client error telemetry.

**Backend sheets:**
- `Schedule` (key/value pairs: workers JSON, clients JSON, weekStart, savedAt).
- `PunchLog` (append-only columns: ID, WorkerID, Worker, Type, Time, Date, Timestamp, Site, Distance(m), GPS Accuracy(m), GPS Suspicious, GPS Warnings, Notes, EditedAt, ClientID; see migration notes below).
- `Salary` (computed dynamically from PunchLog).
- `Clients` (human-readable tab: Name, Address, Lat, Lng, Radius(m), Notes).
- `PushSubscriptions` (web push endpoints).
- `Backups` (daily snapshot for disaster recovery).
- `Errors` (client error log, last 500 entries).

**Backend utilities:**
- `saveWorkerDoc(body)` — store worker PDF docs to Google Drive. Decodes `body.fileBase64` to bytes, saves into Drive under "Schedule manager APP/Workers" folder with `body.fileName`. If `body.previousFileId` is provided, trashes that file by ID first (stable even when OCR'd names drift across rescans); otherwise, falls back to trashing any existing file matching `body.fileName`. Re-uploading with the same `fileName` replaces the file (idempotent). Sets `ANYONE_WITH_LINK` VIEW access so manager can open/download without a Google account sign-in. Returns `{ok:true, url, id}` or error. Called after client-side Form 101 PDF generation + signature capture.
- `backupNow()` / `setupDailyBackup()` — daily 2am backup of Schedule to Backups sheet.
- `restoreBackupRow(rowNum)` — manual restore from Backups.
- `checkShiftReminders()` / `setupHourlyTrigger()` — hourly check for upcoming shifts, send push notifications.
- `normalizeClients(clients)` — enforce numeric radius on load/save.
- `migrateAddClientIdColumn()` — one-time migration to add the `ClientID` column to an existing PunchLog sheet (run once from the Apps Script editor after deploying the version that includes this column; safely handles sheets where the column already exists).
- `fixPunchLogHeaderDrift()` — one-time fix for sheets where an earlier code version wrote GPS Suspicious/GPS Warnings data to columns K:L but the row-1 headers still showed the old 'Notes'/'EditedAt' labels (causing loadPunchLog to silently skip those fields). Rewrites headers K1:N1 only, never touches data rows. Safe to run more than once; detects if headers are already correct.
- `fixGpsAccuracyHeaderLabel()` — one-time fix: rewrites column J's header from the legacy 'QR Verified' label (from before GPS-only verification) to 'GPS Accuracy(m)' so that `loadPunchLog()`'s name-based lookup matches the positionally-written GPS accuracy data. Rewrites J1 only, never touches data rows. Safe to run more than once; detects if header is already correct.
- `backfillOfficeAClientId()` — one-time backfill for historical punches: sets `clientId='c1'` on punches where `site='Office A'` and `clientId` is empty, recovering the client link for punches recorded before the clientId field existed and before client c1 was renamed. Only updates rows with no clientId, so safe to run more than once; never overwrites an existing (possibly correctly-chosen) clientId.
- `formatPunchLogSheet()` — visual formatting pass for the PunchLog sheet: bolds/colors the header row, freezes it, and auto-fits column widths to match the style already used in Clients/Backups/Errors tabs. Formatting only (never touches data). Safe to run more than once; worth re-running after adding a column since new header cells don't inherit existing bold/background styling.

The service worker explicitly never intercepts requests to `script.google.com` (`service-worker.js:31`) — the API always goes straight to network.

### Client-side state & persistence (schedule-manager.html)

- In-memory globals: `workers`, `clients`, `weekStart`, plus UI state like `selectedClientId`, `editingWorkerIdx`. No framework — state mutation is followed by a manual `render()` call.
- `render()` fans out to per-section renderers: `renderStats`, `renderGanttHeader`/`renderGanttBody` (the schedule grid), `renderWorkerList`, `renderWorkersPage`, `renderClientsPage`, `renderDashboard`, `renderSalary`, `renderAdmin`, `renderClientLogs`.
- **Google Sheets is the source of truth; `localStorage` (`schedMgr_v1` / `schedMgr_v1_bak`) is only a cache/offline fallback.** `loadData()` renders cached data instantly, then overwrites with the Sheets response. `autoSave()` debounces writes (800ms), writes to `localStorage` first, then pushes to Sheets via `gsSave`; it also has an "empty state" guard that refuses to persist an accidentally-cleared `workers`/`clients` array over existing cached data.
- Each worker has a generated `token` (`genToken()`) used to build their personal punch-clock link (`buildPunchLink(w)`) — this token is the `t=` query param `worker-punch.html` reads to skip worker selection.
- **XSS Protection (CRITICAL):** `esc(s)` function HTML-escapes user-supplied text (`&<>"'`) to prevent injection. Every `${...}` interpolation of data into HTML templates **must** call `esc()`. This is foundational security — defined early in the script after `uid()` (line 678) and used consistently throughout all render functions (worker names, client names, addresses, phone numbers, notes, punch sites, contacts, photo URLs, etc.). Any new feature interpolating user text must apply `esc()` to the value. Both `schedule-manager.html` and `worker-punch.html` have identical `esc()` definitions that must stay in sync when either is updated.
- **Payroll math (canonical overnight-shift logic):** Core functions form the foundation:
  - `analyzeDayPunches(entries, date)` pairs a single calendar day's IN/OUT punches chronologically and sums hours, flagging anomalies (double-in, out-without-in, >12h shift, open shifts, etc.). Returns `{hours, warnings}`. Used for per-day analysis and anomaly detection in the admin dashboard.
  - `groupPunchesIntoShifts(entries)` pairs a worker's *entire punch history* chronologically into shift-buckets **independent of calendar-day boundaries** — an IN before midnight and OUT after midnight stay in one bucket (tagged by opening punch date) instead of splitting into two half-shifts that `analyzeDayPunches` can't pair (whose hours would otherwise vanish from payroll). **Critical for overnight-shift accuracy.** Returns buckets `{date, entries}` with the date of the IN punch. **This is the canonical function used in all three payroll contexts:** salary table render, salary CSV export, and punch log analysis. Never duplicate its logic. Ensures chronological pairing across all punches (not just today's).
  - `shiftPay(hours, w, isSat)` calculates total pay for one shift: **default applies `israeliDayPay` law tiers** (8h regular at ×1.0, next 2h at ×1.25, rest at ×1.5; Saturday ×1.5/×1.75/×2.0), but **respects per-worker `otRate` and `shabbatRate` overrides** (single flat ₪/h rate replacing law tiers for all OT/Shabbat hours). Unifies payroll: manager's salary table, CSV exports, all route through `shiftPay`. Never replicate this logic.
  - `israeliDayPay(hours, rate, isSat)` implements the law tiers; `wRegRate(w)`, `wOtRate(w)`, `wShabRate(w)` fetch effective rates (base or per-worker overrides); `PAY_RULES` constants encode thresholds (regularMax 8h, ot1Span 2h, otMult 1.25, shabbatMult 1.5).
  - Dashboard salary table (`renderSalary`) and CSV export (`exportSalaryCSV`) use `groupPunchesIntoShifts` → `analyzeDayPunches` → `shiftPay` to compute totals. Ensures overnight shifts never split across midnight, hours are counted once, and pay is correct.
  - Israeli labour law encoding: domain-specific; do not simplify without labour-law expertise. The `shiftPay()` function is the single source of truth for payroll calculations (all three contexts call it).
- **Punch entry `clientId` tracking:** Punch entries include a `clientId` field (client ID UUID, not just name), enabling geofence/client-specific analytics and historical accuracy even when client names/worker assignments change. When editing a punch, the site select stores the client's ID (or `__custom__` sentinel for unmapped legacy sites), preserving the association. Three helper functions work together:
  - `punchSite(e)` — resolves the site name to display: prefers punch's own `clientId` (looks up current client name), falls back to stored site name string (for legacy entries without clientId), then worker's current client assignment. Used for UI display (dashboard, admin table, client logs). Always escaped via `esc()` when interpolated into HTML.
  - `punchClientObject(e)` — retrieves the client's object/branch name as *recorded at punch time*, preferring punch `clientId` over worker's current assignment — critical for payroll accuracy when worker-client relationships change. Used in salary CSV export to show which object was staffed on punch date.
  - `workerClientName(workerId)` — falls back helper: returns worker's current client assignment (for punches recorded before `clientId` existed).
  - Edit flow (`editPunchEntry`/`savePunchEntry`): site select now stores `clientId` values; if `__custom__` is chosen, the stored site name string is preserved (legacy behavior); clearing the site clears `clientId`. Manual punch creation (`saveManualPunch`) records the punch with `clientId` from the selected client.
- **Admin punch log filtering and rendering:** Worker filter now uses `workerId` (matched against punch `workerId`, not `workerName`), de-duplicating by ID so duplicate names don't collapse. Critical when two workers share the same name. Rendering filter dropdowns: build a `Map` of `workerId → workerName` from the punch log, sort by name, so each worker ID appears once with correct current name. Client filter is keyed by `clientId`, enabling filtering by client assignment at punch-record time (even if assignments changed since). **Responsive design:** Punch table is wrapped in a horizontal scroll container (`<div style="overflow-x:auto;-webkit-overflow-scrolling:touch">`), with table `min-width:760px` to ensure columns don't collapse on mobile. Worker name cells, client badge pills, and date/site columns all use `white-space:nowrap` to prevent text wrapping and keep names intact. Client badges include `white-space:nowrap` to prevent pill breakup. This ensures the punch log remains readable on narrow screens without hiding columns.
- Exports: `exportExcel` (SheetJS/xlsx, loaded from CDN), `exportPDF`, `exportJSON`, `exportSalaryCSV`, `exportPunchCSV`. Salary export (`exportSalaryCSV`) now uses `groupPunchesIntoShifts()` to pair overnight shifts correctly before calculating hours and pay per shift.
- Admin panel: `renderAdmin()` and `renderClientLogs()` display punch log with filtering by workerId/clientId/date/type. Edit/delete operations on punches (`editPunchEntry`, `savePunchEntry`, `deletePunchEntry`) now store `clientId` alongside punch data for historical client link preservation.
- **Worker document storage:** When editing a worker, the worker modal displays a "Документы (Форма 101 + скан)" section with controls for scanning/uploading and managing documents. A download link to the stored PDF appears only if a document has been previously uploaded via Form 101 generation (using `mode='upload'`); a timestamp shows when it was saved (`docSavedAt`). Below the optional download link is a "Пересканировать/Сканировать документ" button (`rescanWorkerDoc(workerId)`) that initiates a new scan — the button text is "Пересканировать" (rescan) if a document already exists, or "Сканировать документ" (scan) if none exists yet. Fields `w.docUrl` (shareable Google Drive link), `w.docSavedAt` (ISO timestamp), and `w.docFileId` (Drive file ID) are populated by the backend's `saveWorkerDoc` action response and persisted in the workers JSON. This allows the manager to retrieve assembled Form 101 + signature + ID scan PDFs for each worker from prior uploads.
  - **Cleanup on worker deletion:** `deleteWorker(wi)` resolves the worker's Drive file ID (`w.docFileId`, falling back to `extractDriveFileId(w.docUrl)` for older records saved before `docFileId` existed — parses the `/d/<id>/` segment out of the Drive share link) and, if found, fires `gsDeleteWorkerDoc(fileId)` (POST `action:'deleteWorkerDoc'`) after removing the worker locally and kicking off `autoSave()`. Best-effort and non-blocking — the worker is always removed from the schedule even if the Drive delete request fails. Backend `deleteWorkerDoc(body)` (`google-apps-script.js`/`apps-script/Код.js`, kept in sync) accepts `body.fileId` (preferred, direct `DriveApp.getFileById().setTrashed(true)`) or `body.fileName` (fallback lookup inside the "Schedule manager APP/Workers" folder, trashing all matches), mirroring `saveWorkerDoc`'s folder resolution. Added to the `WRITE` actions list (requires `API_SECRET`).
  - **Auto-link on worker creation from a scan:** `aiToWorker(isId)` sets `window.__aiPendingWorkerUpload=isId` before opening the pre-filled Add Worker modal — `closeModal()` only hides the scan overlay (doesn't clear its DOM), so the `aiSurname`/`aiGiven`/etc. inputs and `window.__aiScanImage` stay readable afterward. When `saveWorker()` creates a brand-new worker and finds this flag set, it clears the flag and fires `aiFillForm101(isId,'upload',newWorker.id,null)` in the background (no `await`, so the worker save itself isn't blocked) — once the upload resolves, that worker's `docUrl`/`docSavedAt` are set, `autoSave()`+`render()`/`renderWorkersPage()` run, and a toast names the worker. Editing an existing worker never re-triggers this — it only fires on first creation from a scan. The explicit `null` (4th arg, `btnEl`) matters: `aiFillForm101` normally resolves its "loading" button from the global `event`, but here `event` is the Add/Save Worker button's click, not a real Form 101 button — passing `null` stops the background call from disabling/relabeling unrelated modal chrome. Three of the four real button `onclick` call sites pass only `onclick="aiFillForm101(isId,mode)"` and resolve their button from `event`. The foreign-passport upload button passes `onclick="aiFillForm101(false,'upload',window.__aiRescanWorkerId)"` with an explicit `workerId` to enable rescan deduplication when re-uploading the same passport holder's updated document.
  - **Worker edit modal close button:** `showWorkerModal` puts its close action in a small `×` icon button next to the title (top-right, matching the pattern already used by `aiScanOverlay`) instead of a text "Cancel" button in `.modal-actions`.
  - **Worker preview card:** `openWorkerCard` (the summary card shown when clicking a worker row, before entering edit mode) has the same small `×` close button next to the name/status block. Its `.modal-actions` row replaces the old text "Close" button with a "Скачать документ" link to `w.docUrl` when the worker has one — omitted entirely (no placeholder) for workers without a linked document, same conditional pattern as the edit modal's "Документы" section above.
- **AI document scan / Form 101 flow** (`onScanFileSelected`, `renderScanEditor`, `runOcr`, `renderAiResult`, `aiFillForm101`, `aiToWorker`): photo/PDF is first turned into a plain image (`onScanFileSelected` renders a PDF's first page to canvas via pdf.js if needed) and handed to a **manual crop/rotate editor** (`renderScanEditor`/`initScanCropBox`/`attachCropDrag`) *before* OCR — straightening/framing the shot by hand makes it easier for the AI to read. The crop rectangle is tracked in on-screen pixels (`window.__cropRect`) while dragging (Pointer Events, corner handles resize, box body moves — `#scanEditWrap` must NOT have `overflow:hidden`, or the corner handles get clipped since they extend past a full-frame crop box via negative margin), then converted to fractions on confirm. "Готово" (`confirmScanEdit`) crops/rotates by hand and calls `runOcr(...,autoAlign=false)`, trusting the manual edit over the AI's own guess; "Пропустить" (`skipScanEdit`) skips straight to `runOcr(...,autoAlign=true)`, which falls back to applying the AI's own `imageAlign` result. `runOcr` uploads to backend Apps Script, which uses **Anthropic Vision API** to OCR and extract passport/Israeli ID fields (`aiReadDoc` action). Server-side only — previous client-side OCR (Tesseract.js, MRZ parser) removed for better accuracy and lighter JS footprint. User UI displays loading spinner with progress bar during scan (`@keyframes spin`, `.progress-bar`). `alignScanImage(b64,mediaType,align)` is the shared canvas-based primitive behind both the manual rotate buttons and the AI auto-align path: affine-only (rotate in 90° steps + rectangular crop, no perspective correction), crop fractions are always measured against the pre-rotation image, falls back to the untouched image on any error.
    - **Form 101 generation modes:** `aiFillForm101(isId, mode, workerId, btnEl)` accepts `mode='download'` (default, download PDF to local device) or `mode='upload'` (assemble Form 101 + signature + scanned ID image into one PDF and upload to Google Drive via `saveWorkerDoc` action). Upload mode shows "Загрузить" button alongside "Форма 101" download button, with explanatory text. `btnEl` is optional — pass an explicit button element (or `null`) to bypass the default `event.target`-based lookup used for real button clicks. Helper `bytesToBase64(bytes)` converts large buffers to base64 in chunks to avoid stack overflow on multi-MB PDFs (common for high-res ID scans).
  - **Rescan deduplication (previousFileId strategy):** When uploading in `mode='upload'`, the function resolves the target worker *before* uploading so it can pass `previousFileId` to the backend's `saveWorkerDoc` action. The function resolves the worker ID in this order: (1) explicit `workerId` parameter (used when called by `aiToWorker` on new-worker creation), or (2) `window.__aiRescanWorkerId` global flag (set by a rescan flow to indicate this upload is replacing a previously-uploaded document). The resolved worker's `docFileId` (if it exists) is sent as `previousFileId` — this lets the backend trash the exact old file by stable ID, rather than relying on the OCR'd filename which can drift between scans. After successful upload, `window.__aiRescanWorkerId` is cleared. This pattern supports rescans: a rescan of an existing worker can set `window.__aiRescanWorkerId=workerId` before calling `aiFillForm101`, ensuring the old PDF is replaced (not duplicated) in Google Drive even if the OCR'd name or document number changed between scans. Fresh scans from the main Workers page "Scan passport" button explicitly clear `window.__aiRescanWorkerId=null` at entry (inline in the button's `onclick` handler) to prevent state leakage from a previous incomplete rescan flow and ensure the subsequent scan creates a new worker, not an overwrite.
  - **Scan results normalization:** After AI extraction, child-name fields are normalized via `_nrm(s)` — collapses multiple spaces, trims whitespace, ensuring clean data in `window.__aiScanChildren` array. This array is populated from Israeli ID scans (if the ID has registered children in its ספח appendix) and displayed in the Form 101 UI.
  - **Form 101 pre-fill UI:** After scanning, users set optional fields and optional signature before PDF generation:
    - **For Israeli ID:** `aiIdWork` (date started), `aiIdFund` (health fund), `aiIdMarital` (marital status) — populate the corresponding PDF fields. Includes signature pad placeholder.
    - **For foreign passport:** `aiPpWork` (date started), `aiPpFund` (health fund) — populate the corresponding PDF fields. Includes signature pad placeholder.
    Each scan path is independent; user customizes before generating the PDF.
  - **Form 101 PDF filling enhancements:**
    - **Text field font sizing:** `setSize(name, size)` helper overrides template default font via `acroField.setDefaultAppearance('/Helv NNpt Tf 0 g')`, making text readable. Applied to `surname` (11pt), `given_name` (11pt), `addr_street` (11pt), `addr_city` (11pt), `hf_name` (10pt), `id_top2` (13pt) — sizes tuned to fit field boxes.
    - **PDF form field combing:** Fields like `dob`, `tax_year`, `passport_no` are printed with per-character boxes. `setComb(name, maxLen, value, size)` helper uses `fld.enableCombing()` to spread each character into its own box. Applied to `dob` (8 chars = DDMMYYYY), `tax_year` (4 chars = YYYY), `passport_no` (13 chars). Sets explicit size to prevent pdf-lib's auto-sizing from overflowing boxes vertically. For fields with no underlying form field (just printed boxes), `drawCombRaw(text, maxLen, rect, size)` manually draws characters evenly spaced across the given box coordinates — used for work-start date and children table.
    - **Work-start date (תאריך תחילת העבודה בשנת המס):** No form field on template — just printed comb box. `fillWorkStart(isoDate)` refactored helper extracts date parts and calls `drawCombRaw()` to fill the date box (DDMMYYYY format) at coordinates `{x:30.75, y:450.42, width:90.64, height:21.01}`. Called by both Israeli ID and foreign passport paths.
    - **Children table (ג. פרטים על ילדיי...):** New feature for Israeli ID scans. Template has 10 printed rows (no form fields) for child ID, DOB, and name. Data comes from `window.__aiScanChildren` array (populated by AI scan via `aiReadDoc` action, each child normalized via `_nrm()`). `aiFillForm101()` iterates children, draws each field via `drawCombRaw()` into the corresponding row's box: ID (9 chars, numeric), DOB (8 chars, DDMMYYYY), Name (right-aligned with `page1.drawText()` using Heebo or system font). Skips eligibility checkboxes (rows 1–2 of the "בן/בת" column) — user marks these by hand since they require parent declaration, not something a scan can provide. Only Israeli-ID path surfaces children (from the ID's ספח).
    - **Signature pad:** Both foreign passport and Israeli ID Form 101 paths include a signature capture canvas (`SIG_PAD_HTML` template constant). Canvas element (`id="aiSigCanvas"`, 500×120px, styled to 340×90px max) supports mouse and touch drawing. Four functions handle capture:
      - `initSignaturePad()` — sets up canvas with black pen on white background, initializes touch/mouse event handlers (preventDefault to block scrolling), tracks cursor position with DPI scaling via `canvas.getBoundingClientRect()`, manages drawing state (lastX/lastY).
      - `clearSignaturePad()` — clears canvas and resets `_sigDirty` flag; called via "Очистить подпись" button.
      - `getSignaturePng()` — returns `canvas.toDataURL('image/png')` if signature was drawn (`_sigDirty=true`), else `null`. Called when building final worker PDF.
      - **CSS support:** `@keyframes spin` for loading spinner and `.progress-bar` visual feedback during AI scanning (client-side only, no external loader libs).
    - **Signature embedding in PDF:** After user signs on the pad, `getSignaturePng()` returns the PNG data URL. `aiFillForm101()` then fetches this PNG, embeds it via `doc.embedPng()`, and draws the signature image onto page 2 of the Form 101 PDF at the printed signature line (coordinates 34.02, 186; 87.99×15mm box), scaled to fit. Gracefully skips if no signature provided.
    - **Form 101 export modes:** `aiFillForm101(isId, mode)` now accepts `mode='download'` (default, downloads PDF locally) or `mode='upload'` (assembles Form 101 + signature + scanned ID image into a single PDF and uploads to Google Drive). Upload mode calls `saveWorkerDoc` action with `fileBase64` (chunked via `bytesToBase64()` to avoid stack overflow on multi-MB PDFs), `fileName` (worker name + doc number), and `mimeType='application/pdf'`. Response returns file ID and shareable link. Both "Форма 101" (download) and "Загрузить" (upload) buttons are displayed in the Form 101 section; upload includes explanatory text about collecting Form 101 + ID scan + signature into one PDF for Google Drive storage.
    - **Heebo Hebrew font (offline-safe):** `_loadHeeboFont()` loads `heebo-hebrew.ttf` as bundled same-origin asset (cache-first), avoiding external CDN. `_loadFontkit()` lazy-loads fontkit from CDN (required by pdf-lib to embed custom fonts; happens once per session). Hebrew-aware text setter `setH(name, value)` calls `setText()` first, then `updateAppearances(customFont)` to re-render field appearance stream with Hebrew glyphs. For multi-word RTL text (e.g. two Hebrew words with space), fixes pdf-lib's appearance bug by: blanking the widget's operators, then manually redrawing text right-aligned via `page1.drawText()` to avoid doubled glyphs. Falls back to ASCII-safe replacement (replacing Hebrew block U+0590–U+05FF with `?`) if Heebo unavailable. Form dict's `NeedAppearances=false` tells PDF viewers to use our appearance streams, not re-render. `HEALTH_FUND_HE` map (lines ~2938) converts enum codes (`Clalit`, `Maccabi`, `Meuhedet`, `Leumit`) to Hebrew fund names for display in the filled form.

### worker-punch.html

- Reads a per-worker `token` from the URL (`URL_TOKEN`) to jump straight to that worker's punch screen; without a token it shows a worker picker (`renderWorkerGrid`).
- `getLastEntry(log, wid)` returns the most recent punch entry for a worker **across all days** (not just today). This determines whether to show "Clock IN" or "Clock OUT" in the UI, and powers the "In since" / "Last: X (out)" status in the worker grid.
- GPS anti-spoofing lives in `analyseGps`/`getLocation`: flags zero/low accuracy, impossibly fast movement between two readings (`haversine` distance ÷ time), suspicious device speed, and instant geolocation responses (`GPS_REQUEST_MS`) as signs of a mocked location, before allowing a punch within `SITE.radius` of the client site.
- Offline-safe punches: `doPunch()` always writes to `localStorage` (`punchLog`) and also queues to `punchQueue` (`getQueue`/`saveQueue`/`queueEntry`) when the Sheets `savePunch` call fails, for later resync.
- `updateScheduleManager` reaches into the *same-origin* `schedMgr_v1` localStorage key to reflect a punch back into the manager app's cached schedule — this only works when both apps share local storage (i.e. same browser/device), it's not a sync mechanism across devices.

### Shared conventions across both files

- No modules/imports — everything is global functions/consts inside one inline `<script>` per file. When adding functionality, follow this style rather than introducing bundling.
- **XSS protection (CRITICAL):** All user-supplied text is wrapped in `esc()` — a helper that HTML-escapes `&<>"'` to prevent injection. Use it on every `${...}` expression inside template strings building HTML from data. The `esc()` function is the single source of truth for HTML-safe interpolation (defined after `uid()`). This is a foundational security requirement. Both files have the same `esc()` definition and it must be kept in sync.
- Both files duplicate constants and helpers: `GS_URL`/`API_SECRET`, `reportError`, `showToast`, `getPunchLog`/`savePunchLog`, `urlB64ToUint8` (`worker-punch.html` has `urlB64ToUint8WP`), `esc()` function, and data analysis functions like `groupPunchesIntoShifts` and `analyzeDayPunches`. This duplication is intentional (no shared build). A fix in one file (API URL rotation, `esc()` improvement, payroll logic) must be mirrored in the other to avoid drift.
- Push notifications: both files subscribe via `savePushSubscription` action; `service-worker.js` handles `push` events and `notificationclick`.
- **Auto-deploy on commit:** `.claude/settings.json` runs a `PostToolUse` hook on `Write|Edit|NotebookEdit` that stages, commits (with co-author trailer), and pushes to `origin/HEAD` automatically after every file change made by Claude Code. Each push to `origin/main` triggers GitHub Actions deploy workflows (no manual `firebase deploy` or `clasp` commands needed).
