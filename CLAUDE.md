# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is the index: the rules that apply everywhere, and which `docs/*.md` file to read before touching which part of the code.

**Session language:** the user communicates in Russian. Claude's own conversational output (explanations, status updates, questions) should be in Russian throughout — independent of what language the app's UI/code is in.

**UI text language:** every UI text in the code is English. The UI is shown in the language picked with the page's one Language button (English by default; remembered per device and on the user's account; English, Hebrew, Russian) **only through the dictionaries** `i18n/<lang>.json`: texts go through `tr()` / `data-i18n`, never a translated string in the code; Hebrew must stay complete (`npm run test:i18n`), Russian is set up but not translated yet; the layout stays left to right in every language (docs/translations.md). **Everything that goes into Form 101 is Hebrew** (per user request 2026-09-30): the labels of every field that feeds the form (worker modal: names, ID, sex, marital status, health fund, address, income types, children, spouse block; firm profile: employer name, deductions file, phone, address) and the values printed in it. The one exception is a **foreign-passport worker's (and a foreign spouse's) given name and surname, which stay in Latin letters** as printed in the passport; every other printed value is Hebrew. There is no Russian anywhere in the repo — UI, the error texts the functions return, code comments, docs (translated to English on 2026-10-05, per user request); don't add any. The exceptions: the Russian dictionary `i18n/ru.json` (and the language's own name in `I18N_LANGS`), and data — the hours import still accepts the Russian column names for Date / In / Out (`parseHoursExcelFile`).

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served as static files from Firebase Hosting (project `schedule-odinson`). No build step, no bundler, no package.json at the root — each page is a self-contained HTML file with inline `<style>`/`<script>`.

Multi-tenant: a super-admin creates firms (tenants), each with its own logins and isolated data. Roles: `superadmin`, `tenant_admin`, `staff` (per-section permissions), `hr` (per-section permissions; by default only the workers assigned to it, `hrId` — docs/hr.md), `supplier` (own workers only), `client` (the client portal: its own workers' hours at its site, by its ticks — docs/client-portal.md). HR, supplier and client review hours the same way (hours ticks, per-day approve / dispute / fix — docs/hours-review.md).

The backend is **Firestore + Firebase Storage + Cloud Functions**, and nothing else. The original Google Apps Script / Google Sheets backend was removed on 2026-10-03 (see docs/history.md); don't add calls to it.

## Files

- `schedule-manager.html` — the manager/admin app (all tabs). Loads `firestore-backend.js` at startup and `scan-pipeline.js` on the first scan.
- `scan-pipeline.js` — the document-scan pipeline, run in the page's global scope.
- `hours-review.js` — the shared hours-review screen (client portal, supplier portal, an HR in the manager app), run in the page's global scope.
- `firestore-backend.js` — the browser Firestore/Storage layer (`initFirestoreBackend()`), shared by the manager app and the supplier portal.
- `worker-punch.html` (`/punch`), `supplier-portal.html` (`/supplier`), `client-portal.html` (`/client`) — the worker, supplier and client pages.
- `service-worker.js` — PWA shell (network-first, same-origin GETs only). `manifest.json`, `manifest-punch.json`.
- `functions/` — Python Cloud Functions, us-central1: `fill_form_101`, `preprocess_scan`; `functions/assets/` holds the PDF template and font (re-sync from the root copies `form101_fillable.pdf` / `heebo-hebrew.ttf` if those change).
- `functions-auth/` — Python Cloud Functions, europe-west3: `login`, `users_admin`, `punch`, `supplier`, `hours`, `ai_read`; the AI prompts are `functions-auth/ai_prompts.json`.
- `i18n/<lang>.json` — the UI dictionaries (English text → translation), `tests/i18n/check.js` checks them.
- `firestore.rules`, `storage.rules`, `firestore.indexes.json`; `tests/rules/` (rules tests + the npm scripts that run `tests/auth/`); `tests/auth/` (functions tests, incl. `ai_golden.json`); `tests/e2e/` (browser tests: the pages in Chromium on the emulators).

## Commands

- Local preview: `firebase emulators:start --only hosting`, or open the HTML files directly.
- Rules tests: `cd tests/rules && npm install && npm test`. Functions tests: `cd tests/rules && PYTHON=<python with firebase-admin, pytest> npm run test:auth`. Browser tests: `cd tests/e2e && npm install && PYTHON=<same python> npm test`. All of them run on every PR into `main` (`tests.yml`); a red check blocks the merge (docs/tests.md). A new feature adds its check in the same PR.
- Deploying `functions/` by hand needs `functions/venv` first (`python -m venv venv && pip install -r requirements.txt`); CI builds its own.
- **Deploy = merge to `main`.** GitHub Actions: Hosting on every push to `main`; functions and rules on pushes touching their paths (details in docs/backend.md).

### Git workflow (enforced by hooks in `.claude/settings.json`)

- **`My_Work_Befor_PR`** is the standing work branch — check it out (or resume the cloud session on it) at the start of work instead of `main`. Don't create ad-hoc branches per session. (A cloud session that is given a designated branch uses that one.)
- A `PostToolUse` hook auto-commits and pushes every file edit to the **current branch** (`git push origin HEAD`). This only fires in a session whose working directory *is* this repo at session start.
- A `PreToolUse` hook blocks any `git push` that force-pushes, targets `main` by name, or runs while the current branch is `main`.
- A `SessionStart` hook injects `git status --short` + current branch as context.
- A `PostToolUse` hook on `gh pr create*` or the GitHub MCP `create_pull_request` tool checks the PR's diff against CLAUDE.md and `docs/*.md` and updates them via an agent.
- **"Deploy" means: open a PR from the work branch into `main` covering everything accumulated since the last one, then merge it — merging is what triggers the real deploy.** Never push/reset directly to `main`. Batch accumulated changes into one PR per deploy request rather than one PR per edit.
- **Never merge a PR without asking the user first.** Pushing to the feature branch needs no confirmation; merging to `main` always does. Exception: the stages of the redesign plan in docs/redesign.md, which the owner approved in advance — each is merged by its session once its CI is green (docs/redesign.md → Auto-continue).

## Rules that apply everywhere

- **XSS:** every `${...}` that puts data into HTML goes through `esc()`. Each page has its own identical `esc()`; keep them the same.
- **No modules or build:** everything is global functions/consts in one inline `<script>` per page (plus the two lazy-loaded `.js` files, which also run as globals). Follow that style.
- **Modals close the same way everywhere (template):** a tap anywhere outside a modal (the dark backdrop) closes it — one document handler for every `.overlay` (docs/app-core.md → Layout). Modals have no ✕ and no Cancel / Close button; a modal whose closing must undo or save something sets `overlay.__onUserClose` (the worker window saves itself this way and has no Save button). A new modal follows this and adds no close button or backdrop handler of its own.
- **Tap reads, double click / long press edits (template):** a single tap on a list item or card opens its card, or its edit form when it has no card; a double click (computer) or a long press (phone) opens the edit form; a card that only reads (the worker card) also has a ✎, and a line that also does something else (a firm: open it) carries a ✎ at its right; controls inside keep their own job (`tapEdit` / `longPress` / `isPlainTap`, class `.tap-edit`, docs/app-core.md → Layout). On a phone a window closes with a swipe down too, and the page behind it doesn't scroll. A window opened from another window goes back to it when it closes (`__returnTo`, manager app). A new list, card or modal follows this.
- **List look (template, variant 3 → Odinson Glass plates):** figures as text on top, sections with a count, items as plates with a colored bar on the left and the avatar in the same color (`t3Line`, `.t3-line`); row actions under a bare ⋮ (`o.menu`) and a swipe (`o.swipe`), Delete never asks — the Undo snack (`undoDelete`), Select mode from the header ⋮ (`startSelect`); on a phone windows open from the bottom (docs/app-core.md → Layout). The Schedule tab too: a line per worker, its days opened under it.
- **Short fields in pairs (template):** two short fields share a line in a `.field-row` (phone and computer); long text fields stay one per line (docs/app-core.md → Layout).
- **Checkboxes are tiles (template):** a set of checkboxes is a `.check-grid` of `label.check-chip` tiles, a long form is split by `.form-section` headings — the same on a phone and a computer (docs/app-core.md → Layout). New forms follow this.
- **Lists page by 10:** every list that can grow (workers, clients, suppliers, firms, users, punches, errors, timings, pending hours, salary and rate tables, documents, …) is drawn with `renderPagedList` (docs/app-core.md → Long lists). It shows 10 rows, and the next 10 only when the user scrolls to the end or taps "Show more". A new list follows the same rule. Totals rows always cover every item.
- **Duplicated on purpose:** `esc()`, `reportError`, `showToast`, `getPunchLog`/`savePunchLog`, `loadFirestoreBackend()`, the shift pairing (`groupPunchesIntoShifts`/`analyzeDayPunches`), the pay functions (`PAY_RULES`, `israeliDayPay`, `effectiveRates`, `shiftPay`, `shiftPayFor`, `isDailyPay`, `dailyRate`, `dayOverride`, `salaryPeriodKey`, `wOwnRate`, `localYMD` — manager app, supplier portal and the punch page, which also copies `travelPay`; the daily commission rule — `commissionFor` in the manager app, `myCommission` in the portal), the paging helper (`renderPagedList`, in the manager app and the supplier portal), the new version check (`startVersionWatch` / `showNewVersionBar`, in all three pages), the greeting (`GREET_ICONS`, `partOfDay`, `greetingHtml` and the `.gic` styles, manager app and punch page), the on-demand SheetJS loader (`loadXlsx`, manager app and supplier portal), the translation core (`I18N_LANGS`, `tr`, `applyI18n`, `uiLocale`, `loadI18n`, `storedLanguage`, `setLanguage`, in all four pages) and the Language button and sheet (`I18N_LANG_EN`, `syncLangButtons`, `openLangSheet`, `closeLangSheet`, `renderLangList`, `pickLanguage`, in all four pages; `placeLangButton` in the manager app), the Odinson Glass foundation CSS block (ground, `.gbtn` and its shine handler, `.og-line`, `.plate`, tick tiles, `.lang-*` — the same in all four pages), the phone table cards and their toggle (`cardTables`, `getTablesView` / `setTablesView` / `applyTablesView`, manager app and supplier portal), the new-worker badge (`newWorkerBadgeHtml`, manager app and supplier portal), the client portal's copies (`client-portal.html` copies `esc`, the translation core, `showToast` / `toastKind`, `startVersionWatch`, `loadXlsx`, the backdrop close, `groupPunchesIntoShifts` / `analyzeDayPunches`, `localYMD`, `loadFirestoreBackend`), the hours-review lines (`hrvMonthDays` in `hours-review.js` and `hourDayLines` in the manager app build the same `worker|day|ins|outs` lines), the `hours-review.js` loader and call (`loadHoursReview` / `hoursCall`, in all three pages), the account menu (`toggleAccountMenu` / `closeAccountMenu` and its `.acct` styles, in the manager app and both portals), the template pieces (`.t3-*` styles and the bottom-sheet rule; `t3Line` / `t3Av` in the manager app and the supplier portal), the list pieces (the plates CSS block, `rowFnKey`, `openRowMenu` / `openPopover` / `closePopover`, the swipe handlers and `swipeAct`, `undoDelete` / `finishUndo`, `startSelect` / `selectRoot` / `endSelect`, `listMenuHtml` — manager app and supplier portal), the editor section plates (the `.og-sec` styles, `ogSections` / `ogSecToggle` / `ogSecOpen` / `ogSecSummary` / `ogSegSelect` and the focus patch — manager app and supplier portal), the modal backdrop close (the document click handler + `__onUserClose`, and the phone swipe-down close — also in the client portal) and the tap / edit helpers (`tapEdit`, `longPress`, `isPlainTap`), both in the manager app and the supplier portal, exist in more than one page. A fix in one must be mirrored in the others.
- **Payroll:** hours and pay only through the canonical functions in docs/accounting.md (a shift's pay: `shiftPayFor`, which covers hourly and daily pay) — never a second calculation. Supplier commission and client billing are separate figures that never change a worker's pay.
- **Firm data isolation:** a firm sees only its own data; an own-workers HR login sees only the workers whose `hrId` is its uid and their punches (rules + `hrOnly()` queries), and never changes a worker's `hrId`; a supplier never receives client billing, GPS, a worker's punch-link token or file links, and receives its own workers' pay inputs (rates, pay mode) only with "Sees own workers' pay" (claim `pay`, on by default; server-side allow-lists, docs/supplier-portal.md); an HR never gets the full Accounting tab — its Accounting section (off by default) shows only its own workers' pay and its commission; a client login (the client portal) sees only its own workers' names and shifts at its site, by its ticks, through the `hours` function — never pay, rates, suppliers, GPS, documents or tokens, and no client-facing surface shows supplier data.
- **Form 101:** see the language rule above; field positions only via docs/form101-field-map.md.
- **AI prompts** live in `functions-auth/ai_prompts.json`; `tests/auth/test_ai.py` checks every request against `tests/auth/ai_golden.json`, so a prompt edit also updates that file (docs/backend.md).
- **Uploads:** new upload features go through the shared helpers (`filesToUploadPages`/`fileToUploadPages`/`downscaleForUpload`/`fileForStorage`) and send per-page requests in parallel (docs/scan.md).
- **Parallel AI calls:** a feature that sends several AI requests starts the independent ones at once (`Promise.all`, one request per page or field batch, merged in page order); a Cloud Function that receives such calls is declared with `cpu=1`, `concurrency=20` and keeps no shared per-request state (docs/backend.md → Parallel AI calls). **When a task adds or changes a feature with several AI or server calls that could use this pattern but doesn't yet, Claude points it out in chat and proposes applying it (what would run in parallel, which function settings) before writing the code — don't apply it silently, don't skip it silently.**
- **Icons:** the pages use a self-hosted subset of Tabler Icons (`icons/`); a new `ti-<name>` needs `python tests/icons/build.py` and `npm run test:icons` passing (docs/app-core.md → Fonts and icons).
- **Service worker:** when `service-worker.js` changes, bump its `CACHE` version (now `schedule-mgr-v122`), or clients keep stale files.
- **Hosting ignore** in `firebase.json` must keep `functions/**` (otherwise the venv is uploaded publicly), `functions-auth/**`, `tests/**`, `docs/**`, `*.md` and the rules files.
- **Secrets** live in Secret Manager (`ANTHROPIC_API_KEY`) — never in the repo, never asked for in chat.

## Keeping the docs true

When a change alters what a documented function does (parameters, control flow, data shape, who may call it), update the matching `docs/*.md` file in the same PR, describing only the current state. A debugging trail or a reverted approach goes to docs/history.md. Add a new `docs/*.md` file (and a row above) for a new tab or module rather than growing this file.
