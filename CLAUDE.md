# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Session language:** the user communicates in Russian. Claude's own conversational output (explanations, status updates, questions) should be in Russian throughout — independent of what language the app's UI/code is in.

**UI text language:** general new UI text (tabs, buttons, messages) is in English. **Everything that goes into Form 101 is Hebrew** (per user request 2026-09-30): the labels of every field that feeds the form (worker modal: names, ID, sex, marital status, health fund, address, income types, children, spouse block; firm profile: employer name, deductions file, phone, address) and the values printed in it. The one exception is a **foreign-passport worker's (and a foreign spouse's) given name and surname, which stay in Latin letters** as printed in the passport; every other printed value is Hebrew. The `Бухгалтерия` (Accounting) tab is a Russian pocket added by mistake — don't repeat it. Leave existing English/Russian text outside Form 101 as is unless asked.

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served as static files from Firebase Hosting. No build step, no bundler, no package.json, no test suite — the two pages are self-contained HTML files with inline `<style>`/`<script>`.

**Multi-tenant:** a super-admin creates "firms" (tenants) with their own login; each firm's data (schedule, punches, Drive docs) is isolated. See `MULTI_TENANT_PLAN.md` for the data model, auth design, and status. `apps-script/Код.js`/`google-apps-script.js` require session tokens on top of the legacy `API_SECRET`; `schedule-manager.html` has a login screen plus `gsAuth()`/`gsAuthQuery()` wrappers sending that token on every request.

### Files

- `schedule-manager.html` — the manager/admin app (shifts, workers, clients, payroll, exports). RTL, Hebrew (`lang="he"`), ~4500+ lines. Lazy-loads `scan-pipeline.js` on first scan to avoid parsing the document-scanning code (~100KB, corner editor, alignment/OCR orchestration, field verification, etc.) on every page load.
- `scan-pipeline.js` — document-scanning pipeline, lazy-loaded by `schedule-manager.html` (added 2026-09-28). Contains the corner editor (`renderScanQuadEditor`/`initScanQuad`/`attachQuadDrag`), alignment (`autoPreAlignScan`/`refineQuadCorners`/`finalTightenPass`), OCR calls and field verification, and all related helpers. Loaded once via `ensureScanPipelineLoaded()` and executed in global scope — every function becomes an ordinary global after load, exactly as if it were still inline in `schedule-manager.html`. **Entry points** (always in the main HTML file): `startNewScan()` (new manual scan, async wrapper around `openAiScan()`) and `rescanWorkerDoc(workerId)` (rescan existing worker, async wrapper around `openAiScan()` with `__aiRescanWorkerId` set). Both become async in the main file to handle the load promise, though `openAiScan()` itself (defined in the pipeline once loaded) remains synchronous.
- `worker-punch.html` — the worker-facing clock-in/out app, opened via a per-worker tokenized link.
- `supplier-portal.html` — the supplier/agency-facing app (added 2026-10-02, Admin/Roles plan stage 16), routed at `/supplier`. A deliberately separate, lighter file (like `worker-punch.html`, not an embedded mode inside `schedule-manager.html`) — see its own section below for why and what it does/doesn't include.
- `service-worker.js` — PWA offline shell (network-first, cache fallback). Never intercepts `script.google.com` — the API always goes straight to network.
- `manifest.json` / `manifest-punch.json` — installable-PWA manifests for the two apps.
- `google-apps-script.js` — backend Apps Script source (mirrors `apps-script/Код.js`, the one actually deployed). Backed by a Google Sheet acting as the database.
- `apps-script/appsscript.json` — Apps Script project config (timezone, runtime, web app access, OAuth scopes: `spreadsheets`, `script.external_request` for the Anthropic API, `drive`).
- `apps-script/.clasp.json` — clasp config linking local source to the deployed Apps Script project.
- `form101_fillable.pdf` / `heebo-hebrew.ttf` — source copies at repo root; the client no longer fetches these. `functions/assets/` holds the copies the Cloud Function actually uses. Re-sync `functions/assets/` from these if the template/font is ever updated.
- `form101-field-map.md` — verified field-by-field map of `form101_fillable.pdf` (every AcroForm field's name/rect/Hebrew label/meaning). **Consult and update whenever touching `functions/main.py`'s field rects or the PDF template changes** — drift between this map and the code is a known source of "fields land in the wrong place" bugs.
- `functions/` — Python Cloud Functions: `fill_form_101` (builds the Form 101 PDF via PyMuPDF), `preprocess_scan` (runs AFTER the client's manual crop editor now — see the AI document scan flow section below — OpenCV auto-crop tightening, then Pillow contrast enhancement, then blur check), and `gs_upload_proxy` (added 2026-10-02 — CORS-friendly relay for `saveWorkerDoc`/`saveWorkerAssets`; see `xhrPostJSON()`'s comment in schedule-manager.html and Troubleshooting for why a direct browser→Apps-Script XHR can never carry real upload-byte progress). Has its own `venv/` (gitignored) — `firebase deploy --only functions` expects a pre-built virtualenv and won't create one; run `python -m venv venv && pip install -r requirements.txt` inside `functions/` before deploying from a fresh clone. **Note:** the blur threshold (`BLUR_VARIANCE_THRESHOLD`) was calibrated against pre-enhancement images; as of 2026-09-21 the check runs after enhancement, so post-enhancement blurry photos score higher on the Laplacian variance test — if genuinely blurry scans start passing in practice, raise the threshold.
- `MULTI_TENANT_PLAN.md` — data model, auth design, and status tracker for the multi-tenant feature.

## Commands

No npm/build/lint/test tooling — edit the HTML and reload.

- Local preview: `firebase emulators:start --only hosting`, or open the HTML files directly.
- Routing: `firebase.json` rewrites `/` → `schedule-manager.html`, `/punch` → `worker-punch.html`, `/supplier` → `supplier-portal.html`.
- **Deploy = push to `main` (via PR, see below).** GitHub Actions deploys on every push to `main`:
  - `.github/workflows/deploy.yml` — Firebase Hosting (project `schedule-odinson`).
  - `.github/workflows/deploy-apps-script.yml` — `clasp push --force && clasp deploy` for `apps-script/` (needs `CLASP_CREDENTIALS`/`CLASP_DEPLOYMENT_ID` secrets).
  - `.github/workflows/deploy-functions.yml` — deploys `functions/` on any push touching `functions/**`, or via manual `workflow_dispatch`. Builds a fresh venv in CI. `firebase.json`'s `functions[0].runtime` is pinned to `"python312"` for a deterministic runtime. On failure it opens/updates a GitHub Issue with likely causes — see Troubleshooting below for the known IAM permission gaps.
- When bumping the service worker's cache (`CACHE` constant in `service-worker.js`), increment the version string or clients keep serving stale HTML after deploy. Current version: v94 (as of 2026-10-01, bumped for slow-call telemetry and the Users prefetch).
- `firebase.json`'s hosting `ignore` list must include `functions/**`, or `firebase deploy --only hosting` sweeps the entire `functions/venv` into the public hosting bucket.

### Git workflow (enforced by hooks in `.claude/settings.json`)

- **`My_Work_Befor_PR`** is the standing work branch — check it out (or resume the cloud session on it) at the start of work instead of `main`. Don't create ad-hoc branches per session.
- A `PostToolUse` hook auto-commits and pushes every file edit to the **current branch** (`git push origin HEAD`). This only fires in a session whose working directory *is* this repo at session start — a session rooted elsewhere that reaches this repo only via absolute paths/`cd` never loads this project's `.claude/settings.json`, so no auto-commits happen there.
- A `PreToolUse` hook blocks any `git push` that force-pushes, targets `main` by name, or runs while the current branch is `main`.
- A `SessionStart` hook injects `git status --short` + current branch as context automatically.
- A `PostToolUse` hook on `gh pr create*` diffs the PR's full range against this file and updates it via an agent — so this file should stay reasonably in sync with the code across PRs.
- **"Deploy" means: open a PR from `My_Work_Befor_PR` into `main` covering everything accumulated since the last one, then merge it — merging is what triggers the real deploy.** Never push/reset directly to `main`. Batch accumulated changes into one PR per deploy request rather than one PR per edit.
- **Never merge a PR without asking the user first.** Pushing to the feature branch needs no confirmation; merging to `main` always does.

## Architecture

### Backend: Google Apps Script

Both HTML files talk to the same Apps Script Web App endpoint (`GS_URL`, hardcoded near the top of each file's `<script>`), authenticated with a hardcoded shared secret (`API_SECRET`). Source lives in `apps-script/` (auto-deployed on push to `main`).

**GET endpoints:** `ping` (no auth, returns `{ok:true}`; the login screen calls it so a cold Apps Script instance wakes up while the user types), `loadSchedule`, `loadPunchLog` (optional worker/date/type filters — pre-filters raw rows by tenantId/worker/type *before* the expensive per-row mapping/date-formatting, since PunchLog is append-only and interleaves every firm's rows chronologically with no per-tenant split; see "Optimizations (2026-09-28)" below), `loadPendingHours` (added 2026-10-02, stage 14 — lists all batches pending/approved/rejected for the calling firm, grouped by batchId, never for supplier role).

**Supplier-role server-side data filtering (added 2026-10-02, Admin/Roles plan stage 11):** `loadSchedule(tenantId, auth)` and `loadPunchLog(filter, tenantId, auth)` both gained an `auth` parameter; when `auth.role==='supplier'`, the response is built via allow-list sanitizers rather than trusting the caller to only look at "the right" fields in an otherwise-full response — the defense is that the forbidden data is never serialized into the JSON at all. `_stripWorkerForSupplier(w, supplierId)` filters `m.workers` down to `w.supplierId===auth.supplierId` first, then rebuilds each survivor from an explicit field allow-list (name/docs/address/schedule/etc.) — deliberately excludes `hourlyRate`/`otRate`/`shabbatRate`/`clientRates` (the worker's real wage) entirely, and replaces the raw `supplierRates` map with a single `supplierRate` number (just this supplier's own flat commission, computed server-side — see stage 12 for why it's flat). `_stripClientForSupplier(c)` reduces a client to `{id,name,object}` — a supplier can see WHICH site a worker is assigned to, never that client's own billing/rate fields. The `suppliers` directory itself comes back empty for a supplier caller (its own commission is already on each worker, it never needs the full firm-wide supplier list). `loadPunchLog()` resolves the calling supplier's own worker-id set from the Schedule sheet first (same `supplierId` match), filters punch rows to just those workers, and for a supplier caller omits `dist`/`gpsAccuracy`/`gpsSuspicious`/`gpsWarnings`/`notes`/`editedAt`/`tenantId` entirely — keeps only `id/workerId/workerName/type/time/date/site/clientId`, i.e. exactly IN/OUT + which site, nothing else. Every other role's response is byte-for-byte unchanged (the `auth`/`auth.role==='supplier'` branch is additive, not a rewrite of the existing path). Verified via a Node `vm`-sandboxed test against the real `apps-script/Код.js` source: a supplier sees only its own worker/punches with every forbidden field absent (not just falsy — genuinely `undefined`, confirming the allow-list never touched them) and its own correct flat commission; `tenant_admin`/no-auth calls return completely unstripped data.

**Server-side permission enforcement (added 2026-10-02, Admin/Roles plan stage 9):** `saveSchedule(data, baseSavedAt, tenantId, auth)` gained an `auth` parameter and calls `requirePermission(auth, 'schedule')` at the top — the practical single gate for the whole bundled workers/clients/suppliers/schedule write (see `readScheduleMap()`'s own comment for why it's one combined blob, not separate per-entity actions), so a `staff` login without `'schedule'` in its `permissions` simply can't write any of it. `doPost()`'s `saveSchedule` case now passes `auth` through. **Scope note:** `saveWorkerDoc`/`saveWorkerAssets`/`deleteWorkerDoc` were deliberately left ungated server-side for now — they're only ever triggered from inside the Workers tab, which `applyNavPermissions()` (stage 8) already hides from a `staff` login lacking `'workers'`, so the practical risk is low; a future stage can add the same `requirePermission()` call to them if that indirect protection ever proves insufficient.

**Roles and permissions (added 2026-10-02, Admin/Roles plan stage 3):** `Users` rows now carry `permissions` (JSON array of allowed sections — `workers, clients, suppliers, schedule, accounting, exports` — or the literal string `'*'` for full access, the default for every pre-existing login) and `supplierId` (nullable, only set for `role==='supplier'`). Four roles: `superadmin` (everything, every firm, never gated), `tenant_admin` (everything within its own firm — the legacy role name `'tenant'` is normalized to `'tenant_admin'` at login time in `login()`, no data migration of existing rows needed), `staff` (a firm's own sub-user, gated per-section via `permissions`), `supplier` (external agency login, scoped to its own workers — see the supplier-portal plan). `requireAuth()` now also resolves `permissions`/`supplierId` from the session token payload. New helper `requirePermission(auth, section)` — throws unless `auth.role!=='staff'` (every other role bypasses this check entirely) or the `staff` login's `permissions` includes that section (or is `'*'`); call at the top of any action that should be gated, same pattern `requireAuth()` itself already establishes. `USERS_HEADERS` const replaces what used to be an inline array literal repeated at each write site. One-time migration `migrateUsersAddPermissionsColumns()` (run manually from the Apps Script editor, safe to re-run) appends the two new header columns to an existing `Users` sheet and backfills `permissions='*'` on every existing row — belt-and-suspenders, since `login()` itself already treats a missing/empty `permissions` cell as `'*'` regardless.

**POST endpoints** (require `API_SECRET`, and a session token except for `login`):
- Auth/tenant: `login` (for a super-admin the reply also carries `tenants`, the Firms list, saving the next screen a round-trip), `createUser` (super-admin, creates a firm — new firm owner is written as `role:'tenant_admin'`, `permissions:'*'`), `updateTenant` (edit firm profile, returns refreshed `profile`), `loadTenantProfile`, `listTenants`/`setTenantActive`/`deleteTenant` (super-admin). `listTenants` reads only the small Schedule columns (TenantId, savedAt, `workerCount`, `clientCount`), never the workers/clients JSON; a row saved before the count columns existed is parsed once as before. **Critical:** `createUser`/`updateTenant` format phone/deductions-file-number fields as plain text (`setNumberFormat('@')`) *before* `setValue()`, or Sheets auto-coerces the digit string to a number and drops leading zeros (Israeli phone numbers, deductions file numbers) — corrupting what Form 101 prints. Pre-existing rows written before this guard, or via `migrateToMultiTenant()`'s initial tenant row, can still have this corruption; see Troubleshooting.
- Punch-log bulk delete: `deletePunchesByMonths` (`body.months: ['yyyy-MM',...]`, `tenant_admin`/`superadmin` only) removes those whole months from both `PunchLog_<tenantId>` and `PunchLogArchive_<tenantId>` (month from the `Date` column, falling back to `Timestamp`), rewriting each sheet in one pass and recoloring rows. Client: Admin → Punch Log → "Clear Log" (`clearPunchLog()` → `#clearLogOverlay` month checklist with record counts + type-DELETE confirm → `submitClearPunchLog()`), hidden for `staff`; downloads a CSV backup of exactly the rows being deleted, then drops them from the local `punchLog` cache too. Other devices' local caches keep already-loaded rows until their own cache is cleared (`syncPunchesFromGS()` keeps local-only rows).
- Schedule/punches: `saveSchedule` (optimistic concurrency via `baseSavedAt`; `clients.radius` always coerced to a number; guards each `workers`/`clients` JSON blob against Google Sheets' ~50,000-char cell limit before writing — see "Optimizations (2026-09-27)" below), `savePunch`/`updatePunch`/`deletePunch`, `deletePunchesByMonths` (Admin → Punch Log → "Clear Log" — bulk delete by calendar month, gated to `tenant_admin`/`superadmin`, deletes from both live and archive sheets), `savePushSubscription`.
- AI document scan (all call the paid Anthropic API, all require `API_SECRET`):
  - `aiReadDoc` — main OCR call (passport/Israeli ID). Uses `ANTHROPIC_MODEL` (Script Properties; default `claude-sonnet-5` — deliberately not the cheap model, since a misread digit corrupts a real tax form). `max_tokens: 8000`, prompt-caching enabled. On JSON-parse failure, checks `stop_reason==='max_tokens'` to report truncation specifically rather than a generic parse error. Response includes `fieldBoxes` (bounding boxes for digit fields, for zoomed re-verification), `photoBox` (portrait location, used by `cropPortraitAvatar()` to build the worker avatar thumbnail), and `children`. `imageAlign` was dropped from both `aiReadDoc` and `aiReadSefach` output on 2026-10-01, since no live path read it and it only cost output tokens; the dormant `runOcr()`/sefach-only paths fall back to the full frame (Israeli ID ספח appendix, if present). The prompt text comes from two shared field maps defined just above it, `IL_ID_FIELD_MAP` and `PASSPORT_FIELD_MAP` (2026-09-30), built from real scans. Israeli pages: (A) biometric card front with no sex, address or children; (B) biometric card back with no address, and its 9-digit `מספר הכרטיס` card number is not the ID; (C) the paper ספח, used with both card types. The older laminated card's labels are too faint to read, so its fields are identified by their fixed top-to-bottom order: ID number, surname, given name, father's name, mother's name, date of birth, place of birth, sex, issuing office. An optional underlined bottom date is its expiry. The ID number is printed in groups (`0 1234567 8`) that get joined. Only Gregorian dates are used, never Hebrew-calendar ones. A ספח child block repeats the holder's number as `מספר זהות בעל התעודה`, and the child's own number is a separate row. The ספח spouse rows are returned as `spouse:{surname,given,idNo}`, never as the holder or a child. Parent and previous names, `מס' דירה`, `מיקוד` and place of birth are never used. Passports: the title (MR.) and non-Latin name copies are dropped, and Personal/Identification No. is not the passport number. The MRZ line 2 layout is spelled out and used to cross-check passportNo/dob/sex/expiry. Prompt-only: the client does not validate MRZ check digits itself.
  - `aiDetectAlign` — lightweight rotate+corners sibling, which since 2026-10-01 also returns the page `kind` (`id_front`/`id_back`/`sefach`/`passport`/`contract`/`other`) on a separate `ANTHROPIC_ALIGN_MODEL` (default Haiku). **Revived 2026-09-26** (was dormant 2026-09-21 through today) — `autoPreAlignScan()` (client) now calls it on every queued page in `processAllPendingPages()`, right before `preAlignScan()`'s classical-CV attempt. See that function's own comment and the "AI document scan flow" section below for why: the manual corner editor's real-world crops turned out rough enough, and the classical OpenCV detector unreliable enough on real photos, that an AI-guessed starting point is worth the small extra Haiku call after all.
  - `aiVerifyField` — re-reads a single already-extracted digit field from a tight zoomed crop (`kind`: `digits9`/`date`/`passportNo`). Uses the same accuracy-first `ANTHROPIC_MODEL` as `aiReadDoc`. Returns empty string rather than guessing if illegible. Only call site left is `verifyIdChecksum()`'s one-off idNo retry (schedule-manager.html) — the multi-field case now goes through `aiVerifyFields` below.
  - `aiVerifyFields` (added 2026-09-28) — batched sibling of `aiVerifyField`: one Anthropic call verifying several cropped fields at once (`body.jobs: [{field,kind,image,mediaType}, ...]`, returns `{ok:true, values:{field:value,...}}`). Replaces the client's old `Promise.all` of 2-3 separate `aiVerifyField` calls in `verifyDigitFields()` — see "Optimizations (2026-09-28)" below for why.
  - `aiReadSefach` — narrow sibling of `aiReadDoc` for an extra page after an Israeli-ID primary: the paper ספח or the biometric card back. It skips type detection and the portrait, and shares `IL_ID_FIELD_MAP` with `aiReadDoc`. Always returns `type:"israeli_id"` with `idNo` (cross-check only), address/houseNumber/city, `maritalStatus`, `sex`, `spouse` and children. The card back yields only idNo and sex. The client merge (`ID_CORE_FIELDS`) only fills fields the front left empty, so the card back supplies the sex the front lacks. Used for every extra page in both `processAllPendingPages()` and `onScanFilesSelected()`, where `needMore`/`missingCore` only fire for an `israeli_id` primary. It is faster than `aiReadDoc`, which also returns type/fieldBoxes/photoBox with `max_tokens` 8000 vs 4500.
  - `aiReadHoursTable` (added 2026-10-02, Admin/Roles plan stage 14 — hours-import vision extraction): reads a photographed/scanned timesheet/hours-log and extracts work entries as JSON (`{entries:[{date, inTime, outTime}, ...]}`) — no structured parsing, just raw vision extraction. Client-side caller is entirely responsible for routing this through the approval queue; the function itself never writes anything, so a bad read can't silently poison PunchLog. Uses the accuracy-first `ANTHROPIC_MODEL`, never the cheap model — a misread hour corrupts real payroll. Supplier role is explicitly rejected at the top (returned as an error response, not thrown), per the anti-fraud stage-14 design.
- Hours-import approval queue (added 2026-10-02, Admin/Roles plan stage 14 — anti-fraud boundary explicitly requested by the user: no uploaded hours ever reach payroll without a human approval, and the `supplier` role can never use this at all, to prevent an agency from fabricating its own hours): `savePendingHoursBatch(body, tenantId, auth)` (new POST) writes parsed `{workerId,clientId,date,inTime,outTime}` rows into a new per-tenant `PendingHours_<tenantId>` sheet (same per-tenant-sheet pattern as `PunchLog_<tenantId>`) with `status:'pending'` — throws for `auth.role==='supplier'`, otherwise open to any role (`staff`/`tenant_admin`/`superadmin`) with no permission gate, since nothing financially-relevant happens until approval. `loadPendingHours(tenantId, auth)` (new GET) lists batches grouped by `BatchId` — also blocked for `supplier`, but any other role may view (read-only for `staff`, see client-side gating below). `requirePendingHoursApprover(auth)` — new helper, throws unless `role` is `tenant_admin` or `superadmin` — gates `approvePendingHours(body, tenantId, auth)` and `rejectPendingHours(body, tenantId, auth)` (both new POST). Approving a batch calls the exact same `savePunch()` every other punch goes through (IN+OUT per shift, resolving `workerName` from the tenant's own `Schedule` sheet) — never a parallel write path — tagging `Notes` with `'Imported' + filename` so an approved-import punch is visibly distinguishable from a GPS-verified one; deliberately no GPS/distance fields at all (there's nothing real to put there). Rejecting a batch flips its rows to `'rejected'` and creates nothing. Verified via a Node `vm`-sandboxed test against the real `apps-script/Код.js` source: upload/list/approve/reject all work correctly, a supplier is blocked from every one of the four actions, a plain `staff` login is blocked specifically from approving/rejecting (but not from uploading or listing), approving creates exactly 2 PunchLog rows per shift with no GPS data and the right Notes tag, re-approving an already-approved batch is a no-op, and a rejected batch never touches PunchLog at all.
  - **`aiReadHoursTable(body)`** (new POST action, also blocked for `role==='supplier'` at the `doPost()` dispatch level) — the AI-vision half of the import (a photographed/scanned timesheet); the Excel half is parsed entirely client-side via SheetJS, no AI call. Same accuracy-first `ANTHROPIC_MODEL` as `aiReadDoc`/`aiVerifyField` (a misread digit here corrupts real payroll hours, same reasoning). Returns `{ok:true, entries:[{date,inTime,outTime}]}` and never writes anything itself — the client is responsible for routing the result through `savePendingHoursBatch()`, so a bad AI read can't silently reach PunchLog without going through the same approval queue as every other import.
  - **Client-side** (`schedule-manager.html`): `openHoursImportModal(workerId)` (new `#hoursImportOverlay`/`#hoursImportModal`) — a button in `openWorkerCard()`'s action row, gated by `hasPermission('workers')` (so it respects the same nav permission a `staff` login without `'workers'` already can't reach) — client/object `<select>` (defaults to the worker's own assigned clients) + a file input accepting `.xlsx/.xls/.csv` or any image. `onHoursImportFileSelected(fileOrList)` accepts several files at once (the input is `multiple`, and accepts PDF too). Each page is sent to `aiReadHoursTable` by `parseHoursImagePage()`, all pages in parallel. `submitHoursImportBatch()` tags every parsed entry with the chosen `workerId`/`clientId` and posts the whole set to `savePendingHoursBatch` in one call. In `#sectionAccounting`, a new "Pending hours" block (`renderPendingHours()`, called from `renderAccounting()`) lists only `status==='pending'` batches; Approve/Reject buttons (`approveHoursBatch()`/`rejectHoursBatch()`, calling the matching backend actions and then refreshing both the list and `renderSalary()`) are shown **only** when the logged-in role is `tenant_admin`/`superadmin` — mirrors the server-side `requirePendingHoursApprover()` gate exactly, so a plain `staff` login sees a read-only view of what's pending (including its own uploads) but has no way to self-approve. - Removed the dead `calcSalary` GET/POST endpoint and its `toMins()` helper from `apps-script/Код.js` (mirrored in `google-apps-script.js`) — grep across both HTML files confirmed no client code ever called it; it duplicated (cruder, no shift-grouping-across-midnight, no labour-law tiers) what `groupPunchesIntoShifts()`/`shiftPay()`/`israeliDayPay()` already do client-side.
- `saveWorkerDoc`/`saveWorkerAssets`'s duplicate-file cleanup now uses `folder.searchFiles("title contains '<docNumber>'")` instead of `folder.getFiles()` — the old code fetched metadata for every file in the folder over the Drive API just to check its name locally, an O(n) cost per save that grows with the roster; `searchFiles` lets Drive's own index filter server-side. `docNumber` (`extractDocNumberFromFileName()`) is always a `\d{5,}` digit run, so no quote-escaping risk in the query string. The exact-match check (`extractDocNumberFromFileName(f.getName()) === docNumber`) still runs locally on the (now much smaller) result set, so behavior is unchanged.
- `saveSchedule` now guards `workersJson`/`clientsJson` against Google Sheets' real ~50,000-char-per-cell limit (`CELL_SAFE_LIMIT = 45000`) before writing, returning `{error, tooLarge: true}` instead of letting a cryptic Sheets API exception surface mid-save on a large roster (many `avatarB64` photos). `gsSave()` (schedule-manager.html) shows a clear Russian toast on `json.tooLarge` instead of treating it like a generic failure.
- `aiFillForm101()`'s upload path fires `saveWorkerDoc` (the PDF) and `saveWorkerAssets` (the scan/signature sidecar) concurrently via `Promise.all` instead of one full round-trip after the other — they write to two independent Drive files and don't depend on each other's result. This runs behind a blocking "please wait" overlay for new workers/rescans, so halving the round-trip latency there is directly user-facing. #### AI document scan flow

**Full debugging history moved to `HISTORY.md`** ("AI document scan flow — alignment/crop-tightening history") — that file has the blow-by-blow of every threshold/approach tried and reverted between 2026-09-26 and 2026-09-30. This section states only the current pipeline.

`onScanFileSelected`/`onScanFilesSelected` → **manual corner-adjustment editor** (`renderScanQuadEditor`/`initScanQuad`/`attachQuadDrag`, drag 4 SVG handles) on the raw downscaled photo → `confirmScanQuad()` perspective-warps the quad flat via `warpQuadImage()` (homography math, output capped at 1568px long edge) → the cropped page is **queued**, not processed yet (`window.__pendingScanPages`, `renderPendingPagesPrompt()`) → once the user is done adding pages, `processAllPendingPages()` sends the whole queue through the steps below. **Since 2026-10-01 pages are not processed one after another:** steps 1-2 run for all queued pages concurrently; then the primary page is read, and when it is an Israeli ID still missing core fields, the following pages' `aiReadSefach` reads (`readSefachPage()`) start in the background while the primary's digits are re-verified. Results are still merged in page order with the same `needMore` rule. A blurry page still stops the run at that page, with the same queue/resume semantics. In a mocked-latency test, 2 pages took 6.1s instead of 9.2s. The steps:
1. `autoPreAlignScan()` — cheap Haiku corner detection (`aiDetectAlign`) → `refineQuadCorners()` (local pixel-gradient refinement, search-outward-take-first-qualifying-peak, never the single strongest gradient anywhere in the window) → `warpQuadImage()`, skipped entirely via `_isNearIdentityQuad()` when it would be a lossy no-op.
2. `preAlignScan()` — server-side (`preprocess_scan`, `functions/main.py`) contrast enhance + blur check, on the already-cropped image. Its own classical-CV auto-crop (`_find_document_quad`/`_warp_quad`) is currently **dormant** (client-side tightening already runs first).
3. `aiReadDoc` → digit-field verify (`verifyDigitFields`/`verifyIdChecksum`) → merge across pages (`mergeIsraeliIdFields`/`mergeScanPage`/`rebuildPrimaryFromPages`, shared by both the collect-then-batch and multi-file paths so removing a page always recomputes consistently).
4. `finalTightenPass()` — unconditional final safety net, scans each of the 4 sides **independently** for a real edge (`_scanSideEdge()`, same search-outward-first-qualifying-peak technique as `refineQuadCorners()`), catching any thin background sliver the earlier passes left on an axis they didn't touch.

→ `renderScanPagesPrompt()` → `openWorkerModalFromScan()`.

- The corner editor runs **before** OCR — the user positions the rectangle on the raw photo, no AI-guessed starting rectangle. `renderScanQuadEditor()` waits on `img.decode()` (capped at 1.2s) then one more `requestAnimationFrame` before reading `clientWidth/clientHeight`, falling back to the uncropped original if decode never settles. 4 corner handles (radius 13) plus a white grip bar at each edge's midpoint (`.quad-side-handle`, visual only) let the user drag one corner or slide a whole side. Hit-testing is not on the SVG shapes: `attachQuadDrag()` listens on the whole `#scanEditWrap` (the photo plus a `QUAD_PAD`=18px dark margin, so an edge lying on the photo border can be grabbed from outside) and `quadHitTest()` picks the nearest corner within `QUAD_CORNER_HIT`=36px, else the nearest edge within `QUAD_EDGE_HIT`=32px; pointer capture + `pointercancel` keep touch drags reliable.
- **New scan session reset (fixed 2026-10-01):** `openAiScan()` clears `__aiParsed`, `__aiScanImage`, `__aiPacketOtherPages` and `__aiAvatarB64` along with `__aiPrimaryParsed`. `processAllPendingPages()` only resumes when a primary record AND its `__aiScanImage` exist. Before this, the previous scan's `__aiParsed` made the second scan in the same page session resume the old worker's record. The new page became an extra page of that record, and the review screen crashed at 100% with "Cannot read properties of null (reading 'mediaType')". `renderScanPagesPrompt()` skips empty thumb slots and keeps the remove-button indexes.
- `renderScanProgress(label,pct)` shows real sub-step progress (`#aiScanStage`) through align/enhance/read/verify/tighten, not just start/done.
- **Page kinds (2026-10-01):** `autoPreAlignScan()` returns `aiDetectAlign`'s `kind`, and the multi-file path gets it from `classifyPage()` (all pages in parallel). `extraPageReader(kind)` picks how an extra page is read: `contract`/`other`/`passport` are attached without any AI read, `id_front` gets the full `aiReadDoc` (`readFrontPage()`), and `sefach`/`id_back`/unknown get `aiReadSefach`. A contract/other page is never tried as the primary (`isNonIdKind()`). When a front page follows the ספח, `mergeScanPage()` also fills in the empty `given`/`surname`/`expiry`.
- Multi-file/multi-page uploads (`onScanFilesSelected`) skip the manual crop step entirely. Every page (raw phone photos and PDF pages rendered at 2.5x) is first shrunk by `downscaleForUpload()` (≤1800px JPEG), and each goes to `aiReadDoc` for classification. After an Israeli-ID primary, the following pages' `aiReadSefach` reads are prefetched in parallel with its digit re-check. Pages land in the same `renderScanPagesPrompt()` review screen.
- Worker's own mobile number is a plain modal field (`#wPhone`), not scanned.
- `_preAlignThenOcr()`/`runOcr()` are DORMANT — nothing in the live UI sets `__scanEditPurpose==='preOcr'` anymore; left defined in case an immediate no-batch fast path is wanted again.

#### Form 101 PDF generation (server-side, `functions/main.py`)

`aiFillForm101()` client-side only assembles a JSON payload (name/dob/sex/id/address/marital/health fund/children/employer profile/signature PNG/extra scan pages) and POSTs to `FORM101_FN_URL`; the Python Cloud Function (PyMuPDF) builds the actual PDF bytes and returns `{pdfBase64, fileName}`. See `form101-field-map.md` for the field/rect map.

- **PDF-embed image optimization (added 2026-09-26):** `build_form101_pdf()` shrinks each embedded scan/signature image via `_shrink_for_embed()` (Pillow, downscale to `EMBED_DPI`=150 sized to the actual PDF box + re-encode, JPEG for scans, PNG for the alpha-channel signature) right before `insert_image(..., stream=...)` — deliberately only at this final embed step, never earlier in the scan pipeline, since OCR/digit verification have already run upstream on the full-resolution image by then (shrinking here can't affect field-extraction accuracy, only the generated PDF's file size). `finalize()`'s `doc.tobytes()` also now passes `garbage=4, deflate=True, deflate_images=True, clean=True` for container-level cleanup. The raw, unshrunk scan is still preserved separately in the Drive asset sidecar (`saveWorkerAssets`) for future regeneration.

- Fields are addressed by name on `form101_fillable.pdf`'s own AcroForm markup (`Form101Builder.set_hebrew()`/`set_comb()`/`set_text_centered()`) — there's no from-scratch field creation except `SIG_RECT` (the signature image, which needs a rect since it's an image, not a form field). One field is mapped despite its name: `employer_zeut_num` actually holds the **worker's own** Israeli ID number (verified by position, not name).
- PyMuPDF has no RTL/BiDi shaping — every Hebrew-capable field is corrected via `python-bidi`'s `get_display()`, then the field's auto-generated appearance is blanked and the corrected text is hand-drawn on the page (`_blank_appearance()`/`_draw_rtl_text()`). Comb (digit) fields don't need this — LTR digit runs render fine through PyMuPDF's own appearance.
- Address (`addr_street`/`addr_number`/`addr_city`) and children are filled for both document types (a foreign worker's come from manual entry). Children: 6 template row-slots (`CHILD_FIELD_SUFFIXES`), each child's combined name split on the first space into given/surname; the child ID box takes digits or a foreign passport number (letters kept). All 8-box date combs (worker, child, spouse DOB) go through `_ddmmyyyy()`, which zero-pads `1.2.2018` → `01022018`.
- Spouse, section ו (`fill_spouse()`): `spouse_surname`/`spouse_given_name`, an 8-9 digit ID into `spouse_employer_deductions` (the spouse ID box despite its name, zero-padded to 9), anything else into `spouse_passport_no`, `spouse_dob`, and `SPOUSE_INCOME_CB` (`none`→`cb_p1_22`, `work`→`cb_p1_23`+`cb_p1_24`, `other`→`cb_p1_23`+`cb_p1_25`). A passport worker gets `marital` if set, else `marital_single`.
- **Warm-up ping (2026-10-01):** `fill_form_101`, `preprocess_scan` and `gs_upload_proxy` answer `{"ping":true}` immediately via `_ping_response()`, without doing any work; the proxy never relays a ping to Apps Script. On the client, `warmCloudFunctions(urls)` (`schedule-manager.html`, throttled to once per URL per 4 minutes and stored in `__fnWarm`) pings all three at `startNewScan()`/`rescanWorkerDoc()`, and pings `fill_form_101`/`gs_upload_proxy` in `showWorkerModal()`. A cold instance therefore wakes while the user is still photographing or filling in the form. The scan timing's `enhancePingMs` records that ping.
- `FIELD_RECT_NUDGES` holds small per-field `(dx, dy)` point offsets applied to the actual widget rect for one-off position corrections — add further nudges here rather than re-editing the PDF template by hand.
- `functions/venv` must exist locally before `firebase deploy --only functions` (see Files above); CI builds its own venv fresh and never touches the committed one.

## Troubleshooting

### Worker document (Form 101 PDF/scan) upload fails: "network unavailable" or a session/auth error, worker record still created (fixed 2026-10-01)

**Symptom:** creating or rescanning a worker succeeded (the worker record itself saved fine, autoSave ran), but the Form-101 PDF and scan/signature sidecar never made it to Drive — the blocking upload spinner ended in a "network unavailable"-style error, or an auth/session error telling the manager to log in again, even right after a fresh login.

**Root cause:** `xhrPostJSON()` (added 2026-09-30 for real upload-byte progress — see its own comment) was the only GS_URL caller in the file that explicitly set `Content-Type: application/json` on the request. Every other `fetch(GS_URL, {method:'POST', body:...})` call deliberately omits any explicit Content-Type so the browser defaults to `text/plain` and the request stays a CORS "simple request" (no preflight). Apps Script Web Apps only implement `doGet()`/`doPost()` — there's no `doOptions()` — so a request that DOES trigger a preflight gets its OPTIONS silently blocked by the browser before the real POST is ever sent, surfacing to the caller as a bare "network error" with nothing in the Apps Script `Errors` sheet (the server never saw the request at all). Since `saveWorkerDoc`/`saveWorkerAssets` are the only two calls routed through `xhrPostJSON()`, this broke exactly (and only) the document-upload path while every other GS_URL call kept working normally — the reported symptom.

Separately, `xhrPostJSON()` used raw `XMLHttpRequest`, which never goes through the `window.fetch` wrapper below that detects `SESSION_EXPIRED_ERROR` and retries/cleanly logs out — so on the rarer occasion the session token really was invalid, these two calls surfaced the raw `SESSION_EXPIRED_ERROR` text as a failed-upload error instead of the same retry-then-clean-redirect-to-login flow every other call gets, which is what produced the "auth error, need to log in" variant of the symptom.

**Fix (part 1):** removed the explicit `Content-Type` header from `xhrPostJSON()` (now matches every other GS_URL call), and added the same `SESSION_RETRY_DELAYS_MS`-based retry + `reportAuthFailureXhr()` telemetry + clean session-clear-and-reload flow that `checkExpired()` gives plain `fetch()` calls. Verified via a headless-browser test: `xhrPostJSON()` sends no `Content-Type` header, and a mocked `SESSION_EXPIRED_ERROR` response triggers exactly the expected 2 retries before clearing the session (matching `SESSION_RETRY_DELAYS_MS.length+1` total attempts) rather than surfacing immediately as a raw error.

**Recurred after part 1 (fixed 2026-10-01, part 2):** the "network error" kept happening even with the header removed. Real root cause, missed the first time: per the Fetch/XHR spec, merely **attaching any listener to `xhr.upload`** (e.g. `xhr.upload.onprogress`, which `xhrPostJSON()` did whenever a caller passed an `onProgress` callback) unconditionally forces a cross-origin request into CORS-preflight mode — an entirely separate trigger from request headers, spec'd as the "upload listener flag." Apps Script still has no `doOptions()` to answer that preflight, so it fails exactly the same way, regardless of Content-Type. This means **real byte-level upload progress via `xhr.upload.onprogress` is fundamentally impossible against a bare Apps Script Web App** — no header combination avoids it once an upload listener is attached. `xhrPostJSON()` temporarily dropped the `onProgress` parameter entirely; `saveWorkerDoc`/`saveWorkerAssets`'s progress bar in `aiFillForm101()` used a fake ticker (creeps 20%→85% on a timer while the request is in flight, jumps to 100% on completion) instead of real bytes.

**Real progress restored (2026-10-02) via a Cloud Function proxy:** since Apps Script itself can never answer a CORS preflight, the fix was to stop asking it to — `functions/main.py` gained `gs_upload_proxy()` (same `CorsOptions(cors_origins="*", cors_methods=["post"])` pattern already used by `fill_form_101`/`preprocess_scan`, which DO answer preflight correctly), and `saveWorkerDoc`/`saveWorkerAssets` now XHR-POST to this Cloud Function (`GS_UPLOAD_PROXY_URL`) instead of `GS_URL` directly. The browser can freely attach `xhr.upload.onprogress` against the Cloud Function (its preflight gets answered), and the Cloud Function itself does a plain server-to-server `requests.post()` to Apps Script — no browser involved on that leg, so no CORS applies at all. `xhrPostJSON()` regained its `onProgress` parameter, but only attaches the upload listener when one is actually passed — every other GS_URL caller (which never passes `onProgress`) still never touches `xhr.upload`, so nothing else is newly exposed to the preflight trigger. Verified via headless-browser tests: real progress ticks flow through for `GS_UPLOAD_PROXY_URL` calls with `onProgress` passed; a call with no `onProgress` never touches `xhr.upload` even under a mock XHR that throws on access; the full `aiFillForm101()` upload path targets `GS_UPLOAD_PROXY_URL` for both `saveWorkerDoc`/`saveWorkerAssets`.

### Session-expiry false logouts — ROOT CAUSE FOUND AND FIXED (2026-10-01)

The `Errors` sheet showed `authFailure: action=logError, attempt=2, outcome=logged-out`. `reportError()` (the client's `window.onerror`/`unhandledrejection` telemetry) sent `logError` with **no session token**, `doPost()` required auth for it and answered "session expired", and the `window.fetch` wrapper treated that like a real expiry: two retries, still without a token, then logout. So **any client-side JS error or unhandled promise rejection logged the user out**, and the error itself was never recorded. That fits every "kicked to login mid-scan" report (a scan is where transient errors/rejections are most likely), including the OCR-burst case below that had stayed open. Fixed three ways: `logError` is accepted with just `API_SECRET` server-side, `reportError()` sends `secret` + token, and the fetch wrapper skips logout handling for `logError`/`authFailure`/`login`. Verified with a headless test where the server still answered "session expired" to `logError`: the user stayed logged in. Also checked in a Node vm against the real `Код.js`: `logError` with the secret and no token is recorded, and without the secret it is rejected. The sections below are the earlier investigation, kept for history.

### Session-expiry false logouts during document scan (reported 2026-09-27; the `saveWorkerDoc`/`saveWorkerAssets` upload case root-caused and fixed 2026-09-30 — see below; the earlier mid-scan/OCR-call case remains open)

**Symptom:** a manager gets kicked to the login screen ("as if the session dropped") specifically while uploading a scan — reported to happen right after a *fresh* login (not near the real 6h token TTL) and right after selecting/uploading the photo (before OCR review, i.e. the very first `aiReadDoc` round-trip of the scan — most consistent with the multi-file/PDF path, `onScanFilesSelected()`, which calls `aiReadDoc` immediately per page with no manual-crop step in between).

**What was ruled out:** real 6h session expiry (happens on a fresh login too); a string mismatch between the client's `SESSION_EXPIRED_ERROR` and the backend's literal error text (byte-compared, identical); `SESSION_SECRET` rotation (would break every request, not just scan ones); request/JSON-parse corruption from a large base64 image (would surface as a generic parse error, not the literal "session expired" text the user actually sees).

**Root cause not yet confirmed** — a real production recurrence with server-side telemetry is needed. Two things ship in the meantime:
- **Widened retry** (`schedule-manager.html`'s `fetch` wrapper, was: retry once immediately, added 2026-09-21): now retries up to twice more (3 attempts total) before giving up, with a short delay before the last retry (`SESSION_RETRY_DELAYS_MS = [0, 500]`) — a single immediate retry wasn't enough to clear whatever transient hiccup this is, and a scan's burst of parallel/sequential `aiDetectAlign`/`aiReadDoc`/`aiVerifyField` calls is exactly the worst case for a spurious mid-flow logout to lose real user progress.
- **`authFailure` diagnostic** (new POST action, unauthenticated by design — see Backend section) — every time a GS_URL call gets rejected as "session expired," the client fire-and-forget-reports the failing action name, which retry attempt it was, and the outcome (`retrying` vs `logged-out`) to the `Errors` sheet. **Next real recurrence: check the `Errors` sheet for `source=authFailure` rows** — the `failedAction` there is the actual trigger (confirm it's `aiReadDoc`/`aiDetectAlign`/etc. as suspected, not something unrelated), and whether it recovers on retry (`outcome=retrying` followed by a normal request) vs. genuinely never recovers (three `retrying`/`logged-out` rows in a row) is the key fact still missing to actually root-cause this.
- **Richer `authFailure` telemetry + fresh-token retry (2026-10-01):** the client now also sends the token it used (`sentToken`), `bodyKB`, `hasSession` and `viaProxy` (XHR/proxy path); the server's `_tokenRejectReason()` logs *why* the token was rejected (`missing` / `malformed` / `bad-signature` / `expired Nmin ago` / `valid-now`) and never logs the token itself. Retries after a session-expired response now rebuild the request with the **currently stored** token (`withCurrentToken()` in the fetch wrapper, same in `xhrPostJSON()`), not the one the original request was built with. On the next recurrence, the `Errors` sheet row's `reason=` tells which case it is: `missing` means the token never reached Apps Script (a proxy/body problem), `valid-now` means a transient server-side rejection.
- **`aiVerifyFields` batching (2026-09-28)** — see "Optimizations (2026-09-28)" above: `verifyDigitFields()` no longer fires 2-3 concurrent `aiVerifyField` calls per page, cutting one real source of concurrent Apps Script executions during a scan burst. If Apps Script's per-account concurrent-execution quota was ever a contributor here, this alone may reduce (not necessarily eliminate) how often the issue shows up — still worth checking `authFailure` rows on any future recurrence rather than assuming this fixed it.

**Sliding session expiration (added 2026-09-30) — defensive improvement, turned out NOT to be what was wrong:** first shipped on the theory that the 6h TTL (`SESSION_TTL_MS`) is a hard wall counted from **login time** and never extended by activity. That theory didn't hold up — a full scan→review→upload session takes on the order of 2-3 minutes in practice, nowhere near 6 hours, so an unextended TTL couldn't be the actual cause. Kept anyway (still a reasonable thing to have — a session genuinely near its 6h wall no longer drops mid-task for unrelated reasons), but superseded by the confirmed root cause below as the explanation for this specific report. `requireAuth()` (`apps-script/Код.js`) reissues a fresh token on every authenticated request, attached to the response as `refreshedToken`/`refreshedExpiresAt` via `_withRefreshedToken()`; client-side `applyRefreshedToken(json)` (`schedule-manager.html`) picks it up in both the `window.fetch` wrapper and `xhrPostJSON()`'s `onload`; `supplier-portal.html` got the same pickup via its own small `window.fetch` wrapper.

**Actual root cause, confirmed and fixed (2026-09-30):** the `Errors` sheet's `authFailure` diagnostic (finally checked after a real recurrence) showed `action=saveWorkerDoc, outcome=retrying` — i.e. the very FIRST attempt of the upload call was already being rejected as "session expired," which a stateless HMAC token check has no legitimate reason to do seconds after a fresh, successful scan. The real bug: `xhrPostJSON()` (used only for `saveWorkerDoc`/`saveWorkerAssets`, which since 2026-10-02 post to `GS_UPLOAD_PROXY_URL`, a Flask-based Cloud Function, not Apps Script directly) deliberately sends no explicit `Content-Type` header — a rule that made sense when it posted straight to Apps Script (which parses `e.postData.contents` as JSON regardless of Content-Type) but was never revisited after the target changed to a Flask app. The browser then defaults to `Content-Type: text/plain`, and Flask/Werkzeug's `request.get_json(silent=True)` **without `force=True` refuses to parse a body whose Content-Type isn't `application/json`, silently returning `None`** — so `gs_upload_proxy()`'s `payload = req.get_json(silent=True) or {}` evaluated to `{}` on every single call: no `action`, no `token`. That empty object is what actually got forwarded to Apps Script (`requests.post(GS_URL, json=payload)`), whose `doPost()` then called `requireAuth({})` — `body.token` is `undefined`, so it threw "session expired," exactly matching the reported symptom, on an exactly-valid, seconds-old token that simply never arrived. Fixed in two places: `functions/main.py`'s `gs_upload_proxy()` (and, as defense in depth, `fill_form_101`/`preprocess_scan` too) now calls `req.get_json(silent=True, force=True)`, parsing the body regardless of Content-Type; `xhrPostJSON()` also restores an explicit `Content-Type: application/json` header, but only when posting to `GS_UPLOAD_PROXY_URL` specifically (never to bare `GS_URL`, where it would reintroduce the CORS-preflight problem documented in the entry above this one — Apps Script still has no `doOptions()`). Verified with a Flask/Werkzeug test: a `text/plain` body reproduces the empty-`{}`-parse bug under `get_json(silent=True)` without `force`, and parses correctly with `force=True`; an `application/json` body (what `fill_form_101`'s client call already sends) behaves identically either way, confirming the fix is safe for every existing caller. **This closes the upload-specific case.** The original 2026-09-27 report (a kickout during the OCR burst itself — `aiReadDoc`/`aiDetectAlign`/`aiVerifyField`, which all go straight to `GS_URL`, never through this proxy) is a different code path and remains unconfirmed — if it recurs, check `authFailure` rows for a `failedAction` other than `saveWorkerDoc`/`saveWorkerAssets` before assuming this same fix covers it.

### New worker appears, then disappears from the list; its Form 101 stays in Drive (fixed 2026-10-01)

Cause: the 2026-10-01 login-speed change grew `SCHEDULE_HEADERS` to 8 columns (`workerCount`/`clientCount`), but `saveSchedule()` still wrote its own 6-value row into an 8-column range, so **every save of an existing firm threw** ("The data has 6 but the range has 8") and nothing reached the sheet. Workers lost between the two fixes have to be scanned again, or re-entered; their Form 101 is in Drive.

### "Could not load from GS" after picking a file on a phone (fixed 2026-10-01)

On a phone, opening the camera/gallery to pick a file can make the browser drop and reload the tab; the first `loadSchedule` right after coming back often failed, and `gsLoad()` turned any failure (network, Apps Script HTML error page, quota) into an immediate "Could not load from GS" toast. ### "Deploy to Apps Script" CI fails with `invalid_grant` / `invalid_rapt`
