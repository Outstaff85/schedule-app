# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is the index: the rules that apply everywhere, and which `docs/*.md` file to read before touching which part of the code.

**Session language:** the user communicates in Russian. Claude's own conversational output (explanations, status updates, questions) should be in Russian throughout — independent of what language the app's UI/code is in.

**UI text language:** every UI text in the code is English. The UI is shown in the language picked with the page's one Language button (English by default; remembered per device and on the user's account; English, Hebrew, Russian) **only through the dictionaries** `i18n/<lang>.json`: texts go through `tr()` / `data-i18n`, never a translated string in the code; Hebrew must stay complete (`npm run test:i18n`), Russian is set up but not translated yet; the layout stays left to right in every language (docs/translations.md). **Everything that goes into Form 101 is Hebrew** (per user request 2026-09-30): the labels of every field that feeds the form (worker modal: names, ID, sex, marital status, health fund, address, income types, children, spouse block; firm profile: employer name, deductions file, phone, address) and the values printed in it. The one exception is a **foreign-passport worker's (and a foreign spouse's) given name and surname, which stay in Latin letters** as printed in the passport; every other printed value is Hebrew. There is no Russian anywhere in the repo — UI, the error texts the functions return, code comments, docs (translated to English on 2026-10-05, per user request); don't add any. The exceptions: the Russian dictionary `i18n/ru.json` (and the language's own name in `I18N_LANGS`), and data — the hours import still accepts the Russian column names for Date / In / Out (`parseHoursExcelFile`).

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served from Firebase Hosting (project `schedule-odinson`). The app is moving to **React + Vite + TypeScript + Tailwind + shadcn/ui** page by page (docs/react-migration-plan.md; stage 0 — the build — is done). `npm run build` makes `dist/`, which Hosting serves: the new pages built by Vite from `src/`, plus the **old pages** — self-contained HTML files with inline `<style>`/`<script>` at the repo root — copied in unchanged (docs/build.md). Until a page's stage moves it, it stays an old page.

Multi-tenant: a super-admin creates firms (tenants), each with its own logins and isolated data. Roles: `superadmin`, `tenant_admin`, `staff` (per-section permissions), `hr` (per-section permissions; by default only the workers assigned to it, `hrId` — docs/hr.md), `supplier` (own workers only), `client` (the client portal: its own workers' hours at its site, by its ticks — docs/client-portal.md). HR, supplier and client review hours the same way (hours ticks, per-day approve / dispute / fix — docs/hours-review.md).

The backend is **Firestore + Firebase Storage + Cloud Functions**, and nothing else. The original Google Apps Script / Google Sheets backend was removed on 2026-10-03 (see docs/history.md); don't add calls to it.

## Commands

- Install and build (repo root, Node ≥ 20.19): `npm ci`, then `npm run dev` (dev server: the old pages and the new ones at their Hosting paths), `npm run build` (typecheck + Vite + the old pages copied into `dist/`), `npm run typecheck`, `npm run check:build` (docs/build.md). Local preview of the built site: `npm run build && firebase emulators:start --only hosting`; the old pages can still be opened directly as files.
- Payroll (old code vs the module): `node tests/payroll/compare.test.mjs`; after editing `src/lib/payroll.ts`: `npm run build:payroll`.
- Rules tests: `cd tests/rules && npm install && npm test`. Functions tests: `cd tests/rules && PYTHON=<python with firebase-admin, pytest> npm run test:auth`. Browser tests (after `npm run build` at the root; they run on `dist/`): `cd tests/e2e && npm install && PYTHON=<same python> npm test`. All of them run on every PR into `main` (`tests.yml`); a red check blocks the merge (docs/tests.md). A new feature adds its check in the same PR.
- Deploying `functions/` by hand needs `functions/venv` first (`python -m venv venv && pip install -r requirements.txt`); CI builds its own.
- **Deploy = merge to `main`.** GitHub Actions: on every push to `main`, `npm ci && npm run build` and the `dist/` check, then Hosting serves `dist/` (a failed build deploys nothing); functions and rules on pushes touching their paths (details in docs/backend.md, docs/build.md).

### Git workflow (enforced by hooks in `.claude/settings.json`)

- **`My_Work_Befor_PR`** is the standing work branch — check it out (or resume the cloud session on it) at the start of work instead of `main`. Don't create ad-hoc branches per session. (A cloud session that is given a designated branch uses that one.)
- A `PostToolUse` hook auto-commits and pushes every file edit to the **current branch** (`git push origin HEAD`). This only fires in a session whose working directory *is* this repo at session start.
- A `PreToolUse` hook blocks any `git push` that force-pushes, targets `main` by name, or runs while the current branch is `main`.
- A `SessionStart` hook (`.claude/hooks/session-start.sh`) runs `git fetch` and fast-forwards the checkout — to `origin/main` when the branch has no commits of its own beyond it, else to its own `origin/<branch>` — never merging, and leaving a dirty tree or a branch with unmerged commits alone; then injects the result + `git status --short` + current branch as context.
- On a Windows PC, `scripts/install-local-sync.ps1` registers a scheduled task running the same script at logon and every 15 min (hidden, via `scripts/local-sync-hidden.vbs`; log in `.git/local-sync.log`; `-Uninstall` removes it), so a local clone stays in sync without Claude Code running.
- A `PostToolUse` hook on `gh pr create*` or the GitHub MCP `create_pull_request` tool checks the PR's diff against CLAUDE.md and `docs/*.md` and updates them via an agent.
- **"Deploy" means: open a PR from the work branch into `main` covering everything accumulated since the last one, then merge it — merging is what triggers the real deploy.** Never push/reset directly to `main`. Batch accumulated changes into one PR per deploy request rather than one PR per edit.
- **Never merge a PR without asking the user first.** Pushing to the feature branch needs no confirmation; merging to `main` always does. Exceptions, approved by the owner in advance: the stages of the redesign plan in docs/redesign.md (docs/redesign.md → Auto-continue) and the stages of the React migration in docs/react-migration-plan.md (one stage per session, started every 2 hours by the scheduled task "React migration autopilot"; docs/react-migration-plan.md → Auto-continue) — each is merged by its session once its CI is green.

## Rules that apply everywhere

- **XSS:** every `${...}` that puts data into HTML goes through `esc()`. Each page has its own identical `esc()`; keep them the same.
- **New code goes to the new stack:** React components and TypeScript modules in `src/` (strict TypeScript). **Check `src/components/ui` and `src/components/shared` first (docs/components.md); write a new component only when nothing there fits**, and add it to docs/components.md and the `/next` gallery. Colors and sizes only from the tokens (`bg-plate`, `text-muted-foreground`, `rounded-lg` — never a raw color or a token redefined); what `og.css` already draws is used through its class. A new shadcn/ui component goes into `src/components/ui` (`npx shadcn add` where the registry is reachable, else written from the shadcn source) and is restyled once to Odinson Glass. Every UI text through `tr()` from `src/lib/i18n.tsx`; icons from `@tabler/icons-react`. The templates below hold in React too, through the shared pieces (`Window`, `Plate`, `PagedList`, `undoDelete`, Select mode). A new page follows docs/build.md → Adding a new page and gets a browser check.
- **The old page keeps its style until its stage moves it:** in `schedule-manager.html` and its `.js` files everything stays global functions/consts in one inline `<script>` (plus the two lazy-loaded `.js` files, which also run as globals) — no `import`, no build; work there (fixes, features, the redesign stages) goes on as before and follows the rules below. Every rule below that names an old-page function (`esc()`, `tr()`, `renderPagedList`, the duplicated list…) is about the old pages; its React counterpart arrives with the stage that moves the page.
- **Modals close the same way everywhere (template):** a tap anywhere outside a modal (the dark backdrop) closes it — one document handler for every `.overlay` (docs/app-core.md → Layout). Modals have no ✕ and no Cancel / Close button; a modal whose closing must undo or save something sets `overlay.__onUserClose` (the worker window saves itself this way and has no Save button). A new modal follows this and adds no close button or backdrop handler of its own.
- **Tap reads, double click / long press edits (template):** a single tap on a list item or card opens its card, or its edit form when it has no card; a double click (computer) or a long press (phone) opens the edit form; a card that only reads (the worker card) also has a ✎, and a line that also does something else (a firm: open it) carries a ✎ at its right; controls inside keep their own job (`tapEdit` / `longPress` / `isPlainTap`, class `.tap-edit`, docs/app-core.md → Layout). On a phone a window closes with a swipe down too, and the page behind it doesn't scroll. A window opened from another window goes back to it when it closes (`__returnTo`, manager app). A new list, card or modal follows this.
- **List look (template, variant 3 → Odinson Glass plates):** figures as text on top, sections with a count, items as plates with a colored bar on the left, no letters avatar (`t3Line`, `.t3-line`); row actions under a bare ⋮ (`o.menu`) and a swipe (`o.swipe`), Delete never asks — the Undo snack (`undoDelete`), a Select button above the list that shows the tick boxes and Select all (`startSelect`); a create button (New, New user, New firm…) is plain glass — `.og-new` on the button (`.gbtn.og-new` in `og.css`); on a phone windows open from the bottom (docs/app-core.md → Layout). The Schedule tab too: a line per worker, its days opened under it.
- **Short fields in pairs (template):** two short fields share a line in a `.field-row` (phone and computer); long text fields stay one per line (docs/app-core.md → Layout).
- **Checkboxes are tiles (template):** a set of checkboxes is a `.check-grid` of `label.check-chip` tiles, a long form is split by `.form-section` headings — the same on a phone and a computer (docs/app-core.md → Layout). New forms follow this.
- **Lists page by 10:** every list that can grow (workers, clients, suppliers, firms, users, punches, errors, timings, pending hours, salary and rate tables, documents, …) is drawn with `renderPagedList` (docs/app-core.md → Long lists). It shows 10 rows, and the next 10 only when the user scrolls to the end or taps "Show more". A new list follows the same rule. Totals rows always cover every item.
- **Duplicated on purpose:** `esc()` (the manager app; the new pages' one copy is `src/lib/utils.ts`), `reportError`, `showToast`, `getPunchLog`/`savePunchLog` (the manager app and `src/punch/core.ts`), `loadFirestoreBackend()` (the new pages: `loadBackend()`, `src/lib/backend.ts`), the payroll wrappers (the shift pairing and the pay functions are one copy, `src/lib/payroll.ts` → `payroll.js`; each old page keeps one-line wrappers with the old names that pass its own `clients` — docs/accounting.md → Payroll module; a wrapper change is mirrored), the supplier commission (the daily commission rule — `commissionFor` in the manager app, `myCommission` in `src/supplier/money.ts`; the supplier's own rate by date — `supplierRateOn` / `supplierShiftCommission` in the manager app, `myRateOn` / `myShiftCommission` in `src/supplier/money.ts`), the paging helper (`renderPagedList` in the manager app — `PagedList` in the new stack), the new version check (`startVersionWatch` / `showNewVersionBar` in the manager app — `useVersionWatch` in the new stack), the greeting (`GREET_ICONS`, `GIC_CLOUD`, `WX_ICONS`, `weatherIconHtml`, `partOfDay`, `greetingHtml` and the `.gic` / `.gtemp` styles, the manager app and `src/punch/greeting.ts`), the translation core (`I18N_LANGS`, `tr`, `applyI18n`, `uiLocale`, `loadI18n`, `storedLanguage`, `setLanguage`, in the manager app; the new pages' one copy is `src/lib/i18n.tsx`) and the Language button and sheet (`I18N_LANG_EN`, `syncLangButtons`, `openLangSheet`, `closeLangSheet`, `renderLangList`, `pickLanguage`, `placeLangButton` in the manager app — `LanguageButton` in the new stack), the `.gbtn` shine handler (the manager app and `src/punch/main.tsx` — the Odinson Glass CSS itself is not duplicated: it lives once in `og.css`), the new-worker badge (`newWorkerBadgeHtml` in the manager app — `NewBadge` in the new stack), the hours-review lines and states (`hrvMonthDays` / `hrvDayState` / `hrvSchedDay` in `hours-review.js`, `monthDays` / `dayState` / `planned` in `src/hours-review/hours.ts`, and `hourDayLines` in the manager app build the same `worker|day|ins|outs` lines), and the old pages' template pieces whose React counterparts are in `src/components/` (the account menu `toggleAccountMenu` — `AccountMenu`; `t3Line` — `Plate`; the list pieces `openRowMenu` / swipe / `undoDelete` / `startSelect` — `Plate`, `undoDelete`, `useSelection`; the editor section plates `ogSections` — `Accordion`; the modal backdrop close and `tapEdit` / `longPress` — `Window`, `Plate`), exist in more than one place. A fix in one copy must be mirrored in the others.
- **Payroll:** hours and pay only through the canonical functions in docs/accounting.md (a shift's pay: `shiftPayFor`, which covers hourly and daily pay) — never a second calculation. Their one copy is `src/lib/payroll.ts`; a change there is followed by `npm run build:payroll` (the committed `payroll.js` the old pages load) and must keep `tests/payroll` green — never edit `payroll.js` by hand. Supplier commission and client billing are separate figures that never change a worker's pay.
- **Firm data isolation:** a firm sees only its own data; an own-workers HR login sees only the workers whose `hrId` is its uid and their punches (rules + `hrOnly()` queries), and never changes a worker's `hrId`; a supplier never receives client billing, GPS, a worker's punch-link token or file links, and receives its own workers' pay inputs (rates, pay mode) only with "Sees own workers' pay" (claim `pay`, on by default; server-side allow-lists, docs/supplier-portal.md); an HR never gets the full Accounting tab — its Accounting section (off by default) shows only its own workers' pay and its commission; a client login (the client portal) sees only its own workers' names and shifts at its site, by its ticks, through the `hours` function — never pay, rates, suppliers, GPS, documents or tokens, and no client-facing surface shows supplier data.
- **Form 101:** see the language rule above; field positions only via docs/form101-field-map.md.
- **AI prompts** live in `functions-auth/ai_prompts.json`; `tests/auth/test_ai.py` checks every request against `tests/auth/ai_golden.json`, so a prompt edit also updates that file (docs/backend.md).
- **Uploads:** new upload features go through the shared helpers (`filesToUploadPages`/`fileToUploadPages`/`downscaleForUpload`/`fileForStorage`) and send per-page requests in parallel (docs/scan.md).
- **Parallel AI calls:** a feature that sends several AI requests starts the independent ones at once (`Promise.all`, one request per page or field batch, merged in page order); a Cloud Function that receives such calls is declared with `cpu=1`, `concurrency=20` and keeps no shared per-request state (docs/backend.md → Parallel AI calls). **When a task adds or changes a feature with several AI or server calls that could use this pattern but doesn't yet, Claude points it out in chat and proposes applying it (what would run in parallel, which function settings) before writing the code — don't apply it silently, don't skip it silently.**
- **Icons:** the old pages use a self-hosted subset of Tabler Icons (`icons/`; the new stack imports them from `@tabler/icons-react`); a new `ti-<name>` needs `python tests/icons/build.py` and `npm run test:icons` passing (docs/app-core.md → Fonts and icons).
- **Service worker:** when `service-worker.js` changes, bump its `CACHE` version (now `schedule-mgr-v129`), or clients keep stale files.
- **What Hosting serves:** `firebase.json` → `hosting.public` is `dist`; only `npm run build` fills it, and `scripts/static-files.mjs` decides which old files are copied in — it must keep out `functions/`, `functions-auth/`, `tests/`, `docs/`, `src/`, `*.md`, the rules files, the config files and every dot file (`tests/build/check.js` fails otherwise). The Hosting `ignore` list keeps `functions/**` (otherwise the venv is uploaded publicly), `functions-auth/**`, `tests/**`, `docs/**`, `*.md` and the rules files as a second guard.
- **Secrets** live in Secret Manager (`ANTHROPIC_API_KEY`, `OPENWEATHER_API_KEY`) — never in the repo, never asked for in chat.

## Keeping the docs true

When a change alters what a documented function does (parameters, control flow, data shape, who may call it), update the matching `docs/*.md` file in the same PR, describing only the current state. A debugging trail or a reverted approach goes to docs/history.md. Add a new `docs/*.md` file (and a row above) for a new tab or module rather than growing this file.
