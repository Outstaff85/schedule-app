# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is the index: the rules that apply everywhere, and which `docs/*.md` file to read before touching which part of the code.

**Session language:** the user communicates in Russian. Claude's own conversational output (explanations, status updates, questions) should be in Russian throughout — independent of what language the app's UI/code is in.

**UI text language:** every UI text in the code is English. The UI is shown in the language picked with the page's one Language button (English by default; remembered per device and on the user's account; English, Hebrew, Russian) **only through the dictionaries** `i18n/<lang>.json`: texts go through `tr()` / `data-i18n`, never a translated string in the code; Hebrew must stay complete (`npm run test:i18n`), Russian is set up but not translated yet; the page content (lists, plates, tables, windows, forms) stays left to right in every language — in Hebrew only the manager app's frame is mirrored: the side menu moves to the right and the title bar reverses (logo and breadcrumb on the right, the account on the left; react-migration-plan.md → Additions from the UI audit, V7) (docs/translations.md). **Everything that goes into Form 101 is Hebrew** (per user request 2026-09-30): the labels of every field that feeds the form (worker modal: names, ID, sex, marital status, health fund, address, income types, children, spouse block; firm profile: employer name, deductions file, phone, address) and the values printed in it. The one exception is a **foreign-passport worker's (and a foreign spouse's) given name and surname, which stay in Latin letters** as printed in the passport; every other printed value is Hebrew. There is no Russian anywhere in the repo — UI, the error texts the functions return, code comments, docs (translated to English on 2026-10-05, per user request); don't add any. The exceptions: the Russian dictionary `i18n/ru.json` (and the language's own name in `I18N_LANGS`), and data — the hours import still accepts the Russian column names for Date / In / Out (`parseHoursExcelFile`).

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served from Firebase Hosting (project `schedule-odinson`). The app is built on **React + Vite + TypeScript + Tailwind + shadcn/ui** (docs/react-migration-plan.md — the migration is done, stages 0–7). `npm run build` makes `dist/`, which Hosting serves: the pages built by Vite from `src/`, plus the **manager page** `schedule-manager.html` — an HTML file with inline `<style>`/`<script>` at the repo root, copied in unchanged — whose every tab and window is React (`assets/manager.js`); the page itself keeps the frame, the login and the data layer the React pieces call through `ManagerBridge` (docs/build.md).

Multi-tenant: a super-admin creates firms (tenants), each with its own logins and isolated data. Roles: `superadmin`, `tenant_admin`, `staff` (per-section permissions), `hr` (per-section permissions; by default only the workers assigned to it, `hrId` — docs/hr.md), `supplier` (own workers only), `client` (the client portal: its own workers' hours at its site, by its ticks — docs/client-portal.md). HR, supplier and client review hours the same way (hours ticks, per-day approve / dispute / fix — docs/hours-review.md).

The backend is **Firestore + Firebase Storage + Cloud Functions**, and nothing else. The original Google Apps Script / Google Sheets backend was removed on 2026-10-03 (see docs/history.md); don't add calls to it.

## Commands

- Install and build (repo root, Node ≥ 20.19): `npm ci`, then `npm run dev` (dev server: every page at its Hosting path), `npm run build` (typecheck + Vite + the manager page and its files copied into `dist/`), `npm run typecheck`, `npm run check:build` (docs/build.md). Local preview of the built site: `npm run build && firebase emulators:start --only hosting`.
- Payroll (a frozen snapshot of the old code vs the module): `node tests/payroll/compare.test.mjs`; after editing `src/lib/payroll.ts`: `npm run build:payroll`.
- Accounting (the old tab's figures vs `src/manager/accounting.ts`): `node tests/accounting/compare.test.mjs` (`npm run test:accounting`).
- Rules tests: `cd tests/rules && npm install && npm test`. Functions tests: `cd tests/rules && PYTHON=<python with firebase-admin, pytest> npm run test:auth`. Browser tests (after `npm run build` at the root; they run on `dist/`): `cd tests/e2e && npm install && PYTHON=<same python> npm test`. All of them run on every PR into `main` (`tests.yml`); a red check blocks the merge (docs/tests.md). A new feature adds its check in the same PR.
- Deploying `functions/` by hand needs `functions/venv` first (`python -m venv venv && pip install -r requirements.txt`); CI builds its own.
- **Deploy = merge to `main`.** GitHub Actions: on every push to `main`, `npm ci && npm run build` and the `dist/` check, then Hosting serves `dist/` (a failed build deploys nothing); functions and rules on pushes touching their paths (details in docs/backend.md, docs/build.md).

### Git workflow (enforced by hooks in `.claude/settings.json`)

- **`My_Work_Befor_PR`** is the standing work branch — check it out (or resume the cloud session on it) at the start of work instead of `main`. Don't create ad-hoc branches per session. (A cloud session that is given a designated branch uses that one.)
- No hook commits or pushes automatically: commit and push deliberately (the old auto-commit/push hook is archived in `archive/claude-hooks/`).
- A `PreToolUse` hook (`.claude/hooks/push-guard.py`) blocks any `git push` that force-pushes (`-f`, `--force*`, a `+refspec`), targets `main`, or runs while the current branch is `main` — every push in the command is checked, `git -C <dir> push` included.
- A `SessionStart` hook (`.claude/hooks/session-start.sh`) runs `git fetch` and fast-forwards the checkout — to `origin/main` when the branch has no commits of its own beyond it, else to its own `origin/<branch>` — never merging, and leaving a dirty tree or a branch with unmerged commits alone; then injects the result + `git status --short` + current branch as context. The same script also runs as a `UserPromptSubmit` hook (`session-start.sh UserPromptSubmit`), so a live session picks up GitHub changes before every message; there it runs at most once per 5 min (`.git/claude-sync-at`) and stays silent unless the checkout was fast-forwarded or a warning (dirty tree, or own commits while `main` moved on) differs from the last one given (`.git/claude-sync-note`).
- On a Windows PC, `scripts/install-local-sync.ps1` registers a scheduled task running the same script at logon and every 15 min (hidden, via `scripts/local-sync-hidden.vbs`; log in `.git/local-sync.log`; `-Uninstall` removes it), so a local clone stays in sync without Claude Code running.
- A `PostToolUse` hook on the GitHub MCP `create_pull_request` tool checks the PR's diff against CLAUDE.md and `docs/*.md` and updates them via an agent.
- **"Deploy" means: open a PR from the work branch into `main` covering everything accumulated since the last one, then merge it — merging is what triggers the real deploy.** Never push/reset directly to `main`. Batch accumulated changes into one PR per deploy request rather than one PR per edit.
- **Before opening a PR, run the Tests workflow on the branch and open the PR only once it is green.** Pushes to a branch without a PR start no tests (`tests.yml` runs on pull requests), so start it by hand: `workflow_dispatch` of `tests.yml` with `ref` = the branch (GitHub MCP `actions_run_trigger`, method `run_workflow`). A red run is fixed on the branch and run again; a flaky check is made robust, never skipped. Then open the PR — its own run tests the same code.
- **Never merge a PR without asking the user first.** Pushing to the feature branch needs no confirmation; merging to `main` always does. Exceptions, approved by the owner in advance: the stages of the redesign plan in docs/redesign.md (docs/redesign.md → Auto-continue) and the stages of the React migration in docs/react-migration-plan.md (one stage per session, started every 2 hours by the scheduled task "React migration autopilot"; docs/react-migration-plan.md → Auto-continue) — each is merged by its session once its CI is green.

## Rules that apply everywhere

- **XSS:** every `${...}` that puts data into HTML goes through `esc()` — the manager page's own and `src/lib/utils.ts`'s are identical; keep them the same.
- **New code goes to the new stack:** React components and TypeScript modules in `src/` (strict TypeScript). **Check `src/components/ui` and `src/components/shared` first (docs/components.md); write a new component only when nothing there fits**, and add it to docs/components.md and the `/next` gallery. Colors and sizes only from the tokens (`bg-plate`, `text-muted-foreground`, `rounded-lg` — never a raw color or a token redefined); what `og.css` already draws is used through its class. A new shadcn/ui component goes into `src/components/ui` and is restyled once to Odinson Glass. **Always run `npx shadcn add <name>` first** (owner, 2026-10-18) — only when the task needs a component that `src/components/ui` / `src/components/shared` don't have, not at session start; when it works, tell the owner in chat (and in the PR) which component was taken from shadcn; writing it by hand from the shadcn source is allowed only when that command fails (the registry `ui.shadcn.com` not reachable); then say so in chat and in the PR, with the error. Every UI text through `tr()` from `src/lib/i18n.tsx`; icons from `@tabler/icons-react`. The templates below hold in React too, through the shared pieces (`Window`, `Plate`, `PagedList`, `undoDelete`, Select mode). A new page follows docs/build.md → Adding a new page and gets a browser check.
- **The manager page's own script keeps its style:** in `schedule-manager.html` and `scan-pipeline.js` everything stays global functions/consts in one inline `<script>` — no `import`, no build. It holds only the frame, the login, the map picker, the scan window and the bridge's actions (the data layer is `src/manager/data/` → `manager-core.js`); a new screen, tab or window is React in `src/manager/`, reading data and running actions through `ManagerBridge` (docs/build.md → The manager's React pieces). A rule below that names a page function (`renderPagedList`, `t3Line`…) is about the page's own lists (the bell, the More sheet).
- **Modals close the same way everywhere (template):** a tap anywhere outside a modal (the dark backdrop) closes it — one document handler for every `.overlay` (docs/app-core.md → Layout). Modals have no ✕ and no Cancel / Close button; a modal whose closing must undo or save something sets `overlay.__onUserClose` (the worker window saves itself this way and has no Save button). A new modal follows this and adds no close button or backdrop handler of its own.
- **Tap reads, double click / long press edits (template):** a single tap on a list item or card opens its card, or its edit form when it has no card; a double click (computer) or a long press (phone) opens the edit form; a card that only reads (the worker card) also has a ✎, and a line that also does something else (a firm: open it) carries a ✎ at its right; controls inside keep their own job (`Plate`, docs/components.md). On a phone a window closes with a swipe down too, and the page behind it doesn't scroll. A window opened from another window goes back to it when it closes (`__returnTo`, manager app). A new list, card or modal follows this.
- **List look (template, variant 3 → Odinson Glass plates):** figures as glass tiles on top (`Figures`), sections with a count, items as plates with a colored bar on the left, no letters avatar (`Plate`); row actions under a bare ⋮ and a swipe, Delete never asks — the Undo snack (`undoDelete`), a Select button above the list that shows the tick boxes and Select all (`useSelection` / `SelectBar`); a create button (New, New user, New firm…) is plain glass — `.og-new` on the button (`.gbtn.og-new` in `og.css`); on a phone windows open from the bottom (docs/components.md, docs/app-core.md → Layout). The Schedule tab too: a line per worker, its days opened under it.

## Keeping the docs true

When a change alters what a documented function does (parameters, control flow, data shape, who may call it), update the matching `docs/*.md` file in the same PR, describing only the current state. A debugging trail or a reverted approach goes to docs/history.md. Add a new `docs/*.md` file (and a row above) for a new tab or module rather than growing this file.
