# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Session language:** the user communicates in Russian. Claude's own conversational output (explanations, status updates, questions) should be in Russian throughout — independent of what language the app's UI/code is in.

**UI text language:** all new user-facing UI text (tab labels, buttons, messages) must be in English going forward. Most of the existing app is Hebrew (`lang="he"`); the `Бухгалтерия` (Accounting) tab is a Russian pocket added by mistake — don't repeat that. Existing Hebrew/Russian text doesn't need retranslating unless asked.

## What this is

A staff scheduling & GPS punch-clock PWA for a single client ("Odinson"), served as static files from Firebase Hosting. No build step, no bundler, no package.json, no test suite — the two pages are self-contained HTML files with inline `<style>`/`<script>`.

**Multi-tenant:** a super-admin creates "firms" (tenants) with their own login; each firm's data (schedule, punches, Drive docs) is isolated. See `MULTI_TENANT_PLAN.md` for the data model, auth design, and status. `apps-script/Код.js`/`google-apps-script.js` require session tokens on top of the legacy `API_SECRET`; `schedule-manager.html` has a login screen plus `gsAuth()`/`gsAuthQuery()` wrappers sending that token on every request.

### Files

- `schedule-manager.html` — the manager/admin app (shifts, workers, clients, payroll, exports). RTL, Hebrew (`lang="he"`), ~5000+ lines.
- `worker-punch.html` — the worker-facing clock-in/out app, opened via a per-worker tokenized link.
- `service-worker.js` — PWA offline shell (network-first, cache fallback). Never intercepts `script.google.com` — the API always goes straight to network.
- `manifest.json` / `manifest-punch.json` — installable-PWA manifests for the two apps.
- `google-apps-script.js` — backend Apps Script source (mirrors `apps-script/Код.js`, the one actually deployed). Backed by a Google Sheet acting as the database.
- `apps-script/appsscript.json` — Apps Script project config (timezone, runtime, web app access, OAuth scopes: `spreadsheets`, `script.external_request` for the Anthropic API, `drive`).
- `apps-script/.clasp.json` — clasp config linking local source to the deployed Apps Script project.
- `form101_fillable.pdf` / `heebo-hebrew.ttf` — source copies at repo root; the client no longer fetches these. `functions/assets/` holds the copies the Cloud Function actually uses. Re-sync `functions/assets/` from these if the template/font is ever updated.
- `form101-field-map.md` — verified field-by-field map of `form101_fillable.pdf` (every AcroForm field's name/rect/Hebrew label/meaning). **Consult and update whenever touching `functions/main.py`'s field rects or the PDF template changes** — drift between this map and the code is a known source of "fields land in the wrong place" bugs.
- `functions/` — Python Cloud Functions: `fill_form_101` (builds the Form 101 PDF via PyMuPDF) and `preprocess_scan` (runs AFTER the client's manual crop editor now — see the AI document scan flow section below — OpenCV auto-crop tightening, then Pillow contrast enhancement, then blur check). Has its own `venv/` (gitignored) — `firebase deploy --only functions` expects a pre-built virtualenv and won't create one; run `python -m venv venv && pip install -r requirements.txt` inside `functions/` before deploying from a fresh clone. **Note:** the blur threshold (`BLUR_VARIANCE_THRESHOLD`) was calibrated against pre-enhancement images; as of 2026-09-21 the check runs after enhancement, so post-enhancement blurry photos score higher on the Laplacian variance test — if genuinely blurry scans start passing in practice, raise the threshold.
- `MULTI_TENANT_PLAN.md` — data model, auth design, and status tracker for the multi-tenant feature.

## Commands

No npm/build/lint/test tooling — edit the HTML and reload.

- Local preview: `firebase emulators:start --only hosting`, or open the HTML files directly.
- Routing: `firebase.json` rewrites `/` → `schedule-manager.html`, `/punch` → `worker-punch.html`.
- **Deploy = push to `main` (via PR, see below).** GitHub Actions deploys on every push to `main`:
  - `.github/workflows/deploy.yml` — Firebase Hosting (project `schedule-odinson`).
  - `.github/workflows/deploy-apps-script.yml` — `clasp push --force && clasp deploy` for `apps-script/` (needs `CLASP_CREDENTIALS`/`CLASP_DEPLOYMENT_ID` secrets).
  - `.github/workflows/deploy-functions.yml` — deploys `functions/` on any push touching `functions/**`, or via manual `workflow_dispatch`. Builds a fresh venv in CI. `firebase.json`'s `functions[0].runtime` is pinned to `"python312"` for a deterministic runtime. On failure it opens/updates a GitHub Issue with likely causes — see Troubleshooting below for the known IAM permission gaps.
- When bumping the service worker's cache (`CACHE` constant in `service-worker.js`), increment the version string or clients keep serving stale HTML after deploy. Current version: v36 (as of 2026-09-27).
- `firebase.json`'s hosting `ignore` list must include `functions/**`, or `firebase deploy --only hosting` sweeps the entire `functions/venv` into the public hosting bucket.

### Git workflow (enforced by hooks in `.claude/settings.json`)

- **`My_Work_Befor_PR`** is the standing work branch — check it out (or resume the cloud session on it) at the start of work instead of `main`. Don't create ad-hoc branches per session.
- A `PostToolUse` hook auto-commits and pushes every file edit to the **current branch** (`git push origin HEAD`). This only fires in a session whose working directory *is* this repo at session start — a session rooted elsewhere that reaches this repo only via absolute paths/`cd` never loads this project's `.claude/settings.json`, so no auto-commits happen there.
- A `PreToolUse` hook blocks any `git push` that force-pushes, targets `main` by name, or runs while the current branch is `main`.
- A `SessionStart` hook injects `git status --short` + current branch as context automatically.
- A `PostToolUse` hook on `gh pr create*` diffs the PR's full range against this file and updates it via an agent — so this file should stay reasonably in sync with the code across PRs.
- **"Deploy" means: open a PR from `My_Work_Befor_PR` into `main` covering everything accumulated since the last one, then merge it — merging is what triggers the real deploy.** Never push/reset directly to `main`. Batch accumulated changes into one PR per deploy request rather than one PR per edit.
- **Never merge a PR without asking the user first.** Pushing to the feature branch needs no confirmation; merging to `main` always does.

## Architecture

### Backend: Google Apps Script

Both HTML files talk to the same Apps Script Web App endpoint (`GS_URL`, hardcoded near the top of each file's `<script>`), authenticated with a hardcoded shared secret (`API_SECRET`). Source lives in `apps-script/` (auto-deployed on push to `main`).

**GET endpoints:** `loadSchedule`, `loadPunchLog` (optional worker/date/type filters).

**POST endpoints** (require `API_SECRET`, and a session token except for `login`):
- Auth/tenant: `login`, `createUser` (super-admin, creates a firm), `updateTenant` (edit firm profile, returns refreshed `profile`), `loadTenantProfile`, `listTenants`/`setTenantActive`/`deleteTenant` (super-admin). **Critical:** `createUser`/`updateTenant` format phone/deductions-file-number fields as plain text (`setNumberFormat('@')`) *before* `setValue()`, or Sheets auto-coerces the digit string to a number and drops leading zeros (Israeli phone numbers, deductions file numbers) — corrupting what Form 101 prints. Pre-existing rows written before this guard, or via `migrateToMultiTenant()`'s initial tenant row, can still have this corruption; see Troubleshooting.
- Schedule/punches: `saveSchedule` (optimistic concurrency via `baseSavedAt`; `clients.radius` always coerced to a number; guards each `workers`/`clients` JSON blob against Google Sheets' ~50,000-char cell limit before writing — see "Optimizations (2026-09-27)" below), `savePunch`/`updatePunch`/`deletePunch`, `savePushSubscription`.
- AI document scan (all call the paid Anthropic API, all require `API_SECRET`):
  - `aiReadDoc` — main OCR call (passport/Israeli ID). Uses `ANTHROPIC_MODEL` (Script Properties; default `claude-sonnet-5` — deliberately not the cheap model, since a misread digit corrupts a real tax form). `max_tokens: 8000`, prompt-caching enabled. On JSON-parse failure, checks `stop_reason==='max_tokens'` to report truncation specifically rather than a generic parse error. Response includes `fieldBoxes` (bounding boxes for digit fields, for zoomed re-verification), `photoBox` (portrait location, used by `cropPortraitAvatar()` to build the worker avatar thumbnail), `imageAlign` (`{rotate, corners, crop}` for straightening), and `children` (Israeli ID ספח appendix, if present).
  - `aiDetectAlign` — lightweight rotate+corners-only sibling on a separate `ANTHROPIC_ALIGN_MODEL` (default Haiku). **Revived 2026-09-26** (was dormant 2026-09-21 through today) — `autoPreAlignScan()` (client) now calls it on every queued page in `processAllPendingPages()`, right before `preAlignScan()`'s classical-CV attempt. See that function's own comment and the "AI document scan flow" section below for why: the manual corner editor's real-world crops turned out rough enough, and the classical OpenCV detector unreliable enough on real photos, that an AI-guessed starting point is worth the small extra Haiku call after all.
  - `aiVerifyField` — re-reads a single already-extracted digit field from a tight zoomed crop (`kind`: `digits9`/`date`/`passportNo`). Uses the same accuracy-first `ANTHROPIC_MODEL` as `aiReadDoc`. Returns empty string rather than guessing if illegible.
  - `aiReadSefach` — narrow sibling of `aiReadDoc` for when the photo is known to be the address/ospח side of an Israeli ID (avoids `aiReadDoc`'s front/back type misclassification). Always returns `type:"israeli_id"`.
- Drive/documents: `saveWorkerDoc` (stores the assembled Form 101 PDF under `Schedule manager APP/<CompanyName>/Workers`, deduped by the ID/passport number extracted from the filename via `extractDocNumberFromFileName()`; accepts `previousFileId` to trash the exact old file), `deleteWorkerDoc` (by `fileId` or `fileName`, **requires `tenantId` to guard against cross-tenant file access**), `saveWorkerAssets`/`loadWorkerAssets` (a private JSON sidecar in a `Workers/Assets` subfolder holding the raw scan image + signature + extra pages, so a later field edit can regenerate the same PDF without re-scanning; also deduped by document number; **`loadWorkerAssets` requires `tenantId` parameter for cross-tenant security — validates via `_fileBelongsToTenant()` that the file belongs to the caller's firm**).
- `logError` — client error telemetry.

**Sheets:** `Schedule` (key/value: workers JSON, clients JSON, weekStart, savedAt), `PunchLog` (append-only, includes `ClientID`, `GPS Accuracy(m)`, `GPS Suspicious`, `GPS Warnings`), `Salary` (computed dynamically), `Clients`, `PushSubscriptions`, `Backups` (daily snapshot), `Errors` (last 500).

**Notable backend utilities:** `extractDocNumberFromFileName()` (longest run of 5+ digits — the stable identifier across rescans), `backupNow()`/`setupDailyBackup()`, `checkShiftReminders()`/`setupHourlyTrigger()` (push notifications for upcoming shifts), `normalizeClients()`. A handful of one-time migration/fix functions exist for historical sheet-schema drift (header renames, missing columns) — safe to re-run, look them up in `apps-script/Код.js` if a sheet looks like it needs one.

**Optimizations (2026-09-27):**
- Removed the dead `calcSalary` GET/POST endpoint and its `toMins()` helper from `apps-script/Код.js` (mirrored in `google-apps-script.js`) — grep across both HTML files confirmed no client code ever called it; it duplicated (cruder, no shift-grouping-across-midnight, no labour-law tiers) what `groupPunchesIntoShifts()`/`shiftPay()`/`israeliDayPay()` already do client-side.
- `saveWorkerDoc`/`saveWorkerAssets`'s duplicate-file cleanup now uses `folder.searchFiles("title contains '<docNumber>'")` instead of `folder.getFiles()` — the old code fetched metadata for every file in the folder over the Drive API just to check its name locally, an O(n) cost per save that grows with the roster; `searchFiles` lets Drive's own index filter server-side. `docNumber` (`extractDocNumberFromFileName()`) is always a `\d{5,}` digit run, so no quote-escaping risk in the query string. The exact-match check (`extractDocNumberFromFileName(f.getName()) === docNumber`) still runs locally on the (now much smaller) result set, so behavior is unchanged.
- `saveSchedule` now guards `workersJson`/`clientsJson` against Google Sheets' real ~50,000-char-per-cell limit (`CELL_SAFE_LIMIT = 45000`) before writing, returning `{error, tooLarge: true}` instead of letting a cryptic Sheets API exception surface mid-save on a large roster (many `avatarB64` photos). `gsSave()` (schedule-manager.html) shows a clear Russian toast on `json.tooLarge` instead of treating it like a generic failure.
- `aiFillForm101()`'s upload path fires `saveWorkerDoc` (the PDF) and `saveWorkerAssets` (the scan/signature sidecar) concurrently via `Promise.all` instead of one full round-trip after the other — they write to two independent Drive files and don't depend on each other's result. This runs behind a blocking "please wait" overlay for new workers/rescans, so halving the round-trip latency there is directly user-facing. Behavior change: `saveWorkerAssets` now fires even if `saveWorkerDoc` ultimately fails (previously it only ran after a successful doc upload) — acceptable since it's best-effort/independent and a retry re-uploads identical bytes harmlessly via the existing dedup.

### Client-side (schedule-manager.html)

- In-memory globals: `workers`, `clients`, `weekStart`, plus UI state (`selectedClientId`, `editingWorkerIdx`). No framework — mutate state, then call `render()`. `render()` refreshes the Schedule tab's own pieces every time, plus whichever *other* tab is currently open (keyed off `currentTab`) — so a mutation while sitting on e.g. the Workers tab reflects immediately rather than only after switching tabs away and back.
- **Google Sheets is the source of truth; `localStorage` is a cache/offline fallback only.** `loadData()` renders cached data instantly, then overwrites with the Sheets response. `autoSave()` debounces writes (800ms) and refuses to persist an accidentally-cleared `workers`/`clients` array over existing cached data. The cache key is scoped per tenant (`STORAGE_KEY()` → `schedMgr_v1_<tenantId>`) so switching firms as super-admin can't flash a different firm's stale cache; writes also mirror to the legacy unscoped `schedMgr_v1` key purely so `worker-punch.html`'s same-device `updateScheduleManager()` bridge keeps working.
- Each worker has a `token` (`genToken()`) used to build their personal punch-clock link (`buildPunchLink(w)`); `worker-punch.html` reads it via `?t=`.
- **XSS (CRITICAL):** `esc(s)` HTML-escapes `&<>"'`. Every `${...}` interpolating data into an HTML template must call it. Both HTML files have identical `esc()` definitions that must stay in sync.
- **Payroll math — canonical functions, never reimplement:**
  - `groupPunchesIntoShifts(entries)` pairs a worker's *entire* punch history into shift-buckets independent of calendar-day boundaries, so an overnight IN→OUT stays one shift instead of splitting (and losing hours) at midnight. Used by the salary table, CSV export, and punch-log analysis alike.
  - `analyzeDayPunches(entries, date)` pairs one calendar day's punches and flags anomalies (double-in, out-without-in, >12h shift, open shifts).
  - `effectiveRates(w, clientId)` resolves hourly rates through a 3-tier chain: per-worker-per-client override (`w.clientRates[clientId]`) → client's `defaultHourlyRate` → worker's base rate. `shiftPay(hours, w, isSat, clientId)` applies Israeli labour-law tiers (8h ×1.0, next 2h ×1.25, rest ×1.5; Saturday ×1.5/×1.75/×2.0) via `israeliDayPay()`, unless a flat OT/Shabbat override rate is set. This is domain-specific labour-law logic — don't simplify without expertise.
  - Client per-object default rates live on the client record (`defaultHourlyRate`/`defaultOtRate`/`defaultShabbatRate`, editable in the Add/Edit Client modal); the per-(worker,client) override matrix lives under the **Бухгалтерия** (Accounting) tab (`renderRateMatrix()`/`setClientRateOverride()`).
- **Бухгалтерия (Accounting) tab** (`#sectionAccounting`) holds all payroll/rate UI (`renderSalary()` + `renderRateMatrix()`). The Today/Dashboard tab (`renderDashboard()`) only shows real-time attendance: On Site Now, Should Be Here, Contract Expiry, Today's Log.
- **Contract-expiry warning** (opt-in per worker: `expiryEnabled`/`expiryMonths`/`expiryWarnMonths`): `workerExpiryStatus(w)` computes `{level:'warning'|'overdue', deadline}` purely from `startDate`, no backend involvement. Shown as a badge in the worker list/table and as a card on the Today tab when any worker is flagged.
- **Punch `clientId` tracking:** punches store the client's ID (not just a site name string), so payroll/history stay accurate even if worker-client assignments or client names change later. `punchSite(e)`/`punchClientObject(e)`/`workerClientName(id)` resolve display name vs. historical-at-punch-time client.
- Admin punch log filters by `workerId`/`clientId` (not name), so two workers sharing a name don't collapse together.
- Exports: `exportExcel` (SheetJS/xlsx from CDN), `exportPDF`, `exportJSON`, `exportSalaryCSV`, `exportPunchCSV` — salary export goes through `groupPunchesIntoShifts()` like everything else.

#### Worker modal (`showWorkerModal()`)

Single screen for adding a worker by hand, editing an existing one, and reviewing/completing a document scan — there's no separate post-OCR screen. Field order has shifted several times by request; check the actual template rather than assuming a layout. Notable behavior:

- `w.name` is derived from `docGiven + ' ' + docSurname` on every save. **A worker whose record predates this split (only has `name`, no `docGiven`/`docSurname`) gets those fields derived on the fly when the modal opens** (split on first space) — this is display-only until an actual save persists it. Without this fallback the name fields render blank for such a worker, and `saveWorker()`'s "name required" guard then silently no-ops the entire save (nothing persisted, no toast) if the manager doesn't happen to retype the name.
- `__wDocType` (seeded from `w.docType`, defaulting to `'israeli_id'`) is captured into `commonFields.docType` on save — needed so a worker scanned from a foreign passport doesn't get silently relabeled `israeli_id` after its first PDF upload (which is what happens if `docType` isn't threaded through explicitly).
- **Every save auto-generates/uploads the Form 101 PDF in the background.** Three paths, chosen in `saveWorker()`:
  - **New worker:** blocking `autoUploadWithRetry()` (spinner overlay, one retry on failure) using the live scan globals (`window.__aiScanImage`/`__aiPacketOtherPages`).
  - **Rescan of an existing worker** (`rescanWorkerDoc()` → `openAiScan()` → ... → `openWorkerModalFromScan()`, which sets `editingWorkerIdx` to that worker AND `window.__aiRescannedWorkerId` — a flag that, unlike `window.__aiRescanWorkerId`, survives until `saveWorker()` consumes it): **also** the blocking `autoUploadWithRetry()` path, same as a new worker — the manager just captured brand-new photos, so the regenerated PDF must actually use them. **Fixed 2026-09-26** — this branch didn't exist before: every rescan of an existing worker silently fell through to the plain-edit path below, which reads the Drive sidecar and discards the fresh scan entirely. A manager could rescan a worker any number of times (through today's server-economy reorder, collect-then-batch, `refineWithAiAlign`, and the geometric auto-crop re-enable, none of which ever visibly took effect for a *re*scan) and the PDF's embedded photo would never change — only creating a brand-new worker record ever exercised the live-scan path. `window.__aiRescannedWorkerId` is cleared immediately after use either way (consumed by this branch, or left stale-but-harmless if the save that follows a rescan never happens). **Regression fixed 2026-09-27:** the live-scan path's `otherPagesToUse` (`aiFillForm101()`) was always `window.__aiPacketOtherPages` — only THIS session's queued extra pages — so rescanning JUST the primary card (front ID/passport) without re-adding a previously-scanned ספח/contract page silently wrote a NEW Drive sidecar with `extraPages:[]`, permanently discarding the old ones (`saveWorkerAssets(..., previousFileId: w.assetsFileId)` trashes the file it replaces). Fixed: when the rescan path's own `otherPagesToUse` is empty and the worker already has an `assetsFileId`, `loadWorkerAssets` fetches the OLD sidecar's `extraPages` and uses those instead — carrying them forward untouched. Only triggers when this session captured no extra pages itself; scanning a fresh ספח in the same rescan session is used as-is, no fallback fetch. Verified via headless-browser tests for both cases.
  - **Plain field edit on an existing worker** (no rescan this session): non-blocking `regenerateWorkerDoc()` (toast on completion) whenever a field in `FORM101_WATCHED_FIELDS` actually changed — this reads the scan/signature back from the Drive sidecar (`w.assetsFileId`) rather than the live globals, since those could belong to an unrelated in-progress scan elsewhere in the same tab. `FORM101_WATCHED_FIELDS` = `docId, address, houseNumber, city, incomeType, otherIncomeType, docSurname, docGiven, maritalStatus, healthFund, workStartDate, phone, docSex, docDob, docChildren`. A worker that's never had a document generated still regenerates fine (empty scan/signature, text-only PDF).
- Duplicate-worker guard on creation: a new worker's `docId` is checked against every existing worker's `workerDocId()` (not name — a document number is unique to one person); `confirm()` on a match, cancel aborts creation entirely.
- Deleting a worker also trashes their Drive PDF (`w.docFileId`, falling back to parsing `w.docUrl`) and asset sidecar (`w.assetsFileId`), best-effort.
- Digit-field verification: `isValidIsraeliId()` is a pure Luhn-style checksum (no AI call). `verifyDigitFields()`/`verifyIdChecksum()` re-verify OCR'd digit fields via a zoomed `aiVerifyField` re-read when the checksum doesn't already pass; a still-failing checksum surfaces as an amber warning under the docId field rather than silently keeping a wrong number.

#### AI document scan flow

`onScanFileSelected`/`onScanFilesSelected` → **manual corner-adjustment editor** (`renderScanQuadEditor`/`initScanQuad`/`attachQuadDrag`, drag 4 SVG handles) on the raw downscaled photo → `confirmScanQuad()` perspective-warps the quad flat via `warpQuadImage()` (homography math: `computeSquareToQuadHomography`/`applyHomography`/`bilinearSample`, output capped at 1568px long edge) → the cropped page is **queued**, not processed yet (`window.__pendingScanPages`, `renderPendingPagesPrompt()`) → once the user is done adding pages, `processAllPendingPages()` sends the whole queue through `autoPreAlignScan()` (cheap Haiku corner detection) + `preAlignScan()` (server contrast enhance + blur check) + `aiReadDoc`/verify/merge + `refineWithAiAlign()` tightening, once → `renderScanPagesPrompt()` → `openWorkerModalFromScan()`.

- **Collect-then-batch (added 2026-09-26, per user request):** cropping a page no longer sends anything to the server by itself. `confirmScanQuad()`/`skipScanQuad()`, when `window.__scanEditPurpose==='collectPage'` (the normal case — set by `onScanFileSelected`), just push `{b64,mediaType}` onto `window.__pendingScanPages` and show `renderPendingPagesPrompt()` (thumbnail queue, "add page" / "process N pages", every thumbnail removable since nothing's been classified yet). Only `processAllPendingPages()` (that screen's "process" button) talks to the server — it mirrors `onScanFilesSelected`'s own classify/merge loop (first `israeli_id`/`passport` page found becomes primary, verified via `verifyDigitFields`/`verifyIdChecksum`; later pages merge missing core fields via `mergeIsraeliIdFields`/`CORE_FIELDS`/`missingCore` — now module-scope, shared by both loops — until none are missing; anything past that needs no further AI call), but runs `autoPreAlignScan()` then `preAlignScan()` per queued page first (see both functions' own comments — enhance+blur-check on the already-cropped image, same as the reordered single-page flow below). One blurry page aborts the loop and is dropped from the queue on its own (the rest of the already-cropped queue is preserved, not lost) — the user re-crops just that one page and presses "process" again. Resumable: `renderScanPagesPrompt()`'s own "add page" button also routes through `onScanFileSelected` → the same pending queue, so adding "just one more page" after already reviewing a first batch still batches, picking up the existing primary/otherPages instead of starting over.
- **`autoPreAlignScan()` revived (2026-09-26, per user request — "drop the classical-CV variants, hand alignment to a cheap AI model instead, a bit of token cost is fine"):** called from `processAllPendingPages()` on every queued page, right before `preAlignScan()`. It was dormant since 2026-09-21 (see its own comment for that history) on the theory that the manual corner editor made an AI-guessed starting point unnecessary — but this same day's real-photo diagnostic (see `preprocess_scan`'s own note below) showed manual crops staying rough in practice and the classical OpenCV detector failing on real backgrounds regardless of hardening. `aiDetectAlign` (Haiku, cheap — small prompt, no field extraction) reads the document's rotation+corners directly from the vision model, which generalizes to messy real photos far better than hand-tuned edge heuristics; `autoPreAlignScan()` then rotates (`alignScanImage`), pixel-refines the guess (`refineQuadCorners`, pure local pixel math, no extra AI call), and warps (`warpQuadImage`) — falling back to the untouched image on any missing/invalid response, same safety net as before. `preAlignScan()`'s own classical-CV pass still runs afterward, now on this already-better-aligned image, as a free additional (if largely redundant) safety net — left in place since it costs nothing and occasionally still helps on a cleaner background. Verified with a mocked `aiDetectAlign` response (classical CV deliberately mocked to fail, matching the real diagnostic) through the full real batch pipeline: a rough ~40%-of-frame rotated synthetic crop came out straightened and tightly cropped to just the card.
  - The temporary `pushScanDebug()`/`window.__scanDebugLog` diagnostic instrumentation (added 2026-09-26, used to chase the uncropped/tilted photo and black-sliver bugs) was **removed 2026-09-27** once the root cause was found and fixed (`finalTightenPass()` below) — no longer present in the code.
  - **`refineQuadCorners()` hardened for precision (2026-09-26, ongoing):** the residual tilt/black-sliver traced to two main causes, fixed in two stages:
    - **Stage 1 (2026-09-26)** — (1) each edge sample snapped to the nearest whole PIXEL step in its search window, and a real photo's own optics/JPEG blur mean the true edge often falls *between* pixels — a systematic sub-pixel bias per side adds up across the whole quad into a visibly crooked result even when every individual sample looks "close enough"; fixed with a parabolic subpixel interpolation around each sample's peak gradient, plus more samples per side (12→20) and a tighter margin (0.18→0.12, sampling closer to the true corners for more/better line-fit data). (2) the fixed gradient-magnitude floor (18) rejected every sample on a real worn/low-contrast/glare-affected card edge (measured peaks as low as ~13-17 in a degraded synthetic test), silently discarding the whole per-side refinement and leaving the AI's raw (imprecise) corner guess in place untouched — lowered to 12. An adaptive per-point threshold (relative to that same point's own local noise floor) was tried first and reverted: it let pure sensor/JPEG noise with no real edge at all snap to false "edges" (verified up to ~17px of spurious drift on a flat noise-only test image, vs 0px before), which the plain lower floor does not (verified still 0px drift on the same noise test — noise's own peak gradients topped out around 11 in testing, safely under the new 12 floor). Verified via headless-browser tests with known ground-truth corners: a clean high-contrast synthetic edge refines to ~0.02° of the true rotation angle (was already accurate before this change); a low-contrast/blurred/noisy synthetic edge — designed to fail under the old N=12/margin=0.18/threshold=18/no-subpixel settings — now also refines to ~0.02° (previously fell back to the raw, ~1°-off AI guess untouched); a pure-noise (no real edge) image still produces 0px drift, matching the pre-change safe-fallback behavior.
    - **Stage 2 (2026-09-27)** — real-device retest showed the ospח page now cropping/straightening correctly, but the front תעודת זהות (Israeli ID) page still coming out visibly tilted with a black sliver: its busier surface (holographic watermark pattern) most likely makes `aiDetectAlign`'s own initial corner guess less precise than on the plainer ospח side. Root-caused via synthetic tests with a deliberately large (up to ~110px on a 1000px-wide test image, ~11% of frame) initial-guess error on one or more corners: (1) `maxDrift` (the safety cap rejecting a computed corner that lands "too far" from the AI's own guess, on the theory that a big jump means a bad line fit rather than a real correction) at its old 0.12-of-frame value rejected a *individually verified-accurate* correction (<1px error) on some corners while accepting others, producing an inconsistent, visibly warped quad — measurably worse than either the fully-raw guess or the fully-corrected result; raised to 0.35. (2) at the same large initial error, the per-point search radius (`SEARCH`, ~2% of frame) was often too narrow to even reach the true edge from a badly-off sample point, so the affected side's line fit failed outright (returned null) rather than merely landing outside `maxDrift` — independent of the `maxDrift` fix above; widened to ~4% of frame.   - `_preAlignThenOcr()`/`runOcr()` are DORMANT as of this change — nothing in the live UI sets `__scanEditPurpose==='preOcr'` anymore (that's what those two functions gated on); left defined, working, in case an immediate no-batch fast path is wanted again later.
- **`preAlignScan()` runs after the manual crop, not before** (reordered 2026-09-26, per user request, for server economy) — it's called on `warpQuadImage()`'s already-cropped-to-just-the-document output (now from inside `processAllPendingPages()`'s loop), so its resize/enhance/blur-check all run over far fewer pixels than when they covered the whole original photo including background. Trade-off: the user crops on a photo without the contrast/sharpness boost yet, and a blurry photo is only caught *after* the user has positioned the rectangle (and, with the collect-then-batch change above, potentially after cropping several *other* pages too — only the offending one is dropped).
- The corner editor runs **before** OCR, not after — the user positions the rectangle themselves on the raw photo; no AI-guessed starting rectangle. `initScanQuad()` reads the displayed `<img>`'s `clientWidth/clientHeight` to build the coordinate space — this must happen after both image decoding and layout are complete. A single `requestAnimationFrame` (the old fix) assumes one frame suffices for the browser to decode a large data-URI photo on all hardware; on slower/mobile devices this wasn't guaranteed, and the bug recurred even with the rAF defer. `renderScanQuadEditor()` now uses `img.decode()` (resolves only when the image is fully decoded, regardless of frame count), followed by one more rAF for layout — it falls back to the rAF-only approach if decode() throws or isn't supported. **Critical:** on some mobile browsers, `decode()` can apparently never settle (neither resolve nor reject) for a large data: URI, which prevented `initScanQuad()`/`attachQuadDrag()` from ever running, leaving the crop rectangle stuck non-interactive. The call is now capped at 1.2s with `setTimeout()` — if decode hangs, the timeout fires anyway and lets the editor become usable (fallback to uncropped original if crop never ran). Reading `clientWidth` before both are complete reads `0`, which locks the crop rectangle at a degenerate point and makes `warpQuadImage()` throw — silently caught, falling back to the *uncropped* original photo. The 4 corner drag handles are radius=13 (26px diameter, shrunk from 20 across several requests on 2026-09-26/27: 20→18→15→13) drawn offset ~6.5pt inward from the true corner toward the quad's own centroid (`paintQuad()`, inset raised from 3.5pt on 2026-09-27 — still hard to grab a corner sitting right at the photo's edge) — purely a visual nudge; `window.__quadRect[key]` (the actual crop-math coordinate `attachQuadDrag()`'s pointermove writes to) is untouched, and pointerdown hit-testing still keys off the handle's `data-c` dataset attribute rather than its drawn position, so the offset can't desync the drag from the true corner. Pointerdown hits only the visible circle (no padding), so a larger radius makes dragging more reliable on small screens — this is the reason the radius was never dropped further despite repeated requests to shrink it, in favor of moving the handle inward instead.
- **Whole-edge drag (added 2026-09-27, per user request — "let me move the whole horizontal/vertical line, not just one corner at a time"):** 4 invisible `<line>` elements (`.quad-side-handle`, `stroke-width:24` for a generous touch target, drawn *before* the corner circles in DOM order so a corner handle still wins the hit-test where they overlap) sit along each of the quad's true edges (positioned in `paintQuad()`, keyed off `SIDE_CORNERS` — `{top:['tl','tr'], right:['tr','br'], bottom:['br','bl'], left:['bl','tl']}`, shared with `attachQuadDrag()`). Dragging one translates BOTH of that edge's corners by the same raw pointer delta (captured at pointerdown, applied cumulatively as the pointer moves, each clamped independently into `[0,imgW]x[0,imgH]`) — a rigid parallel shift of that whole side while the other two corners (and the adjacent sides meeting them) stay fixed, the standard "drag an edge" gesture from a photo-crop tool. Verified via a headless-browser test: dragging the top edge's handle by a given pixel delta moves `tl`/`tr` by exactly that delta while `br`/`bl` stay untouched.
- `preprocess_scan` (the Python endpoint): geometric auto-crop (`_find_document_quad`/`_warp_quad`, OpenCV contour detection) is **re-enabled** (2026-09-26) — real scans were coming out with the manual crop's own rough background/skew untouched, because `refineWithAiAlign()`'s AI-based tightening (below) requires its guessed quad to cover ≥50% of the frame before trusting it, which a rough manual crop routinely fails, so nothing was actually getting tightened in practice. Safe to re-enable for a different reason than why it was originally disabled: it used to run **before** the manual corner editor, so it could lock onto one of two documents photographed together (e.g. a passport + its ספח insert) and silently discard the other; since the 2026-09-26 reorder this function only ever runs **after** the manual editor, so the input is already a single document — there's no second document left to lose. A confident match (passes `MIN_QUAD_AREA_FRAC`/`MAX_QUAD_AREA_FRAC`) tightens the crop; anything low-confidence (very low-contrast background, no plausible-sized contour at all) leaves the image untouched, same as before.

**Hardened for real phone photos (2026-09-26, same day):** the clean-synthetic-image version above worked in testing but a manager's actual rescan on a real device still came out uncropped — real photos carry glare, sensor/JPEG noise, uneven lighting, and worn/scuffed cards that a plain fixed-threshold Canny genuinely struggles with (this isn't a bug so much as a known limitation of simple contour detection on messy real input). `_find_document_quad()` now: (1) applies CLAHE (local contrast normalization) before edge detection, so a real glare/shadow-uneven background doesn't swamp the document's own edges; (2) denoises with `cv2.bilateralFilter` (smooths noise while preserving true edges, unlike a plain Gaussian blur, which softens both) — `sigmaColor=40` chosen by testing against a battery of degraded synthetic cases (glare, motion blur, sensor noise, a worn/scuffed card, low card/background contrast) and picking the value that passed the most of them; (3) uses `_auto_canny()` (median-intensity-based threshold, a standard technique) instead of fixed 50/150 — a real photo's overall exposure varies too much for one fixed pair of numbers; (4) falls back to the largest plausibly-sized contour's `minAreaRect` when no clean 4-point convex polygon is found (a rounded card corner or a bit of noise routinely turns one straight edge into 5-6 slightly-bent points, failing the old strict `approxPolyDP`-must-be-4-points check even though the contour itself is clearly the document). Re-verified against the same battery: 6 of 7 degraded cases now detect correctly (only an inherently ambiguous low-card/background-contrast case still safely declines, matching the "leave it untouched, don't risk a bad guess" design). Enhancement then runs on the (possibly now auto-tightened) image before the blur check. The blur threshold was calibrated on a pre-enhancement, full-frame photo; enhancement can inflate variance scores, and the input is now a cropped-to-document image rather than the full frame — either change alone could shift what the check actually measures, so if obviously blurry scans start passing, `BLUR_VARIANCE_THRESHOLD` may need adjustment.
- Multi-file / multi-page uploads (`onScanFilesSelected`, picking several files or a multi-page PDF at once): still its own separate path with **no manual crop step at all** — each page goes straight to `aiReadDoc` for classification (an already-filled Form 101 is dropped and always regenerated fresh; the first ID/passport page becomes primary; a ספח page's blank-filling fields — `dob/sex/address/city/houseNumber/maritalStatus` — merge into the primary record regardless of which physical card came first), landing in the same `renderScanPagesPrompt()` review screen the batch-crop path above also uses.
- Worker's own mobile number is a plain modal field (`#wPhone`), not scanned — printed on the PDF via a synthetic `worker_phone` field (no real AcroForm field there).
- Each page's own raw parsed data is kept in `window.__aiPageParsed` (parallel to the `renderScanPagesPrompt()` thumbnail strip). Removing a page (`removeExtraScanPage()`) doesn't just drop its thumbnail — it recomputes the primary record from scratch via `rebuildPrimaryFromPages()`/`mergeScanPage()`, so a bad/misread extra page's merged fields (address, city, marital status, an `idMismatch` flag, ...) don't silently survive its own removal.
  - **`processAllPendingPages()` unified with this same merge logic (2026-09-27)** — it used to build `foundParsed` with a hand-rolled `p`-direct-assignment (primary page) and a bare `mergeIsraeliIdFields()` call (merge page), a *different* algorithm than `rebuildPrimaryFromPages()`'s `initPrimaryFromFirstPage()`/`mergeScanPage()` — so removing a page via `removeExtraScanPage()` could recompute a different-looking primary record than how the batch loop originally built it. Now routes through the same two functions. Also a real fix on its own: `mergeIsraeliIdFields()` alone never backfills a missing `idNo` from a later page (`idNo` isn't in `ID_CORE_FIELDS`) — `mergeScanPage()` does. Verified via a headless-browser test: a primary page with a blank `idNo` correctly gets it backfilled from a later merge page.
- **`refineWithAiAlign()` tightening pass** (`aiReadDoc`'s `imageAlign`, tightens the user's own manual crop, never replaces it, falls back to the untouched image on any missing/implausible corners) — added to `processAllPendingPages()` (2026-09-26, per user request: "manual crop, then auto-fit right when the batch is sent for processing") for the primary page and for any page whose `aiReadDoc` response actually ran (the merge-page branch); it's free — piggybacks on the `imageAlign` field of an `aiReadDoc` call the batch loop was already making for field extraction, no extra AI cost. A page that needed no `aiReadDoc` call at all (every core field already complete by the time it's reached) has no `imageAlign` to refine with and keeps the user's raw manual crop as-is. `onScanFilesSelected`'s own no-crop batch loop still never calls it (nothing to tighten there — it never crops in the first place).
  - **`finalTightenPass()` added 2026-09-27** — a real-device test's debug log showed `aiDetectAlign` finding a reasonable quad and `refineWithAiAlign` applying its own tightening, yet the final embedded photo still had a thin black background sliver on the left/right edges. Root cause: that run's `refineWithAiAlign` corners were full-width (`x:0` to `x:1`, only trimming top/bottom) — whatever thin sliver `autoPreAlignScan`'s own corner detection left on the *other* axis was never re-examined by anything downstream. Rather than chase why one specific run's AI corners came out full-width, this adds an unconditional final safety net after every page's alignment chain (primary page, merge page, and the "no aiReadDoc call needed" page that skips `refineWithAiAlign` entirely) that treats the image as already axis-aligned (safe by this late stage, after the full perspective warp) and scans each of the 4 sides **independently** for a real edge just inside a small starting margin, trimming only the sides where one is confidently found (`_scanSideEdge()` — 16 samples per side, median offset, same gradient/subpixel technique as `refineQuadCorners`, but per-side rather than per-corner). This independence is the actual fix for the reported bug: `refineQuadCorners`' own line-**intersection** approach requires both sides meeting at a corner to have signal before it can move that corner at all, so a photo already perfectly cropped top/bottom (no edge signal there — correctly left alone) could never have its left/right sides corrected even when those had a clear, confidently-detected edge of their own. Verified via headless-browser tests: a sliver on both left/right sides is trimmed correctly; a sliver on only one side is trimmed independently of the others; a low-contrast sliver is still found; an already-tight image and a pure-noise (no-edge) image both produce a safe no-op with zero re-encode cost.
  - **`_isNearIdentityQuad()` optimization (2026-09-27)** — a single scanned photo can pass through up to 4-5 sequential `warpQuadImage()` calls in this chain alone (`autoPreAlignScan`, `refineWithAiAlign`, `finalTightenPass`) plus the server's own `_shrink_for_embed()` at PDF-embed time — each one a JPEG decode+re-encode, and thus generation loss, even when that particular pass found nothing worth cropping/rotating. `autoPreAlignScan()` and `refineWithAiAlign()` now check the quad they're about to warp with against `_isNearIdentityQuad()` (all 4 corners within ~1% of the untouched full frame) and skip the warp entirely when it would be a lossy no-op copy. `finalTightenPass()` already had its own equivalent skip (comparing against its own starting margin). Verified via headless-browser tests: an identity quad is correctly detected and skipped (same bytes back), while a real crop still goes through unchanged.
  - **Server-side geometric auto-crop (`_find_document_quad`/`_warp_quad` in `functions/main.py`) made DORMANT again (2026-09-27)** — was re-enabled 2026-09-26 back when the client-side tightening wasn't reliable enough on a rough manual crop; now that `autoPreAlignScan`/`refineQuadCorners`/`finalTightenPass` (above) run client-side *before* this endpoint ever sees the image, running a classical-CV quad detector on an already near-final crop is both a wasted CLAHE/bilateral/Canny/contour pass on every scan AND a regression risk — with little background left to find a document/background boundary against, it can lock onto a strong internal element (the photo, the chip icon, a text block) instead and crop INTO the document. Left defined, unused, matching the same dormant-but-kept pattern as `_preAlignThenOcr()`/`runOcr()` on the client — revive if a future client-side regression makes it worth it again.
  - **Trust floor lowered 50% → 8% of frame (2026-09-26, same day as the hardening above)** — real-world testing (a real photo extracted from an actual generated PDF) showed the classical OpenCV detector (`_find_document_quad`, above) failing to close a clean contour around the card even after CLAHE/bilateral/auto-Canny hardening: the largest edge-based contour found was only ~7% of frame, and a brightness-threshold (Otsu) alternative also tried during debugging leaked into the background along one edge, both symptomatic of a real (not pure-black, not perfectly lit) background rather than a bug. `quadAreaFrac(align.corners)<0.5`'s original 50% floor assumed the manual crop already left mostly-document in frame (a pure tightening pass) — real usage crops far more loosely (~20-35% document-in-frame observed), so that floor rejected the AI's own correct card-boundary guess every single time, which is the opposite of what it was meant to help with. Lowered to 0.08 — still guards against the one real failure mode (the AI locking onto a small internal sub-element, e.g. just the portrait photo, which sits far under 8% of even a rough crop) without penalizing an honestly loose manual crop. Not independently re-verified end to end (would need a real `aiReadDoc` call against a real photo, which costs real Anthropic API usage) — reasoned from the same real photo's OpenCV-detector failure above, but if document photos are still coming out uncropped after this ships, that's the next number to look at, alongside whether `aiReadDoc`'s own `imageAlign` guess is landing anywhere near the true card boundary at all for this kind of photo.

#### Form 101 PDF generation (server-side, `functions/main.py`)

`aiFillForm101()` client-side only assembles a JSON payload (name/dob/sex/id/address/marital/health fund/children/employer profile/signature PNG/extra scan pages) and POSTs to `FORM101_FN_URL`; the Python Cloud Function (PyMuPDF) builds the actual PDF bytes and returns `{pdfBase64, fileName}`. See `form101-field-map.md` for the field/rect map.

- **PDF-embed image optimization (added 2026-09-26):** `build_form101_pdf()` shrinks each embedded scan/signature image via `_shrink_for_embed()` (Pillow, downscale to `EMBED_DPI`=150 sized to the actual PDF box + re-encode, JPEG for scans, PNG for the alpha-channel signature) right before `insert_image(..., stream=...)` — deliberately only at this final embed step, never earlier in the scan pipeline, since OCR/digit verification have already run upstream on the full-resolution image by then (shrinking here can't affect field-extraction accuracy, only the generated PDF's file size). `finalize()`'s `doc.tobytes()` also now passes `garbage=4, deflate=True, deflate_images=True, clean=True` for container-level cleanup. The raw, unshrunk scan is still preserved separately in the Drive asset sidecar (`saveWorkerAssets`) for future regeneration.

- Fields are addressed by name on `form101_fillable.pdf`'s own AcroForm markup (`Form101Builder.set_hebrew()`/`set_comb()`/`set_text_centered()`) — there's no from-scratch field creation except `SIG_RECT` (the signature image, which needs a rect since it's an image, not a form field). One field is mapped despite its name: `employer_zeut_num` actually holds the **worker's own** Israeli ID number (verified by position, not name).
- PyMuPDF has no RTL/BiDi shaping — every Hebrew-capable field is corrected via `python-bidi`'s `get_display()`, then the field's auto-generated appearance is blanked and the corrected text is hand-drawn on the page (`_blank_appearance()`/`_draw_rtl_text()`). Comb (digit) fields don't need this — LTR digit runs render fine through PyMuPDF's own appearance.
- Children: 6 template row-slots (`CHILD_FIELD_SUFFIXES`), each scanned child's combined name split on the first space into given/surname.
- `FIELD_RECT_NUDGES` holds small per-field `(dx, dy)` point offsets applied to the actual widget rect for one-off position corrections — add further nudges here rather than re-editing the PDF template by hand.
- `functions/venv` must exist locally before `firebase deploy --only functions` (see Files above); CI builds its own venv fresh and never touches the committed one.

### worker-punch.html

- Reads `?t=<token>` to jump straight to that worker's screen; without one, shows a worker picker.
- `getLastEntry()` looks at a worker's most recent punch **across all days** (not just today) to decide Clock IN vs. OUT.
- `openHistory()`'s per-day totals pair punches into shifts chronologically (its own from-scratch port of `groupPunchesIntoShifts`, since this file doesn't import from `schedule-manager.html`) *before* grouping by date — grouping by calendar day first would split an overnight shift's hours across two days and lose them from the worker's own history view.
- GPS anti-spoofing (`analyseGps`/`getLocation`): flags zero/low accuracy, impossibly fast movement between readings, and suspiciously instant geolocation responses before allowing a punch within the site's radius.
- Offline-safe punches: `doPunch()` always writes to local `punchLog`, and queues to `punchQueue` for later resync if the Sheets `savePunch` call fails.

### Shared conventions across both files

- No modules/imports — everything is global functions/consts inside one inline `<script>` per file; follow this style rather than introducing bundling.
- Both files **duplicate** constants and helpers on purpose (no shared build): `GS_URL`/`API_SECRET`, `esc()`, `reportError`, `showToast`, `getPunchLog`/`savePunchLog`, `groupPunchesIntoShifts`, `analyzeDayPunches`. A fix in one (API URL rotation, `esc()` improvement, payroll logic) must be mirrored in the other.
- Push notifications: both subscribe via `savePushSubscription`; `service-worker.js` handles `push`/`notificationclick`.

## Troubleshooting

### A tenant's phone / deductions file number prints without its leading zero on Form 101

`createUser`/`updateTenant` already guard against this for new writes (see Backend section above). If it's still happening, the cell is **pre-existing data** written before that guard existed, or via `migrateToMultiTenant()`'s initial tenant row — it's stored as a plain Sheets number and stays broken until rewritten. Fix: Super-admin → Фирмы → edit (pencil) that firm and re-save the phone/deductions field through the normal form; the protected write path fixes it going forward.

### "Deploy Cloud Functions" CI fails with "Missing permissions required for functions deploy" / `iam.serviceAccounts.ActAs`

The `FIREBASE_SERVICE_ACCOUNT` identity needs the **Service Account User** role (`roles/iam.serviceAccountUser`) granted *directly on the runtime service account's own Permissions tab* (not the project's general IAM page) — this is a per-resource grant, `iam.serviceAccounts.actAs`. Needs a human with IAM-admin rights in GCP Console; cannot be done via `gh`/CLI.

This has recurred against more than one service account on this project: first `schedule-odinson@appspot.gserviceaccount.com` (App Engine default), then `<PROJECT_NUMBER>-compute@developer.gserviceaccount.com` (Compute Engine default — the actual 2nd-gen Cloud Functions runtime identity, since they run on Cloud Run under the hood). If a *third* service account shows up in a future `actAs` error, grant it the same way — this is a known pattern for first-time 2nd-gen Functions setups on a project, not a misconfiguration. Also needed at various points: Cloud Functions Admin, Service Usage Consumer, Cloud Build Editor, Artifact Registry Writer, Cloud Run Admin, Eventarc Event Receiver (project-level roles, for "API not enabled"/403 errors during early deploy steps).

The workflow's `firebase deploy` command passes `--force` to auto-accept the Artifact Registry cleanup-policy prompt (otherwise fails non-interactively) — unrelated to the actAs errors, but would be the next failure once those are fixed.

Re-run via `gh workflow run "Deploy Cloud Functions" --ref main` after granting a role, or wait for the next push touching `functions/**`.

### "Deploy to Apps Script" CI fails with `invalid_grant` / `invalid_rapt`

Cause: this is a Google Workspace account (`stas@odinson.ltd`), and Workspace periodically forces OAuth re-authentication for the scopes `clasp` uses, invalidating the refresh token in the `CLASP_CREDENTIALS` secret. This re-auth is a real browser login — cannot be scripted in CI.

Fix: run `scripts/refresh-clasp-login.sh` on a machine with a browser. It logs in via the Web OAuth client at `H:\Tokens\Google api.json` (Cloud Console project `schedule-manager-498317`, redirect URI `http://localhost:8085`), pushes the fresh token to the `CLASP_CREDENTIALS` secret via `gh secret set`, then re-triggers via `gh workflow run "Deploy to Apps Script"`.

Note: `clasp login --creds` requires a `redirect_uris` array *inside* the creds JSON itself, or it fails immediately with "Invalid redirect URL" before opening a browser.

`deploy-apps-script.yml` self-detects this failure and opens/updates a GitHub Issue titled "Apps Script deploy failing — clasp token needs refresh" pointing at the fix script — watch for that Issue rather than the Actions tab.
